# 关键机制（勿回归）

> 中文版 | [English](critical-mechanisms.md)

> 本文档记录 Driftlet 中容易因改动而回归的关键机制（窗口与桌面层级、安装链路、数据流等）。修改 `src-tauri/src/desktop.rs`、`window/factory.rs`、`window/snap.rs`、`skin/protocol.rs`、`lib.rs`、`commands.rs` 及相关前端代码前，请先阅读对应章节。

---

## 无边框机制

皮肤窗口“时有时无经典标题栏”的根因与防线：

1. **`SetWindowSubclass` 必须在窗口所属线程调用**。`load/reload_skin` 如果在 `spawn_blocking` 工作线程跑，跨线程调用会静默失败，窗口残留 tao 的 `WS_CAPTION` 样式，DWM 据此画出经典标题栏。安装/重装一律走 `install_frameless`（主线程直跑 / `run_on_main_thread` 会合），5 秒定时器在主线程幂等重装自愈。
2. **禁止 `DwmExtendFrameIntoClientArea(-1)`**。玻璃延伸会把任何 DWM 边框画进整个客户区，透过透明皮肤看到标题栏。
3. `SWP_FRAMECHANGED` 只在样式真的变脏时发送。无条件调用会让 DWM 反复重评估窗口边框，等于不停给边框出现的机会。
4. tao 的 `to_window_styles()` 对顶层窗口永远带 `WS_CAPTION`，且任何 `set_window_flags`（如 `set_always_on_top`）都会经 `apply_diff` 重写样式——靠子类的 `WM_STYLECHANGING` 同步拦截兜底。

## 贴在桌面

1. **Win+D 的真实机制**：皮肤**不会被最小化**——无边框样式剥掉了 `WS_MINIMIZEBOX`，minimize-all 只针对可最小化窗口。皮肤“消失”是 **z 序遮挡**：Show Desktop 会把桌面图标宿主（和壁纸 WorkerW）抬到非置顶带顶部，盖住桌面层的一切。任何“状态切换时一次性重排”的方案都会与这个抬升赛跑而失败。
2. **现行方案 = 持续 z 序贴附**：250ms 定时校验每个贴桌面皮肤是否就位（判定 = **紧下方是图标宿主或另一个贴桌面皮肤**——多皮肤时严格的「正好在宿主正上方」不可能同时成立，曾导致 ≥2 个皮肤每 tick 相互翻转、各吃一次 SetWindowPos），偏离就插回**桌面图标宿主（`SHELLDLL_DefView` 的宿主）正上方**，收敛后多个皮肤在宿主上方叠成一摞。无状态机、无 helper 窗口，自愈一切乱序（Win+D 双周期、点击抬升、全屏应用、explorer 重启后宿主重建）。皮肤处于前台（用户正在交互）时跳过，失焦后 250ms 内沉回桌面层。宿主自身在 z 序顶端时修复回退 `HWND_TOP`；enforce 对 hwnd 校验进程归属，hwnd 被系统复用成别家窗口时只清理条目、绝不动手。
3. 图标宿主的查找**不做版本启发式**：Progman 直接含 `DefView`（Win11 24H2+、以及 explorer 刚重启后的 Win10/11）与顶层 WorkerW 含 `DefView`（经典形态）都收集，取 z 序最高者——那才是真正在渲染的桌面表面。
4. z 序必须显式放在**图标窗口正上方**——低于它，桌面 ListView（`SysListView32`）会吞掉所有点击，皮肤永远无法点击/拖拽。
5. 贴桌面时置 `WS_EX_TOOLWINDOW`、清 `WS_EX_APPWINDOW`（任务栏 / Alt+Tab 不可见，双保险于 minimize-all）；取消贴桌面时**两个 bit 都清掉**——tao 对 `skip_taskbar` 窗口本就不设 `WS_EX_APPWINDOW`，"恢复"它等于凭空新增，会让皮肤出现在任务栏/Alt+Tab。

## 位置锁定

- 拖动拦截开关 = webview 内 `__DESK_PP__.positionLocked`（bridge 注入，`skin/protocol.rs`）。
- 窗口创建时的锁定态必须经 `skin://` URL query（`locked=1`）由协议层烘焙进 bridge——**不要**用创建后 eval 恢复（与页面加载赛跑，曾导致置顶↔贴桌面切换 reload 后锁定失效）。
- 运行时切换锁定走 `set_skin_position_locked` 的 eval（页面已加载，无竞态）；锁定 CSS 统一用 `#desk-lock-style` id，解锁时移除。

## 皮肤拖动与右键菜单

- 不再依赖 `-webkit-app-region: drag`（Windows 会把可拖动区域当标题栏，右键弹系统菜单）。皮肤 HTML 中的 `.drag-region` 由注入脚本绑定 `pointerdown`，按下左键时调用后端 `start_skin_drag` 命令拖动（边框缩放复用同一合成消息机制，见「边框拖拽缩放」）。**按下点在交互元素（`button/input/select/textarea/a/label/[contenteditable]`）上时必须跳过拖动**——`start_dragging` 在 pointerdown 即进入系统模态移动循环并捕获鼠标，配套的 pointerup 被吃掉、DOM `click` 永不触发（1.0 时 controls-demo 窗口内无任何按钮，该 bug 潜伏至出现带窗口内按钮的皮肤才暴露）。
- 右键 = 自绘原生菜单（打开皮肤配置 / 刷新皮肤 / 卸载皮肤）：桥接层 `contextmenu` → `show_skin_context_menu` 命令 → 主线程 `TrackPopupMenu`（`TPM_RETURNCMD`，模态，调用前 `SetForegroundWindow` 保证点击外部能关闭）→ 动作分发。「打开皮肤配置」点亮管理器并 `emit("open-skin-config")`；刷新/卸载复用 `reload_skin` / `unload_skin`，且必须 **fire-and-forget**（spawn 后立即返回）——动作会销毁发起调用的 webview 自身，await 会让 wry 把 invoke 响应投递到死窗口（debug 下输出无害的 PostMessage 警告）。**皮肤可按元素粒度退出宿主菜单**：桥在 **window 冒泡末端**监听 `contextmenu`（冒泡链最后一站，任何位置注册的页面监听器都已执行），`e.defaultPrevented` 为真即返回——皮肤 `preventDefault()` 就视为它自己消费了这次右键（如卡片右键编辑）。模态等待必须走 spawn_blocking + `SKIN_MENU_OPEN` 重入守卫：等待期原在 async worker 上 `rx.recv()` 裸阻塞，皮肤循环调用可停满 worker 池、嵌套模态在主线程栈上递归——菜单开着时后续调用直接丢弃。
- **`close()` 返回 ≠ label 已释放**。`destroy_skin_window` 里 `window.close()` 后 webview 在事件循环里还要几 ms 才真正销毁，`load_skin` 紧接着用同一 label 建窗会报 "already exists"（右键刷新曾稳定复现「卸载后回不来」）。所以 close 后必须轮询 `get_webview_window(label)` 直到为 None 才返回。**轮询只在「同 label 重建」路径需要**——托盘退出的 `graceful_exit` 用无等待的 `close_skin_window_nowait`（拆出的共享前半段），否则每个已加载皮肤都串行等一次 webview 销毁，是退出卡顿的来源，勿在退出路径改回 `destroy_skin_window`。
- WebView2 默认菜单经 `SetAreDefaultContextMenusEnabled(false)` 关闭。窗口创建时 WebView2 尚未就绪，首次调用会失败——由创建时的重试线程（`spawn_webview_hardening_retry`，~6s）+ 5s 维护定时器持续兜底，**不要**改回创建后单次调用。子类对 `WM_NCHITTEST => HTCLIENT`、`WM_NCRBUTTONUP` / `WM_CONTEXTMENU` 的拦截保留，防系统菜单漏出。
- **浏览器加速键统一禁用（管理器 + 所有皮肤窗口）**：`factory::disable_browser_accelerator_keys` 经 `ICoreWebView2Settings3::SetAreBrowserAcceleratorKeysEnabled(false)`（`settings.cast` 取得 Settings3）关闭 WebView2 浏览器加速键——F5 / Ctrl+R / Ctrl+F5 刷新、Ctrl+P 打印、Alt+Home、F12 devtools 等全部失效；Ctrl+C/V/X/Z/A 等编辑键是 DOM 层快捷键，不受影响。目的：页面不可经按键刷新/导航，窗口生命周期完全归管理器。唯一例外：开发模式（设置页「高级」开关）开启时皮肤窗内 F12 / Ctrl+Shift+I 可开 DevTools——不走加速键开关（`SetAreBrowserAcceleratorKeysEnabled(true)` 会连带放回刷新/打印键，并与维护定时器的自愈重设互踩），由注入桥 keydown（capture 阶段）捕获后经 `open_skin_devtools` 命令调 `ICoreWebView2::OpenDevToolsWindow`。重试结构与右键菜单同一条：创建时的 `spawn_webview_hardening_retry`（取代原 `spawn_context_menu_disable_retry`，两项加固一起在 WebView2 异步初始化期间重试约 6 秒）；此后皮肤窗与管理器窗均由 lib.rs 的 5 秒维护定时器持续自愈重设（与右键菜单同一趟）。

## 边框拖拽缩放（resizable）

- **开关取值 = 三态**：运行时配置 `SkinRuntimeConfig.resizable: Option<bool>`，None = 跟随 `skin.json window.resizable`（老配置字段缺失即 None，自动跟随作者默认），Some(v) = 用户在「窗口」页的显式选择。建窗烘焙与面板展示都用有效值 `config.resizable.unwrap_or(manifest.window.resizable)`。
- **热区必须在 JS 桥接层实现，不能靠子类 `WM_NCHITTEST`**——WebView2 子窗口铺满整个皮肤窗口，父窗口（装子类的 tao 窗口）永远收不到命中测试（曾按此实现，无边框光标也拖不动，已回退）。
- 现行链路（与 `start_skin_drag` 同一机制）：有效值 → 建窗时 URL 烘焙 `resizable=1`（与 `locked=1` 同路径，**不要**改回创建后 eval）→ 协议层烘焙 `__DESK_PP__.resizable` → 桥接脚本 `pointermove` 命中 6px 边缘热区时用 `#desk-resize-style`（`*{cursor:…!important}`）显示缩放光标、`pointerdown`（捕获阶段 `stopPropagation`，避免触发拖动）调 `start_skin_resize` → 后端 `ReleaseCapture` + `PostMessage(WM_NCLBUTTONDOWN, HT*)`，DefWindowProc 进入系统模态缩放循环。
- **运行时开关 = `set_skin_resizable` eval 调桥接的 `__DESK_PP__.setResizable(on)`**（页面已加载，无竞态）：翻转标志 + 同步边框提示层（`#desk-resize-frame`：四边 4px 黄黑警示斜纹，`transform` 位移动画（GPU 合成；background-position 动画逐帧重绘会抽搐，勿改回），`pointer-events:none`，透明皮肤也能看清边界）。桥接的 pointermove/pointerdown 监听**常驻注册、逐事件检查标志**，不要改回按标志条件注册——否则开启时要重载才生效。
- 尺寸持久化走 tao `WindowEvent::Resized`（与 `Moved` 同路径）：物理像素 ÷ **建窗锁定的快照尺**（`SCALE_SNAPSHOTS`：建窗时物理客户区 ÷ 逻辑宽——曾直接用「当前物理 ÷ 已存逻辑」的布局尺，resize 期间分子随事件同步变、分母是旧值，换算恒等旧值导致边框拖拽尺寸永不落盘；快照与尺寸无关天然稳定，销毁时摘除）→ 内存配置立即更新 + 500ms 防抖写盘（与位置共用 `debounced_config_flush`）+ `emit("skin-resized")` 刷新面板输入框。面板 `set_skin_size` 的回环事件值相同，跳过不写。
- **缩放比例（zoom）**：用户可在「窗口」页把皮肤整体缩放到 50%–200%（`MIN/MAX_ZOOM`，`clamp_zoom`）。取值三态：`SkinRuntimeConfig.zoom: Option<f64>`，None 跟随 `skin.json window.zoom`（**用 Option 而非 opacity 式裸 f64**——`or_default()` 建的条目不会把 manifest 默认冲成 1.0；`WindowDefaults.zoom` 的 serde default 必须回 1.0，落 0.0 = 窗口被乘没）。**配置里的 width/height 恒为 100% 基础尺寸，面板的宽高输入框恒为缩放后的实际尺寸**：实际窗口 = 基础尺寸 × zoom（建窗 `inner_size(w*z,h*z)`、`set_skin_zoom`/`set_skin_size` 的 `set_size`），同时 `WebviewWindow::set_zoom(z)`（WebView2 ZoomFactor）同倍缩放内容——**两边同乘 ⇒ 页面 CSS 视口恒为设计尺寸，布局不重排，任何皮肤零适配即可整体缩放**（这就是「所有皮肤编写时就要能实现等比例缩放」的平台落点）。两条尺寸语义的换算点：持久化一律 = 实际 ÷ 有效 zoom（Resized 事件、面板 `set_skin_size` 输入实际尺寸同样换算；有效 zoom 从配置现读，条目缺失回退 manifest——闭包捕获 `manifest_zoom`）；面板显示一律 = 实际（`get_skin_detail` 把 config 宽高 × zoom 后返回、`skin-resized` 发实际值、`set_skin_zoom` 因基础尺寸不变会被 Resized 的「未变化跳过」吞掉回环，必须自己显式 `emit("skin-resized")`）；`set_skin_zoom` 的 entry 缺失时按 manifest 尺寸播种（`or_default` 的 300×200 会把 set_size 缩错）；`set_zoom` 失败仅 log 降级（尺寸仍正确），建窗时在 show 前调用所以无 100% 闪现。
- 子类 `WM_GETMINMAXINFO` 设最小 60×40（DPI 缩放）必须保留——模态缩放循环无论由谁触发都会读它，防窗口被拖成无法抓取的尺寸。

## 边缘吸附

- **挂点 = 窗口子类的 `WM_MOVING`**（`window/factory.rs`），不要用 `Moved` 事件 + `set_position` 实现——那会回环触发且拖动轨迹不平滑。系统模态拖动循环每一步都把待定的屏幕坐标 RECT 传进来，`window/snap.rs` 的 `on_window_moving` 就地改写即完成吸附；面板输入的精确坐标（`set_skin_position`）不走这条路径，不受吸附影响。
- **吸附状态按 HWND 注册**（`snap.rs` 的 `SNAP_WINDOWS`，子类回调里只有 HWND 可用）：建窗 `upsert`、销毁 `unregister`（HWND 会被系统回收复用，残留条目会把无关窗口误当吸附候选，必须随销毁清理）、面板开关/改间距 `upsert` 更新。候选边缘 = 注册表内其他皮肤窗口（拖动时实时 `GetWindowRect`，不缓存，跳过已销毁/不可见/最小化）+ 窗口所在显示器的**工作区**（`MonitorFromRect` + `GetMonitorInfoW`，不含任务栏，多屏正确）。
- **吸附 = 纯距离判定**：X/Y 各轴先算屏幕候选，|delta| ≤ 阈值（`SNAP_THRESHOLD` = 10 逻辑 px，按窗口 DPI 换算成物理 px）就用屏幕；都不在阈值内才取 |delta| 最小的窗口候选（左/右/上/下缘对齐 + 相邻贴合）。窗口候选要求两窗口在垂直于该轴的方向上重叠或间距 ≤ 阈值，否则远处窗口会造成「幻影吸附」。贴边后同一拖动内要拖出阈值区才脱开——手感简单可预期，精细调整走下面的逃逸窗口。曾试过方向感知逃逸（反向 3px 脱开 + 逃逸抑制）与 Shift 临时绕过，实测手感不稳定/多余，均已回退删除，不要再加回来。
- **逃逸 = 「松手再拖」的 1 秒自由窗口**：上次拖动以吸附结束（`DragRuntime.ended_snapped` 记录吸附坐标，逐 WM_MOVING 更新）且窗口仍停在原坐标（±1px）时，`begin_drag`（`WM_ENTERSIZEMOVE`）为本次拖动开启 1 秒逃逸窗口（`escape_until`，`Instant` 判定）——期间不吸附，仅把窗口夹取在屏幕工作区 − gap 内（`clamp_to_work`，「不能超出屏幕 + 自定义间距」，窗口比工作区宽时钉 min 边防 panic）；时间到即恢复吸附（同一拖动内生效）。`DRAG_STATES` 跨拖动保留、只随 `unregister` 清除；**不要**在 `WM_EXITSIZEMOVE` 清理状态，也不要在逃逸窗口内更新 `ended_snapped`（记忆失效会让「松手再拖」失灵）。位置被面板/程序改动后 `should_arm_escape` 的坐标校验自然失效，不会误开窗口。
- 间距 `snap_gap`（逻辑像素，clamp 0–200 = `MAX_SNAP_GAP`）对屏幕边缘与窗口相邻贴合都生效（对齐类候选不含间距）。持久化在 `SkinRuntimeConfig.edge_snap` / `snap_gap`（均 `#[serde(default)]`，默认关 / 0）；命令 `set_skin_edge_snap` / `set_skin_snap_gap` 未加载时仅持久化、已加载时同步注册表即时生效（同 `set_always_on_top` 语义）。

## 鼠标穿透（已恢复——当年根因是自家子类摘位，不是样式位无效）

- **可行机制（现行实现）**：tao 的 `set_ignore_cursor_events(true)` 给顶层窗口置 `WS_EX_TRANSPARENT|WS_EX_LAYERED`（tao `window_state.rs`：`IGNORE_CURSOR_EVENT` ⇒ 两位置位），OS 命中测试随即**整体跳过该窗口**——铺满客户区的 WebView2 子孙窗口根本不会被命中，点击/滚动直达下层窗口或桌面。最小 demo（同 tao 0.35.3、同形态无边框+透明 WebView2 窗口）实证可用；旧担忧「LAYERED 破 WebView2/DirectComposition 渲染」在当前 WebView2 运行时不成立。
- **当年两轮失败的真正根因**：不是组合无效，而是自家无边框子类与功能对打——`force_frameless`、`WM_STYLECHANGING`、`WM_STYLECHANGED` 三处无条件剥掉 TRANSPARENT|LAYERED，5 秒自愈定时器再兜底重剥，tao 设上的位活不过一个清理周期；第一轮又走了「非分层 TRANSPARENT」路线（命中测试确实无视该位，结论仍成立），第二轮的子孙 HTTRANSPARENT 子类跨进程断链（结论仍成立）。
- **现行实现的命门**：
  - 穿透窗口**按 HWND 登记**（`window/factory.rs` 的 `PASSTHROUGH_HWNDS`，子类回调里只有 HWND 可用）；上述三处摘位逻辑对登记窗口改用 `FRAMELESS_EXSTYLE_PASSTHROUGH` 掩码保留 TRANSPARENT|LAYERED，其余窗口行为与旧版完全一致。
  - **顺序命门：先 `set_passthrough_hwnd` 登记，再调 `set_ignore_cursor_events`**——tao 经 `execute_in_thread` 在主线程落 `SetWindowLongPtr`，其触发的 `WM_STYLECHANGING` 由子类按彼时的登记状态决定放行还是摘回；顺序反了位立失。
  - 销毁路径（`close_skin_window_nowait`）必须摘除登记——HWND 会被系统回收复用，残留条目会让无关窗口被放行穿透位（与边缘吸附登记同一纪律）。
  - 配置 `SkinRuntimeConfig.click_through`（`#[serde(default)]`，默认关）；命令 `set_skin_click_through`（挂 `require_manager`）皮肤已加载时原位翻转、未加载仅持久化下次建窗生效；`create_skin_window` 建窗时按配置应用。逃逸路径 = 管理器面板（托盘可唤出）——穿透皮肤不再响应鼠标，故无需全局热键（单窗口 demo 才需要）。
- **仍成立的历史探测结论**（探针 `tools/win32-probes/ctprobe.ps1`，这些路线勿再试）：顶层非分层 TRANSPARENT 被命中测试无视；贴桌面（WorkerW 子窗）兄弟间透明命中跳过仅对同线程窗口有效；子类返回 HTTRANSPARENT 的冒泡跨进程断链（WebView2 子孙属 msedgewebview2 进程）；跨进程 `SetWindowLongPtr` 给子孙补 TRANSPARENT 只「吞」不「穿」；`WindowFromPoint` 只跳过隐藏/禁用窗口，不能当穿透判官。重路线（`WH_MOUSE_LL` 拦截转发 / DWM 缩略图影子窗）依旧不值得。
- **风险敞口**：「LAYERED 破渲染」无法对所有环境（旧 WebView2 runtime、特殊显卡路径）一次证伪——开关逐皮肤、默认关即是熔断；某环境出现视觉回归时关闭即回退。「鼠标免疫」的需求曾由壁纸层承接、壁纸层移除后由本功能承接（桌面图标可直接点按，贴桌面 + 穿透 = 纯展示挂件）。

## 虚拟显示器 DPI 与 rasterization scale

- **黑底病根：虚拟显示器 DPI 不一致致 WebView2 视觉树错位**（GameViewer 虚拟屏 + Win10 21H2 @125% 实测定论）：远程控制软件的虚拟显示器（GameViewer/向日葵等 IddCx 虚拟屏）DPI 上报互相矛盾——`GetDpiForMonitor` 报 96、系统 DPI 实为 120；皮肤窗口建窗后被系统改派到系统 DPI（`GetDpiForWindow` 96→120，**不发 WM_DPICHANGED、不重布局**），WebView2 按新窗口 DPI 把 rasterization scale 重设为 1.25，而 tao 按建窗 DPI 布局（窗口物理尺寸=逻辑值）——内容按「窗口矩形×1.25」错位合成：圆角/透明区没有内容覆盖透黑底，错位部分超出窗口在桌面上留黑色残块；普通/不透明/置顶/贴桌面窗口同样发生。**对策 = `force_webview_rasterization_scale`：把 controller 的 rasterization scale 强制为窗口的「布局尺」**（`layout_scale_factor` = 物理客户区 ÷ 设计逻辑宽——tao 的 `scale_factor()` 在该路径上虚报（窗口物理=逻辑、缓存却 1.25），不能作准；正确不变量经 wry 源码实证：controller Bounds=物理客户区、CSS 视口=Bounds÷scale，故 scale 必须等于 物理÷设计逻辑，并取整到 0.01 消物理取整噪声），建窗时设一次、亮相后 0.6s/1.5s/3s 多次幂等补设（`schedule_rasterization_force`，覆盖运行时的迟到重设）；正常显示器上两尺本就相等，幂等无副作用。已试无效路线（勿再试）：`SetBoundsMode(RAW_PIXELS)`、仅创建期 `SetRasterizationScale`、`--force-device-scale-factor`、`--disable-gpu-compositing`（视觉树脱到屏幕原点更糟）、`NotifyParentWindowPositionChanged`（让 controller 按父链重算呈现布局，窗口右/下缘反露 6×4px 无内容黑条）、按 tao `scale_factor()` 强制（虚报路径上把内容放大 1.25 倍）。探针：`wp-monitor-topology.ps1`（监视器/DPI 拓扑）、`wp-black-diag.ps1`（皮肤父链与各窗样式位现场）。

## 预览截图

- **`capture_skin_preview` 必须保持 `async fn`**：Tauri 2 的非 async 命令在**主线程**执行，而截图实现要 `recv_timeout` 阻塞等待 WebView2 `CapturePreview` 的完成回调——回调恰恰靠主线程消息泵派发。同步命令把主线程堵死后回调进不来，管理器界面整体冻结直到超时；async 命令在运行时工作线程上等待，主线程继续泵消息，互不阻塞。

## 数据流

```
用户拖动皮肤 → WebviewWindow Moved event
→ 后端 factory::save_dragged_position：内存配置立即更新（reload 即时生效）+ 500ms 防抖写盘
→ emit("skin-moved") → skin-editor.js listen() → 仅更新输入框显示
```

- 拖动位置的保存必须留在**后端** Moved 事件里，不要移回前端——前端监听只在配置页打开时才注册，曾导致「面板没开时拖动不保存，reload 后皮肤回到原位置」。
- **完全出屏皮肤的救回**（拔外接屏 / DPI 拓扑变更后皮肤落在所有显示器之外，不可见也拖不回）：`factory::offscreen_target` 判定——窗口矩形与**所有**显示器工作区（`Monitor::work_area`，物理像素，与 outer_position/outer_size 同系）都不相交才算出屏，**部分出屏一律不动**（多屏拼接缝、刻意半掩都是合法摆放）；出屏则 `set_position` 移回主显示器工作区左上 + 24px（走 Moved 事件防抖落盘，新位置即持久化）。两个挂点：lib.rs 的 5 秒维护定时器里 `rescue_offscreen_skins`（拓扑变化最迟 5 秒自愈，启动自载也被首 tick 覆盖，无需 WM_DISPLAYCHANGE 钩子），与配置页「复位到屏幕内」按钮的 `bring_skin_onscreen` 命令（`require_manager`，返回是否移动供前端 toast）。
- 位置与大小的配置值**一律为逻辑像素**（logical pixels）：创建（`inner_size`）、设置（`LogicalPosition` / `LogicalSize`）、事件回读（物理 ÷ `scale_factor`）都遵守同一约定。任何路径把配置值套进 `PhysicalSize` / `PhysicalPosition`，都会在 DPI 缩放 ≠100% 时造成实际尺寸与面板不一致、reload 后"还原"。
- **持久化结构新增字段必须带 `#[serde(default)]`**（`AppConfig` / `SkinRuntimeConfig`；`Option` 字段除外，serde 对缺失自动置 `None`）。漏加的代价：所有老 config.json 整体解析失败、被当损坏文件重置为默认——单文件方案下炸伤半径是全部皮肤数据（仅有 `.bak` 兜底）。
- 磁盘上已不存在的皮肤，其配置残留（`skin_settings` / `loaded_skins` 条目）在**启动时统一清理**（覆盖文件夹被手动删除、作者改 id 两种来源）；应用内删除走 `remove_skin` 即时清理。设置类命令的写盘失败**必须透传到前端**（`配置保存失败: …`），不要改回 `let _ =` 吞掉——用户会看到「保存成功」但重启后丢失。例外：拖动防抖保存只记 `log::warn`（面板可能没开，无人接收错误）。
- config.json（version 2）只存窗口页数据与全局设置；「皮肤设置」页的用户值在**皮肤文件夹的 `settings.json`**（见下节）。v1 配置的 `skin_settings[id].custom` 由启动时的 `migrate_v1_custom_settings`（scan 之后、load_config 之前）迁入各皮肤文件夹：settings.json 已存在则以现有文件为准不覆盖；写入失败的条目保留 custom、**版本号不升**，下次启动重试；孤儿条目（皮肤已不存在）的 custom 随版本升级丢弃（与 prune 语义一致）。`SkinRuntimeConfig` 已删 `custom` 字段，残留旧键 serde 读入时自动忽略。
- **`save_app_config` 统一走归一化**：version 强制写当前版本、`language` 与内存态同步、置顶/贴桌面二选一经 `normalize_mode_flags`（已提为 `pub(crate)`，与配置加载复用同一实现）——所有写盘路径与启动加载产出同一份规范化结果，杜绝「加载时归一、保存时原样写回」的来回抖动。新增写盘入口一律走 `save_app_config`，不要自写 `serde_json::to_string` 落盘。

## 皮肤自定义设置

- 初始值 = `skin://` 协议层 serve HTML 时烘焙进 `__DESK_PP__.settings`（schema 默认值 + 皮肤文件夹 `settings.json` 覆盖值的合并，见 `skin/protocol.rs` 的 `baked_settings_json` 与 `skin/loader.rs` 的 `effective_settings`）——与位置锁定同理，**不要**改成创建后 eval 恢复（与页面加载赛跑）。
- **`password` 类型值不烘焙进页面**：`baked_settings_json` 把 password 项恒替换为空串（`__DESK_PP__.settings` 里该 key 恒为空）——skin:// 对所有皮肤同源，烘进 HTML 的值可被任意皮肤 fetch 走。皮肤改用 `skin_get_setting` 命令按需读取（`skin_api/mod.rs`；身份取自窗口 label，只能读自己 schema 声明过的 key，免 permissions 声明）。配套地，`skin_set_setting` 写盘后的 `skin-setting-changed` 事件改 `emit_to("main")` 定向发管理器——广播会把设置值（可能含 password）经事件路过所有皮肤窗口。
- **用户覆盖值持久化在皮肤文件夹的 `settings.json`**（与 skin.json 同级；`skin/settings.rs` 读写：缺失→空、容忍 BOM、损坏→改名 .bak、原子写）。`skin.json` 应用永不重写：schema 与默认值只在其中，「重置」= 删 `settings.json`（`reset_skin_config` 同时删 `skin_settings[id]`，一并回落默认值）。
- **skin:// 拦截任何 `settings.json`**（含 `.bak` / `.tmp`）→ 404——该文件随值文件方案新引入暴露面，不拦截则 A 皮肤可 fetch B 皮肤的设置值。
- 设置 JSON 序列化进 `<script>` 前必须把 `</` 转义为 `<\/`，否则设置值中的 `</script>` 会提前闭合标签。
- 运行时变更 = `set_skin_custom_setting` 命令写盘后 eval 推送：更新 `__DESK_PP__.settings[key]` 并派发 `desk-setting-changed` 文档事件。皮肤不监听事件也能在下次 reload 时拿到新值。
- **皮肤也能写自己的设置**：`skin_set_setting` 命令（`skin_api/mod.rs`，皮肤专用——不复用管理器命令；身份取自窗口 label，只能写自己 schema 声明过的 key，值走同一个 `validate_custom_setting`，免 permissions 声明）。因此 `settings.json` 有**两个写入方**，load→save 全程必须持 `AppState::settings_lock`（std Mutex，两命令均为同步 fn）防互相丢更新，勿拆回无锁。
- **皮肤→管理器方向的同步**：`skin_set_setting` 写盘后 `emit_to("main", "skin-setting-changed")`（定向发管理器，不广播——见上条），skin-editor.js 监听并原地刷新对应控件（`_syncCustomControl`：列表型重渲行——绑定在容器上事件委托不丢；赋值型只更新 value/checked——节点不能替换；palette/chips 等复合型首版不动 DOM；焦点在控件内一律跳过，编辑中内容优先）。皮肤**自写不回派** `desk-setting-changed`（防「写→事件→再写」成环），仅静默同步 `__DESK_PP__.settings[key]`。
- 持久化的覆盖值只在类型与 schema 声明一致时才被采用，皮肤作者改设置项类型后旧值自动回落到默认值。
- 控件按 `type` 分支渲染，集中在 `skin-editor.js` 的 `renderCustomSettings` / `bindCustomSettings`；**新增控件类型需同步四处**：`types.rs` 的 `SkinSettingKind`、`loader.rs` 的类型匹配与兜底、`commands.rs` 的校验、前端渲染/绑定（`pack-skin` 的手工镜像同理，见 AGENTS.md）。自定义控件独占「皮肤设置」页签，与内置「窗口」页分开。`file` / `directory` 选择器控件另有一条链路：**系统对话框只能由管理器弹**（皮肤窗口拿不到也不该弹系统对话框）——控件按钮调 `pick_path` 命令（require_manager、spawn_blocking 阻塞对话框、扩展名白名单化为小写字母数字），选中回写走 set_skin_custom_setting 同一管道（皮肤照常收 desk-setting-changed）。

## 皮肤后端接口（skin_api）

> 皮肤经 `__DESK_PP__.invoke` 可调的系统信息与敏感能力命令（`skin_api/` 模块）。对外契约见 `docs/皮肤开发指南.md` §2.3 / §5。

- **桥接是直通，无命令白名单**：`__DESK_PP__.invoke` 直接转发 `__TAURI_INTERNALS__.invoke`，任何注册进 `invoke_handler` 的命令皮肤都能调。因此**敏感命令必须自带权限校验**（`require_perm`：窗口 label → skin id → 重扫 manifest 查 `permissions`），不能只靠「文档约定别调」；新增敏感命令一律走这个入口。
- **管理器命令统一 `require_manager` 把关**：桥接直通意味着 `commands.rs` 的管理器命令默认也对皮肤可达，而皮肤本就不该够到它们（与是否声明权限无关，`require_perm` 管不了这层）。全部约 40 个管理器命令（加载/卸载/设置/安装等）入口校验调用窗口 label == "main"，皮肤窗口调用一律报「该命令仅允许管理器窗口调用」。皮肤的合法例外仅三个无害命令：`start_skin_drag` / `start_skin_resize` / `show_skin_context_menu`（身份由窗口 label 反查，只能操作自己）。**新增管理器命令默认挂 `require_manager`**。
- **capabilities 按窗口拆分收紧**：`default.json` 只挂 `"main"`（core:default + minimize/toggle-maximize/hide——只留管理器前端实际用到的）；新建 `skin.json` 挂 `"skin-*"` 且 **permissions 为空**——皮肤不用 @tauri-apps/api，app 自定义命令不受 capabilities ACL 约束，真正的门在 Rust 侧（caller_skin / require_perm / require_manager）；shell / dialog / autostart / window-create / event-emit 等核心与插件权限一律不授予皮肤窗口。
- **速率类读数 = 采样基线模式**：静态 `Mutex<Option<…>>` 持有采样器（CPU 的 `CPU_SYS`、PDH 的 `PdhMultiCounter`），首次调用只做基线、返回 0——开发指南已告知皮肤每秒轮询。
- **sysinfo 0.32 没有磁盘 IO 统计**（0.30 起移除），磁盘读/写速度走 PDH `\LogicalDisk(*)\Disk Read/Write Bytes/sec`（实例名即盘符，与 sysinfo 挂载点按盘符 join；**不要用 `\PhysicalDisk`**——它按物理盘聚合，同盘多个分区会显示相同的速率）；GPU 使用率走 PDH `\GPU Engine(*)\Utilization Percentage`（实例名含 `luid_0x…_0x…`，按 LUID 聚合到 DXGI 适配器）。PDH 计数器路径必须用 `PdhAddEnglishCounterW` 加英文路径，与系统显示语言无关。
- **GPU 两来源拼装**：名称/LUID/显存总量 = DXGI 适配器枚举（跳过 SOFTWARE 适配器），显存占用 = PDH `\GPU Adapter Memory(*)\Dedicated|Shared Usage`（AMD 驱动下 DXGI `QueryVideoMemoryInfo` 恒返 0，DXGI 值仅作 PDH 未就绪时的回退）。核显等统一内存适配器总量与占用均按共享系统内存计——核显专用段只是 BIOS 划分的一小块，「专用 + 共享」合计可能超出物理内存，口径不合理（核显占用本来也几乎全部落在共享计数器）。**核显判定用 D3D12 UMA 架构查询**（`D3D12_FEATURE_DATA_ARCHITECTURE.UMA`，结果按 LUID 缓存）——不要用专用显存大小猜，APU 可在 BIOS 划出 1GB+ 专用段；该判定同时产出返回字段 `gpu_type`（`"discrete"` / `"integrated"`）。核心频率没有 Windows 通用接口（仅厂商 SDK，已按需求移除 NVML 路线与 `frequency_mhz` 字段）。
- **音频环回**：wasapi 对「render 设备 + Capture 方向 + Shared」自动置 `AUDCLNT_STREAMFLAGS_LOOPBACK`，无需手动 flag；`convert=true` 保证拿到 f32/48k/立体声。捕获线程懒启动（首次 `get_audio_spectrum` 时 spawn）、**闲置 30 秒释放设备**（皮肤随时可能卸载，不能常占端点）、失败写 shared.error 由命令侧透出。频谱 = 2048 点 Hann + FFT，30Hz–16kHz 对数分带，-60dB 地板归一化。
- **文件沙箱（`files` 权限已取消，沙箱仍在）**：皮肤目录内文件读写不再需要声明权限——沙箱把一切操作限制在皮肤自身安装目录内，它本身就是免声明的依据：先拒绝绝对路径与 `..` 分量，再 canonicalize 做前缀校验（防符号链接逃逸）；写入前 `create_dir_all` 父目录所以写路径也能 canonicalize。`skin.json` / `settings.json`（含 `.bak`/`.tmp`）只读禁写禁删。读 32MB / 写 16MB 上限。**路径分量含 `:` 一律拒绝**（防 NTFS ADS：`skin.json::$DATA` 是同一文件的备用数据流，可绕过按文件名的只读拦截，与 protocol.rs 的拦截同一规约）。
- **`run_command` 必须是 async + spawn_blocking**：Tauri 2 非 async 命令在主线程执行（见「预览截图」节同一约束），子进程 120 秒超时若跑在主线程会冻结整个管理器。子进程输出用双线程分别读 stdout/stderr（顺序读会被写满的管道堵死），各截断 1MB；中文 Windows 控制台输出是 GBK，无效 UTF-8 时回退 `MultiByteToWideChar(CP_OEMCP)` 转码。`CREATE_NO_WINDOW` 隐藏控制台窗口。
- **音量/媒体的 COM 约定**：`volume.rs` 每次调用 `CoInitializeEx(MTA)` 且**仅返回 S_OK 时才 CoUninitialize**——RPC_E_CHANGED_MODE（线程已被别处初始化）语义是「继续用，别 uninit」；SMTC（`media.rs`）的 WinRT async 一律 blocking `.get()`，两个媒体命令必须 `async + spawn_blocking`（与 `run_command` 同一条主线程禁令，见「预览截图」节）。SMTC 降级契约：无会话返回 `None` 不是错误；封面/进度字段失败只留空，不让整个调用失败。
- **剪贴板走 tauri-plugin-clipboard-manager**（Rust 侧 `app.clipboard()`，命令自带权限门）；`open_external` 用 `ShellExecuteW`（shell 插件的 `open` 已弃用，勿改回），白名单 = `http(s)`/`mailto` 或存在的绝对路径，防 `file:`/`javascript:` 注入；本地路径再加**可执行扩展名黑名单**（exe / bat / cmd / ps1 / vbs / msi / lnk / hta 等——ShellExecuteW 对可执行文件等于皮肤绕过 `shell` 权限声明直接跑程序；另含 search-ms / library-ms / application / appref-ms / diagcab / website 六个可间接指向远程共享的类型，与 UNC 同属 NTLM 外泄面）、**UNC 路径（`\\` / `//` 前缀）一律拒绝**（会触发 SMB 外连与远程可执行文件），URL 与路径两类目标统一报错文案。返回值 ≤32 是 ShellExecute 的失败码。
- **assetProtocol 已整块删除**：tauri 的 assetProtocol scope 按路径前缀放行、拦不住目录内个别文件，曾把各皮肤的 `settings.json` 暴露给所有窗口。预览图改走 `skin://` 协议直出（Windows 下 `http://skin.localhost/<皮肤文件夹>/preview.<ext>`——取预览图绝对路径的**末两段**拼 URL，见 `src/js/api.js`），与皮肤资源同一条拦截链（自带 settings.json 拦截与 canonicalize 防护），不新增暴露面。不要重新开启 assetProtocol。

## 稳定性约定（Mutex / FFI 回调）

- **全域 `std::sync::Mutex` 中毒恢复**：一律 `.lock().unwrap_or_else(|e| e.into_inner())`——持锁路径 panic 后锁进入中毒态，裸 `unwrap()` 会让其余调用方连环 panic 直至整站锁死；`into_inner()` 容忍「状态可能部分更新」继续服务，远好于全灭。新增 Mutex 遵循同一写法，不要写裸 `.lock().unwrap()`。
- **FFI 回调必须 `catch_unwind`**：由 Windows 直接回调进 Rust 的入口（`skin_subclass_proc`、`EnumDisplayMonitors` 等）用 `catch_unwind(AssertUnwindSafe(..))` 包住——panic 穿过 FFI 边界是未定义行为（实际即进程终止），捕获后记 log 并降级返回默认值。新增 WNDPROC / 枚举回调遵循同一模式。

## 皮肤包（.dskin）与皮肤身份

- **皮肤身份 = `skin.json` 的 `id` 字段**（kebab-case）。打包分发时必填；文件夹扫描时缺省按文件夹名 slug 兜底（兼容旧皮肤）。同一 id 视为同一皮肤；扫描按 id 去重，后到者告警跳过。
- **按皮肤定位目录必须先扫描解析**（`find_skin_dir`），不要直接 `skins_dir.join(skin_id)`——id 不一定等于文件夹名。`remove_skin` / `open_skin_folder` / `capture_skin_preview` 已按此改，新增此类命令时同样遵守。
- **用户数据分两处，都在更新/重装/回退时保留**。窗口配置（`skin_settings[id]`）按 id 归属在 config.json，与皮肤文件解耦；「皮肤设置」页的用户值在皮肤文件夹的 `settings.json`，整体替换文件夹时先取出、拷贝后写回（`package.rs` 的 `install_package` 与 `lib.rs` 的 `copy_example_skins` 同一约定，用户值优先于包内同名文件；示例皮肤仅开发期从仓库 `examples/` 同步，安装包不打包）。新 schema 的新增项走默认值，类型不符的旧值由 `effective_settings` 自动回落，被删设置项的残留数据无害忽略。用户侧的清空入口 = 配置面板「重置数据」按钮 → `reset_skin_config` 命令删 `skin_settings[id]` 并删 `settings.json`（窗口配置与自定义设置一并回落 skin.json 默认值），已加载的皮肤随之 reload。
- **`settings.json` 是用户数据，不进分发包**：`tools/pack-skin` 打包时排除 `settings.json` / `settings.json.bak` / `settings.json.tmp`。
- 包解压（`skin/package.rs`）必须经 `enclosed_name` 防 zip-slip；体积上限按**实际解压字节**计量（`io::copy` 返回值累加，不信 zip 头声明的 uncompressed size——头部可伪造，zip 炸弹正是「声明很小、解压很大」），并保留体积/文件数上限（64MB / 256MB / 5000）；临时目录用 RAII 守卫清理。校验规则（可解析、合法 id、入口存在）与打包工具 `tools/pack-skin` **保持一致**（同一套 `SkinManifest` 反序列化，强类型校验）——改一边要同步另一边。
- **安装 = staging 回滚流程**（`install_package`）：① 解压内容完整复制到 `skins/.staging-<id>`；② 已存在的 `<id>` rename 为 `.<id>.old`；③ staging rename 换入（失败把 .old rename 回去）；④ 从 .old 恢复 `settings.json` 后删 .old。任何一步失败都不留「半新半旧」目录，旧版本始终可回退。皮肤扫描**跳过 `.` 开头目录**——staging / .old 与误放的点目录都不会被当皮肤列出。**TOCTOU 收口（审计后）**：向导确认页与安装之间包可能被换掉（「确认 A 的权限、装 B 的内容」）——`install_skin_package` 在安装后校验**实装 id 与安装前解析的 id 一致**，不一致即回滚拆除（同 id 但内容被换的残余面：权限声明与内容仍可能漂移，完整方案是 inspect 算哈希随确认流传递，暂未上）。**同 id 不同文件夹名遮蔽**（审计后）：扫描去重按文件夹名字典序保留先者而包装载落在 `skins/<id>`——已有「id 相同但文件夹名 ≠ id」的皮肤时安装前拦下并引导先移除旧副本。
- **loader 加固**（`skin/loader.rs`）：`skin.json` ≤1MB（手写/打包的清单都是小文件，超限即异常）；`entry` 拒绝 `..` / `\` / `:`（防入口指到皮肤目录外或 ADS）；`id` 黑名单 Windows 保留设备名（con / prn / aux / nul / com1-9 / lpt1-9——系统保留名建不出正常目录，按基名判断，`con.txt` 这类带扩展名的形式同样被系统保留）；目录复制**跳过符号链接与 junction**（防指到 skins 目录外；junction 在 Windows 上不被 is_symlink 标记，按 reparse 属性位判）且限深 32 层；**window 默认值统一归一化**（审计后：宽高钳 1..10000、opacity 非有限/越界回落 [0.1,1.0]、zoom 走 clamp_zoom、refresh_seconds ≤24h——`opacity:0 + 置顶 + 巨尺寸` = 隐形置顶全屏吃点击窗口，安装向导不展示 window 默认值，必须在 load 拦）。
- 更新正在运行的皮肤：先 `unload_skin` 再安装，安装后**保持卸载**（产品决定：更新/重装/回退默认不自动恢复运行，由用户显式加载；不要改回自动 load）。
- 文件选择器只过滤 `.dskin`；`.zip` 不再出现在用户入口，避免与普通压缩包混淆。

## 双击安装（.dskin 文件关联）

- **文件关联 = `tauri.conf.json` 的 `bundle.fileAssociations`**，由 NSIS 安装包写注册表——仅安装版有双击入口；绿色 exe / dev 无双击，但安装逻辑可用命令行参数完整测试：`npm run tauri dev -- -- "D:\path\x.dskin"`。
- **冷/热两条入口路径，不能合并**：
  - 冷启动：`dskin_arg(std::env::args())`（跳过 argv[0]、扩展名大小写不敏感、文件必须存在）→ 存 `AppState.pending_package`，主窗口立即 `show()`，前端启动后用 `take_pending_package_install` **主动拉取**（`Mutex::take` 消费型，只弹一次）。**这里不能 emit 事件**——前端 listener 还没注册，发了就丢。
  - 热启动：`tauri-plugin-single-instance` 回调（必须保持在插件列表**第一位**注册）→ `tray::show_manager_window` + `emit("open-skin-package")`，前端 listener 早已就绪。
  - 已知窗口期：冷启动后前端未就绪的几百毫秒内**第二次**双击，那次转发事件可能丢失（最终显示第一个包的引导页），可接受。
- **安装串行化 = `AppState::install_lock`（tokio Mutex）**，包住整个 `install_skin_package`：反复双击 + 重复点「安装」会并发装同一皮肤，`remove_dir_all` 与复制互踩目录。必须用 `tauri::async_runtime::Mutex`（guard 是 Send，可持有跨过 reload 的 `.await`）——std Mutex 的 guard 是 `!Send`，编译不过；也不要只锁文件操作段，unload/reload 同样需要互斥。覆盖范围：包安装、卸载、备份导入/导出、托盘「重载全部」都取这把锁。**锁序 = lifecycle_lock → install_lock → settings_lock**：`lifecycle_lock`（审计后新增）串行化 load/unload/reload/reset 与 skin_api 生命周期命令（「查存在→注册」非原子，并发交错会让 registry 与 loaded_skins 状态分叉；impl 保持无锁由外层命令/触发点串行——reload_all 持 install_lock 调 impl、reset 持 lifecycle 调 impl、命令持双锁调 impl，均无嵌套 ABBA）；目录替换段（安装/导入）在锁内再持 settings_lock，与 `set_skin_custom_setting`/`skin_set_setting` 的设置写入互斥（防写进刚被替换的旧目录）；settings 命令从不取 install_lock，无反向路径。
- **.dskin 文件图标 = `src-tauri/icons/dskin.ico`**（由 `icon/dskin-icon.png` 缩出 16–256 共 10 帧、经 `tools/make-ico.cjs` 打包）。tauri 不支持 `fileAssociations.icon`，图标由安装器覆盖默认的 exe 图标：NSIS 走 `src-tauri/windows/installer-hooks.nsh` 的 `NSIS_HOOK_POSTINSTALL` 改写 ProgID 的 `DefaultIcon`；ico 本身经 `bundle.resources` 装进安装目录根。**ProgID 与配置强耦合**：键名 = `fileAssociations.name`（现为 "Driftlet Skin Package"）——改 name 必须同步钩子，否则图标静默失效。卸载无需清理注册表（NSIS 删整个 ProgID 键）。**图标即时生效**：tauri 模板全程不调 `SHChangeNotify`，钩子在安装/卸载后各补一次 `UPDATEFILEASSOC`（`SHCNE_ASSOCCHANGED`，模板自带 `FileAssociation.nsh` 提供，勿删）——没有它资源管理器要继续显示旧图标直到手动刷缓存。（曾同时产出 MSI：图标经 `windows/dskin-icon.wxs` 片段、语言按包区分；现已只打 NSIS——`targets: ["nsis"]`，wxs 已删，恢复需从 git 历史找回。）
- **安装包语言自动跟随系统**（NSIS 单包双语言）：`nsis.languages` 顺序为 `["English", "SimpChinese"]`——NSIS 运行时自动匹配系统 UI 语言（探针实测，与是否弹选择框无关），无匹配回退数组**首位**，故 English 必须在前：中文系统→SimpChinese、其余→English，顺序颠倒非中文系统就会看到中文安装器。钩子在 POSTINSTALL 把 `$LANGUAGE` 写入 `HKCU\${MANUPRODUCTKEY}\Installer Language`（同 `MUI_LANGDLL_DISPLAY` 的行为）——不写的话双语言下卸载器 `MUI_UNGETLANGUAGE` 找不到记录会弹语言选择框。**应用首启语言与安装器同步**：`default_language()`（`skin/types.rs`）用 `GetUserDefaultUILanguage` 判中文环境（主语言 ID 0x04）→ `zh-CN`、否则 `en`，与安装器同一判定规则，安装语言即首启语言；只在 config.json 缺 `language` 字段（首启）时生效，已有配置不受影响。
- **卸载数据清理 = 钩子 POSTUNINSTALL 全删，无复选框**：应用数据按 `resolve_portable_dir` 放在 **exe 旁**（可写安装位置；Program Files 等受保护目录回退 `%APPDATA%`），WebView2 数据在 `%LOCALAPPDATA%`——模板自己只删安装的文件、对 `$INSTDIR` 只做非递归 RMDir（config/skins 在里头就失败，整个安装目录残留），这三处都管不到。钩子在非更新卸载时**无条件**补删：`$INSTDIR\config` / `$INSTDIR\skins` 递归删 + 非递归重试根目录（故意不用 /r——用户自放文件保留）+ `%APPDATA%` / `%LOCALAPPDATA%\<bundle id>` + `${MANUPRODUCTKEY}` 注册表（含安装期写入的 `Installer Language`）。**`${If} $UpdateMode <> 1` 守卫绝不能去掉**——更新安装会先跑旧卸载器，少了它每次更新都会清掉用户配置与皮肤。**「删除应用数据」复选框已移除**：原版模板在 `un.ConfirmShow` 里无条件创建它（默认不勾、静默/被动整页跳过、且只覆盖 `%APPDATA%`），没有任何配置开关（tauri-utils 2.9.3 无此字段）、钩子文件也无法编译期抢先定义（模板无 `!ifdef` 守卫，先定义会撞 `!define` 重定义错误）——只能走 `nsis.template` 自带模板 `src-tauri/windows/installer.nsi`（取自 tauri-cli **v2.11.4** tag，删掉了复选框的 Var/SHOW/LEAVE 函数与卸载 Section 里门控块，删除路径收敛为钩子一处）。**升级 @tauri-apps/cli 必须重新同步该模板**（从对应 tag 取新版 installer.nsi，重打本条删改与下面的完结页勾选框、欢迎页文案、重装页选项三处自定义），否则模板漂移会静默丢新修复。
- **安装包完结页「开机自动启动」勾选框**（installer.nsi 第二处自定义）：MUI2 完结页原生只有两个勾选项槽位（RUN =「运行 Driftlet」、SHOWREADME 被借用为「创建桌面快捷方式」），第三个经页面的 SHOW 回调手工创建（`FinishPageShow`，坐标 120u/130u——沿用 MUI2 Finish.nsh 的勾选项间距公式：TEXT_BOTTOM 85 → RUN 90 → README 110 → 本框 130）。LEAVE 回调（`FinishPageLeave`）按勾选态写/删注册表，**口径完全镜像 `auto-launch::enable()/disable()`**：勾选写 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run\driftlet`（值名 = tauri-plugin-autostart 默认 app_name = crate 名；注册表值名大小写不敏感，卸载器按 "Driftlet" 删除仍覆盖）+ `Explorer\StartupApproved\Run` 的 enabled 二进制（`0200…`，`WriteRegBin`，任务管理器「启动」页与应用 `is_enabled()` 都读它），不勾删 Run 值（幂等，同 disable()）。初值默认勾选（opt-out 决策，不再读注册表现状），Back→Next 重进恢复用户选择；更新/被动/静默安装跳过完结页不动注册表，更新卸载保留 Run 值（模板既有 `$UpdateMode` 守卫）。标签双语（`LangString autostart` 中英）直接定义在模板里——Tauri 生成的语言文件由 bundler 产出、不可改，勿投进去。

## 布局备份（导出 / 导入）

- **导入必须先解压到临时目录、全程校验通过后才动真目录**（体积/条目/zip-slip 防线与皮肤包同一套；必须含 `config/config.json`，清单 `driftlet-backup.json` 的 `format` 只认 1），随后**暂存替换**：`config` / `skins` 先 rename 成 `*.import-old`，新内容复制就位失败即删半成品并 rename 回滚——导入失败绝不能留下半替换状态（`backup.rs::replace_data_dirs`，回滚路径有单测覆盖）。
- **替换前必须卸载全部已加载皮肤**（WebView2 锁目录，Windows 下 rename 必失败），并取 `install_lock` 与安装互斥。
- **导入崩溃窗口启动回滚**：「新内容就位」阶段断电/崩溃后可能只剩 `<name>.import-old` 而数据目录缺失——启动时检测：`.import-old` 存在且目标缺失则 rename 回滚，两者都在则视为成功收尾、丢弃 `.import-old`（`backup.rs::rollback_interrupted_import`，setup 在迁移与示例同步之前跑）。
- **导入后的运行时重建清单**（漏一项就是状态漂移）：重读 config + `prune_stale_entries` + 回写内存镜像、语言镜像 + 重建托盘菜单、按 config.autostart 同步 autolaunch 插件、`hotkey::reregister_from_config` 重注册热键（**不能用 `register_from_config`**——它不注销旧注册，配置整体换入后旧组合仍占着，注册必然失败并误报「热键被占用」）、按 loaded_skins 逐个 `load_skin_impl`；前端随后 `location.reload()` 整页再同步（语言/主题/列表/配置缓存一次重建，勿改成局部刷新慢慢补）。
- **导出侧防线（审计后补齐）**：目标不得位于 config/ 或 skins/ 内（否则 zip 把正在写入的自己包进去——自包含、体积失控；导出前按父目录 canonicalize 判定）；**先写临时文件再 rename 就位**（失败不留半截 zip）；junction/reparse point 不跟随（Windows 上不被 is_symlink 标记，按属性位判——成环会无限递归撑爆磁盘，指向外部的 junction 还会把 skins 之外的内容带进备份）；条目数/总字节与导入侧同一套上限（5000 条 / 256MB）；跳过 `.staging-*` / `*.old` / `*.import-old` 暂存残留。

## 开发模式（原皮肤热重载）

- **仅 debug 构建开启**（setup 里 `cfg!(debug_assertions)` 门控）：单 watcher 递归监视整个 skins 目录，按皮肤文件夹防抖 300ms 复用 `reload_skin_impl`；release 无 watcher。**总开关 = `config.hot_reload`（默认关）+ `AppState.hot_reload_enabled`**：设置页切换（`set_hot_reload` 即时翻转标志），watcher 常驻、标志只门控重载动作。该开关在设置页现名「开发模式」，还门控皮肤窗 DevTools 解锁（桥接 keydown 捕获 F12 / Ctrl+Shift+I → `open_skin_devtools` 校验皮肤窗口身份与运行时标志 → `OpenDevToolsWindow`），全构建生效、无 debug 门控。**皮肤 API 自写任意文件名不会触发自重载**——`note_self_write` 登记规范化路径，watcher 命中未过期登记（TTL 5s）即跳过；**命中不删除**：一次 `fs::write` 产生多个 notify 事件，消耗式命中只挡第一个、其余照触发（曾正中 toolbox 存 todo.json 场景）；过期清理由登记侧的 retain 负责。事件通道有界（4096，风暴下满则丢弃——开发便利路径，去抖语义容忍合并）；错误事件置标后根目录恢复存在即自动重建 watch（备份导入把 skins/ rename+删后监视句柄曾静默失效）。
- **自身写入过滤是命门**：`settings.json`（及 `.tmp` / `.bak`）、`preview.png`、`.staging-*` / `*.old` 一律不触发重载，否则死循环——**新增任何应用自身往皮肤目录的写入点，必须同步扩充 `hotreload.rs` 的 `SELF_WRITE_NAMES` / 段过滤**。
- 重载必须 spawn（`tauri::async_runtime::spawn(reload_skin_impl(...))`）：旧窗口 label 要等事件循环处理 close 才释放，同线程同步 destroy+create 会撞 label 重复（同 `tray::reload_all_skins` 的教训）。

## skin:// 协议

皮肤页面与资源经 `skin://` 自定义协议加载（处理器：`skin/protocol.rs`）。它的职责不是限制网络，而是四个控制点：

- **桥接注入**：serve HTML 时烘焙 `__DESK_PP__`（设置值/opacity/锁定/resizable/界面语言/宿主版本 `hostVersion`/右键接管/边缘缩放热区），并挂推荐别名 `window.driftlet`（同一对象，`__DESK_PP__` 为历史名称、永久兼容）——零竞态送达，**不要**改回创建后 eval（见「位置锁定」「皮肤自定义设置」）。`hostVersion` 烘焙 `CARGO_PKG_VERSION`，供皮肤运行期能力探测；skin.json 可选 `min_host_version` 与其互补——`inspect_package` 复用 `update::is_newer` 数字段比较，宿主过旧时向安装向导透传 `requires_host_version` 提示（不拦截安装）。运行时切换语言走 `set_language` 的 eval（更新 `__DESK_PP__.language` 并派发 `desk-language-changed` 事件，页面已加载无竞态，与运行时切锁定同一约定）；运行时切换主题走 `set_theme` 的同款 eval（`__DESK_PP__.theme` + `desk-theme-changed`），烘焙值由 `commands::current_theme` 把 auto 按本地小时折算成具体 light/dark（06–18 浅，与前端 timeBasedTheme 同规则）。**皮肤间事件总线 = `skin_broadcast`（免权限）**：向所有已加载皮肤窗口 eval 派发 `desk-skin-message`（detail = { channel, from, payload }），自己也会收到（自滤按 from）；channel 1–64 字符、payload ≤16KB，只投递 DOM 事件不触宿主状态。
- **用户数据隔离**：`settings.json`（含 `.bak` / `.tmp`）一律 404，A 皮肤拿不到 B 皮肤的设置值。拦截是**双重**的：规范化前按 URL 路径文件名拦一次，canonicalize 之后按真实 `file_name` 再拦一次——Windows 8.3 短名（`SETTIN~1.JSO`）能绕过规范化前的字符串匹配，canonicalize 会把它还原成长名；路径分量含 `:` 一律拒绝（防 ADS `skin.json::$DATA`，备用数据流与本体是同一文件，`skin_api/fs.rs` 同一规约）。
- **路径沙箱**：canonicalize + 前缀校验，皮肤只能读 `skins_dir` 内的文件，同时屏蔽 dev（仓库 `skins/`）与 prod（安装目录）的路径差异。
- **`__fs__` 保留端点（任意路径直出，`file_system` 权限门）**：`http://skin.localhost/__fs__?path=<percent 编码绝对路径>` 让页面用 URL 直引皮肤目录外的文件（图片/视频等展示型引用不经 JS 内存；base64 命令通道留给数据处理）。皮肤 id 只允许小写字母/数字/中划线，**永不与 `__fs__` 撞名**。身份必须取自 `UriSchemeContext::webview_label()`（可信 IPC 通道）——**Referer/Origin 可被页面伪造，绝不可用**（全皮肤同源，A 皮肤能把 Referer 伪成 B 皮肤来借权限）；目标须为存在的普通文件绝对路径（`parse_fs_query` 纯函数已用测试钉住）。
- **窗口态原子送达**：入口 URL query（`opacity` / `locked` / `resizable`）随文档第一帧生效。
- **网页皮肤（entry 为 http(s) URL）**：窗口直接 `WebviewUrl::External` 加载站点页面，不走 skin:// 协议与桥注入——页面上没有拖动区/右键菜单/命令通道（**tauri 的 remote-origin 守卫兜底**：远程源的自定义命令调用一律被拒，见 webview/mod.rs 的 non-local origin 检查），初始 opacity 改走 initialization_script 落（eval 建窗后会竞态丢）；cookie/登录态由 WebView2 用户数据目录持久化（跨重启免登录）；`window.refresh_seconds` 起一条普通线程按间隔 `location.reload()`（**闭包持有建窗时的窗口句柄**——皮肤卸载/重载后旧窗销毁，eval 返回 Err 自然退出；曾按 sid 从注册表重查，会命中重载后的新窗导致旧线程叠加存活）。loader/package/pack-skin 三处的 entry 名校验对 URL 入口一律豁免（无本地文件可查）。

**URL 改写（Windows）**：WebView2 不支持非标准协议的子资源加载，wry 把导航 URL `skin://localhost/...` 改写为 `http://skin.localhost/...`，再在请求侧按 `http://skin.*` 过滤器拦截、改写回来交给协议处理器（wry `custom_protocol_workaround.rs`）——请求不离开进程，无 DNS/TCP。

**网络现实**：皮肤页是完整 Chromium。仅 `http://skin.*` 被拦截，外部 http/https 请求直连真实网络；皮肤页响应**无 CSP**（tauri.conf 的 CSP 只作用于应用协议页，自定义协议的响应由处理器手工构建，只带 Content-Type）。跨域 `fetch`/`XHR` 受 CORS 约束（目标服务器需放行）；`<img>`/`<script>` 标签式加载与 WebSocket 不受 CORS。**第三方皮肤 = 能联网的本机代码**，安装信任模型按此对待。

**边界（已知暴露面）**：所有皮肤共享单一源 `http://skin.localhost`——同源策略不隔离皮肤，A 皮肤可请求 B 皮肤的普通资源文件（仅 `settings.json` 被拦）。若日后要限制皮肤联网，落点仍是本层：协议响应加 CSP 头，或注册 `*://*` 过滤器做白名单。

## 托盘图标

- **逐尺寸 PNG，不合成多尺寸 ico**：`tray.rs` 内嵌 16–48 共 7 个尺寸的托盘图稿（`tools/make-tray-icon.py` 按网格对齐的参数化几何逐尺寸渲染，非大图缩小），Windows 下按 `SM_CXSMICON` 精确选尺寸。Tauri 的 `Image::from_bytes` 只解 ico 单帧，多尺寸 ico 拿不到任何好处，反而让 Windows 把单张位图缩放到 20/24px 发虚。
- **`src-tauri/vendor/tray-icon` 是打了补丁的 vendored 依赖**（`Cargo.toml` 的 `[patch.crates-io]` 指向它），**升级/替换前必须保留这些补丁**：上游（0.24.1/0.24.2）的 `into_windows_icon()` 调 `CreateIcon`，把 **1 字节/像素** 的缓冲传给期望 **1bpp 单色位图** 的 AND 掩码参数（20px 图标应 80 字节，实传 400），生成的 HICON 掩码全是垃圾。`DrawIconEx` 对 32bpp 图标走 alpha 通道、忽略掩码，所以托盘里看着正常；但**掩码敏感的消费者**——任务管理器对无可见窗口进程取托盘图标、Win11 托盘图标拖拽图像——会渲染出横向条纹花屏。补丁改为 `CreateIconIndirect` + 合法 1bpp 掩码（行 16-bit 对齐）+ 32bpp 预乘 DIB（探针 `tools/win32-probes/probe_icon_render.py` 可复现两种渲染路径的差异）。
- 同 crate 第二个补丁（`mod.rs` 的 NOTE(driftlet)）：`TaskbarCreated` 处理路径上的 `NIM_DELETE` 改走安静变体——explorer 重启后旧图标已随死掉的任务栏消失，删除**必然失败**，上游无条件的 `eprintln!` 让每次 explorer 重启都在控制台打一条莫须有的 "Error removing system tray icon"（托盘图标本身经随后的 `NIM_ADD` 正常恢复，纯日志噪音）。
- **窗口图标必须保持禁用**：tao（0.35.x）的 `RgbaIcon::into_windows_icon()` 与上面的 tray-icon bug 是同款代码，而 tauri-codegen 会把 `icons/icon.ico` 烘焙为 `default_window_icon` 并套用到每个窗口（`WindowManager::prepare_window`），窗口可见时任务管理器/Alt+Tab 取的就是这个垃圾掩码 HICON。因此 `lib.rs` 的 `run()` 处显式 `context.set_default_window_icon(None)`，Windows 自动回退到 exe 内嵌的 icon.ico（多尺寸 .ico，无运行时建 HICON）。**不要**给窗口调用 `.icon()`/`set_icon()`，也不要移除这行屏蔽。

## 日志窗口与 app_log

- **后端缓冲常驻、前端按需拉取**：`src-tauri/src/app_log.rs` 的环形缓冲（`VecDeque<LogEntry>`，上限 1000 条，满后淘汰最旧，单条消息截 1000 字符，每条带单调 `seq` 与 epoch 毫秒时间戳）从启动起就记录，但只有 label `"log"` 的窗口存在时 `push` 才 `emit_to("log", "app-log-added")` 增量推送（`get_webview_window("log")` 判存在性）——「不开日志窗口不占前端内存」就落在这一行判断上，不要改成无条件 `emit`。**事件合批（审计后）**：皮肤高频调 `skin_log` 时逐条 emit 会把日志窗口打成 IPC 事件风暴——`push` 把条目先进待发缓冲、约 100ms 一批发出（payload 由单条改为数组，事件名不变，前端两种形状都兼容）。
- **捕获口径 = 自定义 `log` crate logger**：`init_logger()`（顶替原 `env_logger`）只认 target 以 `driftlet_lib` 开头的记录（wry/tao 等第三方 crate 不进门），全级别 `eprintln!` 到 stderr 保留开发期可见性，但**只有 Warn 及以上 `push` 进日志缓冲**——Info 级操作流水（启动/托盘/快捷键/加载/卸载/设置修改）实测对用户无价值（刚操作完就知道的事，没有可行动信息），只到 stderr。挂点照常写 `log::info!/warn!/error!`，进不进窗口由级别决定；过程性调试打点一律 `log::debug!`（低于 `set_max_level(Info)` 闸门，连 stderr 也不到；原「Creating skin window…」三条过程打点即因此降 debug）。
- **操作流水挂点**（Info 级，仅 stderr 不到窗口）：管理器启动（setup 末尾）/隐藏到托盘与无托盘退出（主窗 CloseRequested 分支）/退出（`graceful_exit` 既有打点）、全局快捷键触发（热键 handler 内——**不要**放进 `toggle_all_skins`，托盘菜单 toggle 走同一函数会被误记）、皮肤加载/卸载（`load_skin_impl`/`unload_skin_impl` 汇聚点，重载/配置重置全覆盖；放置切换自原位翻转后不再汇聚于此，由 `set_skin_placement` 单点记一行）、皮肤设置项修改（管理器 `set_skin_custom_setting` 与皮肤 `skin_set_setting` 两侧各一条，**只记 key 不记 value**——password 类设置值连 stderr 也不该出现）。
- **皮肤侧通道 = 桥接自动捕获 console + 显式 `skin_log`**：`inject_bridge` 的 console hook 包装 `console.log/info/debug/warn/error`（先调原始方法再转发），并监听 `error`（capture 阶段——兼抓脚本未捕获异常与 img/script/link 资源加载失败，资源错误事件不冒泡）、`unhandledrejection`、`securitypolicyviolation`。洪泛保护必须在桥接侧（IPC 洪泛才是真实成本）：队列 250ms 一次 flush、整批一次 invoke、相邻重复合并 `(xN)`、每 flush 上限 30 条、队列硬顶 300 条（防死循环刷不同消息撑爆内存）、单条预截 1200 字符，溢出合成一条 warn「flood guard」；hook 内部异常一律静默吞（绝不在 hook 里再调 console——递归）；注入脚本保持纯 ASCII（皮肤页 charset 不受我们控制）。批量命令 `skin_console_log` 的身份取自窗口 label（同 `show_skin_context_menu`），**不走 `caller_skin`**（它每次全量扫盘，持续高频通道不能每批扫一次盘），每批 ≤60 条兜底；显式 `skin_log` 保留（`caller_skin` 验身份）。两者 source 均记 `skin:<id>`，无需权限声明（消息只进本机内存缓冲）。
- **来源过滤为动态按皮肤列表**：全部来源/后端/每个皮肤各一项，选项随条目出现重建；当前选中的皮肤无条目时也保留选项，清空日志不动过滤选择。
- **日志窗口（label `"log"`）**：设置页「高级」页签 `open_log_window` 创建（`require_manager`；已开着则 show+unminimize+focus 防叠开；打开成功后设置页自动关闭），多页构建第二入口 `log.html`（vite `rollupOptions.input`），窗框与管理器窗同配方（无标题栏原生窗框：`decorations(false)` + `apply_native_frame`，详见「管理器/日志窗窗框」条；本命令跑在 spawn_blocking worker 上，子类安装经 `run_on_main_thread`——SetWindowSubclass 跨线程失败），`spawn_webview_hardening_retry` 同样屏蔽右键菜单/加速键。**`open_log_window` 必须是 async 命令 + `spawn_blocking` 建窗**（与 `load_skin_impl` 同一路径）：同步命令在主线程的 WebView2 IPC 回调上下文里执行，就地 `build()` 新窗口会把主线程卡死在 wry 建窗路径上（实测复现：主线程进 `build()` 后不返回、整窗无响应）——任何「前端点击触发的建窗命令」都不得写成同步命令。**主题与语言烘焙进 URL query**（`log.html?theme=…&lang=…`，与皮肤窗烘焙 opacity 同一模式）——日志窗不是管理器窗，`get_app_config` 的 `require_manager` 会拒它；`initI18n(forceLang)` 的可选参数即为此加；运行期切换语言/主题由 `set_language`/`set_theme` 末尾 `emit_to("log", "app-log-language"/"app-log-theme")` 同步（前端重跑 `initI18n`/`applyTheme` 并重绘）——烘焙只管建窗一刻。窗口打开时前端**先 `listen` 再 `invoke get_app_log`**（顺序反过来会丢窗口期内的条目），按 `seq` 去重合并后转纯增量；`get_app_log`/`clear_app_log` 由 `require_log_window` 按 label 把关——缓冲含内部路径与其它皮肤的消息，不能放给皮肤读（注入桥是裸透传，自定义命令无 ACL，与 `require_manager` 同一理由）。

## cargo test 的 comctl32 v6 清单（build.rs）

- **症状**：`cargo test` 的测试 exe 启动即失败 `0xc0000139 STATUS_ENTRYPOINT_NOT_FOUND`（进程根本没进 main）。病根：vendored tauri-runtime-wry 的消息框静态导入 `TaskDialogIndirect`（comctl32 v6 导出），而 tauri_build 的 winres 清单只经 `rustc-link-arg-bins` 嵌进 bins——lib 单元测试二进制没有清单，进程无 v6 激活上下文，`comctl32.dll` 解析到 System32 的 v5（无该导出），加载期绑定失败。`rustc-link-arg-tests` 救不了：它只认 `tests/` 集成测试目标，本 crate 没有，用了直接报错。
- **解法（勿拆散）**：`build.rs` 改为 `try_build(Attributes::new().windows_attributes(WindowsAttributes::new_without_app_manifest()))` 关掉 tauri 的 bins 清单，再用 `embed_resource::compile_for_everything` 把 `windows/app-manifest.rc`（内容与 tauri 默认 windows-app-manifest.xml 相同的 comctl32 v6 依赖）嵌进**全部**链接目标——bins 与 lib 测试二进制各得一份，不重复（直接 compile_for_everything + tauri 默认清单会撞出 CVT1100「资源重复」）。诊断工具：`tools/check_imports.py`（PE 导入表静态核对，依赖 pefile）。

## 行为约束

- “窗口置顶”与“贴在桌面”二选一，必居其一：打开一个自动关闭另一个，关闭当前模式会切换到另一个；默认“贴在桌面”。配置加载时会把历史遗留的“两者同开/同关”状态规范化为“贴在桌面”。
- 主窗口点击 X 按钮 = 隐藏到托盘，不是退出；托盘「退出」才是真正退出。
- **皮肤窗口 Alt+F4 = 隐藏，不是关闭**：Alt+F4 是系统级窗口消息（WM_CLOSE），JS 层和 WebView2 加速键开关都管不到，tao 将其转为 `CloseRequested`；系统强制关闭不可违背，但 WM_CLOSE 只是「请求」，应用层有权解释为隐藏。皮肤窗建窗时的 `on_window_event`（`window/factory.rs`）新增 `CloseRequested` 分支：未经登记的关闭请求 → `api.prevent_close()` + `window.hide()` + `crate::hotkey::sync_tray_toggle_item()` 同步托盘勾选项；唤回复用既有全局快捷键（默认 Ctrl+Shift+Alt+D，stateless「有可见则全隐、全隐则全显」语义）与托盘勾选项。**程序化关闭必须登记 `INTENTIONAL_CLOSES`**：卸载/重载/退出（全部汇聚 `close_skin_window_nowait`）在 `window.close()` 前把 label 登记进 `INTENTIONAL_CLOSES` 静态集合（factory.rs），事件处理消费该登记后放行；`close()` 失败会撤销登记，避免残留条目错误放行同一 label 的下一次用户关闭；`create_skin_window` 建窗时再防御性清理同 label 残留登记（极端场景：`close()` 入队后窗口被外部销毁、`CloseRequested` 未触发）。判别必须存在的原因：vendored tauri-runtime-wry 中 `close()` 与用户 Alt+F4 同走 `on_close_requested`（`WindowMessage::Close` 与 `TaoWindowEvent::CloseRequested` 汇聚），`CloseRequested` 本身不带关闭原因。`hwnd_dead` 分支走 `destroy()` 不触发 `CloseRequested`，无需登记。管理器窗口的 Alt+F4 由既有「关闭=隐藏到托盘」拦截覆盖，行为不变。
- **管理器「已隐藏」状态 = 真实窗口可见性，不是热键簿记**：`SkinInfo`/`SkinDetail` 的 `hidden` 字段由 `list_skins`/`get_skin_detail` 现算（已加载且 `is_visible()` 为假——tao 的 is_visible 即 IsWindowVisible），任何隐藏路径（全局热键 toggle、托盘勾选、Alt+F4 降级隐藏）都落在真实状态上。前端刷新触发点 = `skins-visibility-changed` 事件，发出点在 `hotkey::sync_tray_toggle_item`——它是全部可见性变化的既有漏斗（托盘勾选项同步），三条隐藏路径都经过，**load/reload 收尾也过一遍漏斗**（热键全隐藏后 reload/load 会把新窗无条件 show，托盘勾选与徽标按真实状态即时同步）；不要在前端按热键按下与否自算隐藏态（托盘/Alt+F4 路径会漏）。徽标三档：`hidden`（黄，`--warning*` 令牌）/ `loaded`（绿）/ `unloaded`（灰），列表卡片与配置页眉共用同一派生逻辑。
- 托盘左键 = 显示/隐藏管理器，右键 = 菜单；管理器窗口显示期间在任务栏/Alt+Tab 可见（最小化可正常还原），隐藏后任务栏按钮随之消失；皮肤窗口保持 `skip_taskbar(true)` 不进任务栏。
- 皮肤资源统一通过 `skin://` 自定义协议加载（职责与边界见「skin:// 协议」节）。皮肤 HTML 内引用子资源**只能用相对路径或 `http://skin.localhost/<皮肤 id>/<路径>`**——Windows 上 WebView2 不支持非标准协议的子资源加载，直接写 `skin://` 报 `ERR_UNKNOWN_URL_SCHEME`（样式/脚本静默不加载）。
- 主题变量只挂 `:root[data-theme="dark"]`（浅色是默认主题，变量直接在 `:root`）：主题选项按钮自身带 `data-theme` 属性（JS 读取用），选择器裸写 `[data-theme="dark"]` 会把深色变量套到该按钮上——同类事故曾发生在浅色块上（深色模式下「浅色」按钮静止时黑字隐形、移入变白底），默认主题翻转后方向对调，约束同理。
- 信息提示统一走 `src/js/toast.js` 单例（新提示替换旧提示，向上淡出后移除）；不要再新增各自 `appendChild` 的 showToast——快速连续操作时提示会堆叠。
- 管理器窗口隐藏→重显后按钮会残留 :hover 样式：窗口隐藏时 WebView2 收不到 mouseleave，重显后按「最后已知光标位置」（还停在刚点过的按钮上）重算 hover。合成事件清不掉（非可信输入），只有真实 pointermove 能更新它的光标位置——故 CSS 中所有交互元素的 `:hover` 规则一律挂 `body.hover-ok` 门控（已覆盖 20+ 条规则；`app.js` 在隐藏/失焦时摘除、第一次真实 pointermove 时恢复），按钮点击时同时 `blur()` 避免 :focus-visible 描边残留。
- 管理器/日志窗窗框 = **无标题栏原生窗框**：无边框建窗（`decorations(false)`）后 `apply_native_frame` 做三件事——样式剥 `WS_CAPTION` 加回 `WS_THICKFRAME|WS_BORDER`、装 `native_frame_proc` 子类把 `WM_NCCALCSIZE` 绕开 tao 交 `DefWindowProcW` 默认处理（非最大化时再把 client 顶边拉回「窗口顶 + 1px」，见第三个坑）、发 `SWP_FRAMECHANGED` 让 DWM 重估——DWM 随即画出原生 1px 边框、阴影与最大化/贴靠动画，且无标题栏（Win11 圆角/轮廓同样随真实窗框自动生效）。**关键坑**：tao 0.35 对 `decorations(false)` 窗口自建 `NCCALCSIZE=0`（client = 整个窗口矩形，见其 event_loop.rs）——DWM 据「非客户区为空」判定无框可画，所以只补样式位没用，必须把 NCCALCSIZE 交还默认处理。**第二个坑**：tao 的 `WindowState::apply_diff` 在任何窗口标志变化时（`set_visible`、最大化/还原等）用 `to_window_styles()` 全量重写 `GWL_STYLE`，而该函数无条件带 `WS_CAPTION`（仅 CHILD 窗口才按 decorations 剥除）——建窗时剥掉的标题栏会被 `show()` 静默加回，实机验证 `verify_manager_frame.py` dump 出完整 `WS_OVERLAPPEDWINDOW` 即由此而来；故 `native_frame_proc` 同时拦截 `WM_STYLECHANGING`，样式落地前就地改写 `styleNew`（剥 `WS_CAPTION`、保 `WS_THICKFRAME|WS_BORDER`，同 factory.rs 皮肤子类手法），让标题栏样式永远落不了地。**第三个坑**：默认 NCCALCSIZE 把可缩放边框厚度 inset 加在四边，两种状态各有一修：①还原态——左/右/下被 DWM 放到可视区外（`GetWindowRect` 比可视框大 ~7px），唯独顶部留在可视区内，DWM 只画 1px 顶边框、其余 ~7px 成死白边（管理器窗实测 client 顶比窗口顶低 8px），故把 `rgrc[0].top` 改写为「窗口顶 + 1px」；②最大化——无 `WS_CAPTION` 的 `THICKFRAME` 窗口最大化时系统按显示器全矩形摆窗（不做 work area - **`[hidden]` 属性 vs 作者 display（已复发四次，防第五次）**：UA 样式表给 `[hidden]` 的只是 `display:none`，任何作者规则里的 `display:block/flex/...` 优先级都压过它——元素设了 `hidden` 仍照常显示（web-view 的 `#frame`/`.empty`、media-hub 的封面占位、power-tools 的预览图，四处同根）。规则：**任何既用 `hidden` 属性又有作者 display 的元素，必须配 `<选择器>[hidden]{display:none}` 显式压住**；另注意 `.status-badge.hidden` 这类「语义 class 恰好叫 hidden」的元素若哪天对它加 `hidden` 属性会再踩同一雷（display:inline-flex 恒胜）。排查同类问题时 grep 皮肤/管理器里 `hidden` 属性与作者 display 的交叉点。
- 管理器窗口圆角策略 = **随系统默认**：真实窗框样式下 Win11 由 DWM 自动圆角（见上条窗框机制），Win10 保持方角——这是产品决定，不是缺陷。曾试过「透明窗口 + CSS `border-radius`」让 Win10 也圆，后被否决回退；不要再给管理器窗口加 `transparent(true)` 来追圆角。推论：**窗口级元素（`body`/`#app`/`.settings-overlay`/`.wizard-overlay`）一律不设 `border-radius`**——它们曾带配合圆角窗框的 12px 半径，Win10 方窗上设置/安装引导遮罩的四角会露出未覆盖的角块；Win11 的圆角由 DWM 在窗框上裁切，不依赖这些半径。早年曾否决 `decorations(true)`（怕引入重复标题栏、丢失自绘品牌头部）——最终落地的「无标题栏原生窗框」正是那个顾虑的正解：剥 `WS_CAPTION` 留 `WS_THICKFRAME|WS_BORDER`，边框阴影在、标题栏不在。
