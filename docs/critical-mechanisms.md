# Critical Mechanisms (Do Not Regress)

> [中文版](关键机制.md) | English

> This document records the critical mechanisms in Driftlet that easily regress when the code changes (window/desktop layering, the install pipeline, data flow, etc.). Before modifying `src-tauri/src/desktop.rs`, `window/factory.rs`, `window/snap.rs`, `skin/protocol.rs`, `lib.rs`, `commands.rs`, or the related frontend code, read the corresponding section first.
>
> The `tools/win32-probes/` probe scripts and internal documents referenced in this document (e.g. `docs/设计规范.md`) live only in the dev repo and are not synced to the public one.

---

## Frameless Mechanism

The root cause of, and the defenses against, skin windows "sometimes showing the classic title bar":

1. **`SetWindowSubclass` must be called on the thread that owns the window**. If `load/reload_skin` runs on a `spawn_blocking` worker thread, the cross-thread call fails silently, the window keeps tao's `WS_CAPTION` style, and the DWM draws the classic title bar from it. Install/reinstall always goes through `install_frameless` (run directly on the main thread / rendezvous via `run_on_main_thread`); the 5-second timer idempotently reinstalls on the main thread as self-healing.
2. **`DwmExtendFrameIntoClientArea(-1)` is forbidden**. Glass extension paints any DWM frame into the entire client area, and the title bar shows through transparent skins.
3. `SWP_FRAMECHANGED` is sent only when the styles are actually dirty. Calling it unconditionally makes the DWM re-evaluate the window frame over and over — i.e., keeps giving the frame a chance to come back.
4. tao's `to_window_styles()` always includes `WS_CAPTION` for top-level windows, and any `set_window_flags` (e.g. `set_always_on_top`) rewrites the styles via `apply_diff` — the subclass's synchronous interception of `WM_STYLECHANGING` is the backstop.

## Pin to Desktop

1. **The real mechanism of Win+D**: skins **are not minimized** — the frameless style strips `WS_MINIMIZEBOX`, and minimize-all only targets minimizable windows. The skin "disappearing" is **z-order occlusion**: Show Desktop raises the desktop icon host (and the wallpaper WorkerW) to the top of the non-topmost band, covering everything on the desktop layer. Any "rearrange once on state change" scheme loses the race against that raise.
2. **Current solution = continuous z-order pinning**: every 250 ms, verify that each pinned-to-desktop skin is in place (the test = **the window immediately below is the icon host or another pinned skin** — with multiple skins, the strict "exactly right above the host" condition cannot hold for all of them at once; it once caused ≥2 skins to flip back and forth every tick, each eating a SetWindowPos). If one has drifted, insert it back **immediately above the desktop icon host (the host of `SHELLDLL_DefView`)**; once converged, multiple skins stack in a pile above the host. No state machine, no helper window — it self-heals every kind of disorder (Win+D double cycles, click raises, fullscreen apps, host rebuild after an explorer restart). A skin in the foreground (the user is interacting with it) is skipped, and sinks back to the desktop layer within 250 ms of losing focus. When the host itself is at the top of the z-order, the repair falls back to `HWND_TOP`; enforce validates the process ownership of the hwnd — if the hwnd has been recycled by the system into someone else's window, it only cleans up the entry and never touches the window.
3. Finding the icon host **uses no version heuristics**: both Progman directly containing `DefView` (Win11 24H2+, and Win10/11 right after an explorer restart) and a top-level WorkerW containing `DefView` (the classic form) are collected, and the one highest in z-order wins — that is the desktop surface actually being rendered.
4. The z-order must be explicitly placed **immediately above the icon window** — below it, the desktop ListView (`SysListView32`) swallows all clicks, and the skin can never be clicked or dragged.
5. When pinning to desktop, set `WS_EX_TOOLWINDOW` and clear `WS_EX_APPWINDOW` (invisible in taskbar / Alt+Tab, belt-and-braces against minimize-all); when unpinning, **clear both bits** — tao never sets `WS_EX_APPWINDOW` for `skip_taskbar` windows in the first place, so "restoring" it means inventing it out of thin air, which would put the skin on the taskbar / Alt+Tab.

## Position Lock

- The drag-interception switch = `__DESK_PP__.positionLocked` inside the webview (injected by the bridge, `skin/protocol.rs`).
- The locked state at window creation must be baked into the bridge by the protocol layer via the `skin://` URL query (`locked=1`) — do **not** restore it with a post-creation eval (it races page load; this once caused the lock to be lost after reload when switching always on top ↔ pin to desktop).
- Toggling the lock at runtime goes through the eval in `set_skin_position_locked` (the page is already loaded, no race); the lock CSS uniformly uses the `#desk-lock-style` id, removed on unlock.

## Skin Dragging and the Context Menu

- No longer relies on `-webkit-app-region: drag` (Windows treats draggable regions as a title bar and pops up the system menu on right-click). `.drag-region` in the skin HTML gets a `pointerdown` binding from the injected script; pressing the left button calls the backend `start_skin_drag` command to drag (border resize reuses the same synthesized-message mechanism — see "Border Drag-Resize"). **A press landing on an interactive element (`button/input/select/textarea/a/label/[contenteditable="true"]`) must skip the drag** — `start_dragging` enters the system modal move loop on pointerdown and captures the mouse, so the matching pointerup is eaten and the DOM `click` never fires (in 1.0 controls-demo had no in-window buttons, so this bug stayed latent until a skin with in-window buttons appeared).
- Right-click = a self-drawn native menu (Open Skin Config / Refresh Skin / **the window-behavior quick-toggle section** (Place on Top / Lock Position / Click-through / Resize by Dragging / Edge Snapping — `MF_CHECKED`, check state = a snapshot taken when the menu opens, clicks dispatch to the corresponding `set_skin_*_impl` to flip, two-way sync with the editor's Window tab via the same `window-config-changed` event) / Hide Skin / Unload Skin 「隐藏皮肤 / 卸载皮肤」): bridge `contextmenu` → `show_skin_context_menu` command → `TrackPopupMenu` on the main thread (`TPM_RETURNCMD`, modal, with `SetForegroundWindow` before the call so clicking outside can close it) → action dispatch. "Open Skin Config" activates the manager and `emit("open-skin-config")`; "Hide Skin" calls `set_skin_visibility` to hide the current window (one more native TrackPopupMenu item between Refresh and Uninstall — hiding flows through the `sync_tray_toggle_item` funnel so tray checks and the editor badge follow the real window state, without taking the lifecycle lock); refresh/uninstall reuse `reload_skin` / `unload_skin`, and must be **fire-and-forget** (return immediately after spawn) — the action destroys the very webview that made the call, and awaiting would make wry deliver the invoke response to a dead window (in debug this prints a harmless PostMessage warning). **Skins can opt out of the host menu per element**: the bridge listens for `contextmenu` at the end of the window bubble path (the last stop, after every page handler has run), and returns early when `e.defaultPrevented` is true — a `preventDefault()` means the skin consumed the right-click itself (e.g. right-click-to-edit on a card). The modal wait must run inside spawn_blocking behind the `SKIN_MENU_OPEN` reentrancy guard: the wait used to block an async worker on a bare `rx.recv()`, so a skin looping the call could park every worker (host commands stall) and nested modals would recurse on the main-thread stack — while a menu is open, further calls are dropped. **Skins can register custom menu items** (`skin_set_menu_items`, SkinLabel tier): the registry lives in `factory.rs` (skin id → items; cleared by `unload_skin_impl` on unload, re-registered by the skin itself after reload); custom items render in their own section between Hide and Uninstall with separators (`MF_CHECKED` for check state, zh/en label picked by manager language with fallback), id = `SKIN_MENU_CUSTOM_BASE`(100) + index; a selection is posted back via `window.eval` dispatching the `desk-skin-menu-item` DOM event (same channel as desk-setting-changed, fire-and-forget, no window destruction).
- **`close()` returning ≠ the label is freed**. In `destroy_skin_window`, after `window.close()` the webview still needs a few ms in the event loop to actually be destroyed; `load_skin` recreating a window with the same label right away reports "already exists" (right-click refresh once reliably reproduced "can't come back after uninstall"). So after close you must poll `get_webview_window(label)` until it is None before returning. **Polling is only needed on the "rebuild with the same label" path** — the tray exit `graceful_exit` uses the no-wait `close_skin_window_nowait` (the split-out shared first half); otherwise every loaded skin serially waits for one webview destruction, which is a source of exit jank. Do not change the exit path back to `destroy_skin_window`.
- The WebView2 default menu is disabled via `SetAreDefaultContextMenusEnabled(false)`. WebView2 is not ready yet at window creation, so the first call fails — the creation-time retry thread (`spawn_webview_hardening_retry`, ~6 s) plus the 5 s maintenance timer keep covering it; do **not** change it back to a single post-creation call. The subclass's interception of `WM_NCHITTEST => HTCLIENT` and `WM_NCRBUTTONUP` / `WM_CONTEXTMENU` is kept, to prevent the system menu leaking through.
- **Browser accelerator keys are uniformly disabled (manager + all skin windows)**: `factory::disable_browser_accelerator_keys` turns off WebView2 browser accelerator keys via `ICoreWebView2Settings3::SetAreBrowserAcceleratorKeysEnabled(false)` (Settings3 obtained via `settings.cast`) — F5 / Ctrl+R / Ctrl+F5 refresh, Ctrl+P print, Alt+Home, F12 devtools etc. all go dead; editing keys like Ctrl+C/V/X/Z/A are DOM-level shortcuts and are unaffected. The point: pages cannot be refreshed or navigated by keystroke, so the window lifecycle belongs entirely to the manager. The single exception: with Developer mode on (Settings → Advanced toggle), F12 / Ctrl+Shift+I inside a skin window opens DevTools — this does NOT go through the accelerator-key switch (`SetAreBrowserAcceleratorKeysEnabled(true)` would also hand back refresh/print keys and fight the maintenance timer's self-healing re-application); the injected bridge captures the keydown (capture phase) and the `open_skin_devtools` command calls `ICoreWebView2::OpenDevToolsWindow`. The retry structure is shared with the context menu: the creation-time `spawn_webview_hardening_retry` (replacing the original `spawn_context_menu_disable_retry`, retrying both hardening items together for ~6 s during WebView2's async initialization); afterwards both skin windows and the manager window are re-set self-healingly by lib.rs's 5-second maintenance timer (the same pass as the context menu).

## Border Drag-Resize (resizable)

- **The switch value is tri-state**: the runtime config `SkinRuntimeConfig.resizable: Option<bool>`; None = follow `skin.json window.resizable` (old configs missing the field are None, automatically following the author's default); Some(v) = the user's explicit choice on the "Window" 「窗口」 page. Both window-creation baking and panel display use the effective value `config.resizable.unwrap_or(manifest.window.resizable)`.
- **The hot zones must be implemented in the JS bridge layer, not via subclass `WM_NCHITTEST`** — the WebView2 child window covers the entire skin window, so the parent (the subclassed tao window) never receives the hit test (this was once implemented that way; even the frameless cursor couldn't drag it, and it was reverted).
- Current chain (same mechanism as `start_skin_drag`): effective value → URL-baked `resizable=1` at window creation (same path as `locked=1`; **do not** change back to post-creation eval) → the protocol layer bakes `__DESK_PP__.resizable` → the bridge script, when `pointermove` hits the 6px edge hot zone, shows the resize cursor via `#desk-resize-style` (`*{cursor:…!important}`), and on `pointerdown` (`stopPropagation` in the capture phase, to avoid triggering a drag) calls `start_skin_resize` → backend `ReleaseCapture` + `PostMessage(WM_NCLBUTTONDOWN, HT*)`; DefWindowProc enters the system modal resize loop.
- **Runtime toggle = `set_skin_resizable` eval calling the bridge's `__DESK_PP__.setResizable(on)`** (the page is already loaded, no race): flips the flag + syncs the border hint layer (`#desk-resize-frame`: 4px yellow-black hazard stripes on the four edges, a `transform` displacement animation (GPU-composited; a background-position animation repaints every frame and jitters — do not change back), `pointer-events:none`, boundaries visible even on transparent skins). The bridge's pointermove/pointerdown listeners are **permanently registered and check the flag per event** — do not change back to flag-conditional registration, or enabling it would require a reload to take effect.
- Size persistence goes through tao `WindowEvent::Resized` (same path as `Moved`): physical pixels ÷ **the creation-time snapshot scale** (`SCALE_SNAPSHOTS`: physical client width ÷ logical width measured at window creation — the old layout scale (current physical ÷ stored logical) made the conversion equal the stored value on every event during a resize, so border-drag sizes were never persisted; the snapshot is size-independent and removed on destroy) → in-memory config updated immediately + 500 ms debounced disk write (shares `debounced_config_flush` with position) + `emit_to("main", "skin-resized")` to refresh the panel inputs. The panel's `set_skin_size` loop-back event carries the same value and is skipped, not written.
- **Zoom**: the user can scale the whole skin to 50%–200% on the "Window" 「窗口」 page (`MIN/MAX_ZOOM`, `clamp_zoom`). Tri-state value: `SkinRuntimeConfig.zoom: Option<f64>`; None follows `skin.json window.zoom` (**use Option, not an opacity-style bare f64** — entries built by `or_default()` won't flush the manifest default to 1.0; the serde default of `WindowDefaults.zoom` must fall back to 1.0 — landing on 0.0 = the window gets multiplied away). **The width/height in the config are always the 100% base size; the panel's width/height inputs are always the zoomed actual size**: actual window = base size × zoom (`inner_size(w*z,h*z)` at window creation, `set_size` in `set_skin_zoom`/`set_skin_size`), and `WebviewWindow::set_zoom(z)` (WebView2 ZoomFactor) scales the content by the same factor — **both sides multiplied by the same ⇒ the page's CSS viewport is always the design size, the layout never reflows, and any skin can be scaled as a whole with zero adaptation** (this is the platform landing point of "all skins must be written so they can scale proportionally"). The conversion points of the two size semantics: persistence is always = actual ÷ effective zoom (the Resized event; the panel's `set_skin_size` inputs the actual size and converts the same way; the effective zoom is read live from config, missing entries fall back to the manifest — the closure captures `manifest_zoom`); panel display is always = actual (`get_skin_detail` multiplies the config width/height by zoom before returning, `skin-resized` carries the actual value, and since `set_skin_zoom` leaves the base size unchanged its loop-back would be swallowed by Resized's "unchanged, skip", so it must explicitly `emit("skin-resized")` itself); when `set_skin_zoom`'s entry is missing it seeds from the manifest size (`or_default`'s 300×200 would make set_size wrong); a `set_zoom` failure only degrades to a log (the size is still correct), and at window creation it is called before show, so there is no 100% flash.
- The subclass's `WM_GETMINMAXINFO` setting a minimum of 60×40 (DPI-scaled) must be kept — the modal resize loop reads it no matter who triggered it, preventing the window from being dragged to a size that can't be grabbed.

## Edge Snapping

- **The hook point = the window subclass's `WM_MOVING`** (`window/factory.rs`); do not implement it with the `Moved` event + `set_position` — that would loop back on itself and the drag trajectory wouldn't be smooth. The system modal drag loop passes in the pending screen-coordinate RECT at every step; `on_window_moving` in `window/snap.rs` rewrites it in place to complete the snap. Precise coordinates entered in the panel (`set_skin_position`) don't take this path and are unaffected by snapping.
- **Snap state is registered per HWND** (`SNAP_WINDOWS` in `snap.rs` — only the HWND is available in the subclass callback): `upsert` at window creation, `unregister` at destruction (HWNDs get recycled and reused by the system; a leftover entry would mistake an unrelated window for a snap candidate, so it must be cleaned up on destroy), `upsert` updates on panel toggle / gap change. Candidate edges = the other skin windows in the registry (live `GetWindowRect` during the drag, no caching, skipping destroyed/invisible/minimized ones) + the **work area** of the monitor the window is on (`MonitorFromRect` + `GetMonitorInfoW`, excludes the taskbar, multi-monitor correct).
- **Snapping = pure distance judgement**: on each of the X/Y axes, screen candidates are computed first; if |delta| ≤ threshold (`SNAP_THRESHOLD` = 10 logical px, converted to physical px by the window's DPI) the screen wins; only when neither is within threshold does the window candidate with the smallest |delta| win (left/right/top/bottom edge alignment + adjacent abutting). A window candidate requires the two windows to overlap, or be within threshold distance, in the direction perpendicular to that axis — otherwise distant windows cause "phantom snaps". After snapping, within the same drag you drag out of the threshold zone to detach — the feel is simple and predictable; fine adjustment works via threshold detach or the manager panel's exact coordinates. Direction-aware escape (3px reverse detachment + escape suppression) and Shift temporary bypass were both tried; in practice the feel was unstable/superfluous, both were reverted and deleted — do not add them back. **Do not regress (slow-drag-stuck incident)**: the WM_MOVING proposed rect is a delta off the previously *written-back* rect (verified with injected-input trajectories) — after a snap rewrites the window, the next proposal still hugs the snapped position, so judging the proposal directly sticks a slow drag inside the threshold zone forever (only a single-step jump larger than the threshold — a fast flick — could detach; it felt like "can't drag off screen"). Snap decisions must judge the raw drag trajectory accumulated from deltas (`DragRuntime.raw/last_out`, advanced per step by `advance_raw` as "proposal − previous write-back", reset by `begin_drag`); dragging out of the threshold zone detaches.
- **Escape window (REMOVED — do not add back)**: it used to be a 1-second snap-free window on "release and drag again" (when the previous drag had ended snapped and the window was still at the same spot, the first second of the next drag didn't snap and only clamped the window inside work area − gap to keep it on-screen). Back when slow drags were stuck, it was the only fine-adjustment outlet; once raw-trajectory tracking (above) made threshold detach work, it lost its purpose and was removed wholesale with the fix (`ended_snapped`/`escape_until`/`should_arm_escape`/`clamp_to_work`/`ESCAPE_WINDOW` all deleted — fine adjustment goes through the manager "Window" tab's exact coordinates). `DRAG_STATES` now only serves the per-drag raw-trajectory reconstruction (reset by `begin_drag`, cleared on `unregister`; no cross-drag memory remains).
- The gap `snap_gap` (logical pixels, clamp 0–200 = `MAX_SNAP_GAP`) applies both to screen edges and to window adjacent-abutting (alignment-type candidates don't include the gap). Persisted in `SkinRuntimeConfig.edge_snap` / `snap_gap` (both `Option` + `#[serde(default)]` — None = follow the manifest default, see the do-not-regress note in this same entry); the commands `set_skin_edge_snap` / `set_skin_snap_gap` only persist when the skin is not loaded, and sync the registry for immediate effect when it is loaded (same semantics as `set_always_on_top`). **Do not regress (panel-display-vs-actual-state incident)**: fields with Option-follows-manifest semantics must be resolved to effective values in `get_skin_detail` before going down to the manager panel (`resizable`/`zoom`/`edge_snap`/`snap_gap` — `None → manifest default`). A bare None renders as "off / 0" in the frontend, the opposite of the manifest-driven actual behavior (the isles skins' manifests declare on/20px while the panel showed off/0 — the user concluded the switch did nothing).

## Click-through (RESTORED — the old root cause was our own subclass stripping the bits, not "styles can't do it")

- **The working mechanism (current implementation)**: tao's `set_ignore_cursor_events(true)` sets `WS_EX_TRANSPARENT|WS_EX_LAYERED` on the top-level window (tao `window_state.rs`: `IGNORE_CURSOR_EVENT` ⇒ both bits), and the OS hit-test then **skips the window as a whole** — the WebView2 descendant windows covering the client area are never hit at all, and clicks/scrolls land on the window or desktop below. Proven by a minimal demo (same tao 0.35.3, same frameless+transparent WebView2 window shape); the old fear that "LAYERED breaks WebView2/DirectComposition rendering" does not hold on the current WebView2 runtime.
- **The real root cause of the two failed rounds**: not that the combo doesn't work, but that our own frameless subclass fought the feature — `force_frameless`, `WM_STYLECHANGING` and `WM_STYLECHANGED` unconditionally stripped TRANSPARENT|LAYERED, with the 5-second self-heal timer re-stripping as a backstop, so the bits tao set never survived one cleanup cycle. Round one also took the "non-layered TRANSPARENT" route (hit-testing really does ignore that bit — conclusion still valid), and round two's descendant HTTRANSPARENT subclassing broke across processes (conclusion still valid).
- **Keystones of the current implementation**:
  - Click-through windows are **registered per HWND** (`PASSTHROUGH_HWNDS` in `window/factory.rs` — only the HWND is available inside the subclass callback); the three stripping sites use the `FRAMELESS_EXSTYLE_PASSTHROUGH` mask for registered windows to keep TRANSPARENT|LAYERED, while every other window behaves exactly as before.
  - **Ordering keystone: register (`set_passthrough_hwnd`) BEFORE calling `set_ignore_cursor_events`** — tao lands the `SetWindowLongPtr` on the main thread via `execute_in_thread`, and the resulting `WM_STYLECHANGING` is vetted by the subclass against the registration state at that moment; reversed order loses the bits immediately.
  - The destroy path (`close_skin_window_nowait`) must unregister — HWNDs get recycled by the system, and a leftover entry would let an unrelated window keep the pass-through bits (same discipline as the edge-snap registry).
  - Config `SkinRuntimeConfig.click_through` (`#[serde(default)]`, default off); the `set_skin_click_through` command (gated by `require_manager`) flips in place when the skin is loaded and only persists otherwise (applied at next creation by `create_skin_window`). The escape hatch is the manager panel (always reachable via the tray) — a click-through skin no longer answers the mouse, but no global hotkey is needed (only a single-window demo does).
- **Historical probe conclusions that still hold** (probe `tools/win32-probes/ctprobe.ps1` — do not retry these routes): top-level non-layered TRANSPARENT is ignored by hit-testing; the sibling transparent hit-test skip under the desktop (WorkerW child) only works for same-thread windows; HTTRANSPARENT bubbling from a subclass breaks across processes (the WebView2 descendants live in the msedgewebview2 process); cross-process `SetWindowLongPtr` setting TRANSPARENT on descendants only *swallows* clicks, never *passes them through*; `WindowFromPoint` only skips hidden/disabled windows — **it is not a valid click-through oracle**. The heavy routes (a `WH_MOUSE_LL` intercept+repost hook / a DWM-thumbnail shadow window) remain not worth it.
- **Residual risk**: "LAYERED breaks rendering" cannot be disproven for every environment (older WebView2 runtimes, exotic GPU paths) in one pass — the per-skin, default-off switch is the circuit breaker; if a visual regression shows up somewhere, turning it off reverts instantly. The "mouse-immune" need once served by the wallpaper layer is now served by this feature (pin-to-desktop + click-through = a purely presentational widget; desktop icons stay directly clickable).

## Virtual-Display DPI and the Rasterization Scale

- **The black-background root cause: WebView2 visual misplacement on inconsistent-DPI virtual displays (settled on a GameViewer virtual display + Win10 21H2 @125%)**: remote-control virtual displays (GameViewer/Sunlogin IddCx adapters) report contradictory DPI — `GetDpiForMonitor` says 96 while the system DPI is really 120; after creation the window is reassigned to the system DPI (`GetDpiForWindow` 96→120, **with no WM_DPICHANGED and no relayout**), WebView2 resets the rasterization scale to 1.25 from the new window DPI while tao laid the frame out at the creation DPI (physical size = logical values) — the content is composed at "window rect ×1.25": rounded corners/transparent areas have no content over them and show black, and the oversized visual bleeds past the window leaving black ghosts on the desktop; ordinary, opaque, always-on-top and pin-to-desktop windows are affected too. **Fix = `force_webview_rasterization_scale`: force the controller's rasterization scale to the window's LAYOUT scale** (`layout_scale_factor` = physical client width ÷ design logical width — tao's `scale_factor()` lies on this path (physical == logical while the cache says 1.25) and must not be used; the correct invariant, proven in wry's source: controller Bounds = physical client rect, CSS viewport = Bounds ÷ scale, so scale must equal physical ÷ design-logical, rounded to 0.01 to kill physical-rounding noise). Applied once at creation, then re-applied idempotently at 0.6s/1.5s/3s after showing (`schedule_rasterization_force`) to cover the runtime's late resets; on healthy displays both values are already equal, so it is a no-op. Dead ends (do not retry): `SetBoundsMode(RAW_PIXELS)`, creation-only `SetRasterizationScale`, `--force-device-scale-factor`, `--disable-gpu-compositing` (worse — the visual detaches to the screen origin), `NotifyParentWindowPositionChanged` (makes the controller re-derive its presentation layout from the parent chain and leaves a 6×4 px unwritten black strip at the window's right/bottom edge), and forcing to tao's `scale_factor()` (magnifies content 1.25× on the lying-cache path). Probes: `wp-monitor-topology.ps1` (monitor/DPI topology); the skin-parent-chain diagnostic probe was removed together with the wallpaper layer (`wp-black-diag.ps1` lives in git history).

## Wallpaper Layer (Removed)

The wallpaper layer (the skin `SetParent`-ed as a child of the desktop WorkerW/Progman — below the desktop icons, above the wallpaper, physically mouse-immune) **has been removed in this version**: the implementation depended on a full stack of undocumented internals (the Progman/WorkerW/DefView class names, the `0x052C` message, z-order bands, explorer's re-hosting behavior), Windows 11 24H2 already changed the desktop rendering pipeline once, and every failure mode is a silent visual glitch (invisible skin / black background / ghosts) that can only be verified live on each Windows build — the maintenance cost was judged higher than the feature's value. The full mechanism, root-cause history (visibility keystone, form convergence, WS_CLIPCHILDREN paint holes, surface holes, etc.) and all probes live in git history (the wallpaper-layer probes were removed from the working tree in the tools cleanup; only the topology probes still relevant to the current z-order pinning — `wp-topology-check.ps1` / `wp-monitor-topology.ps1` — remain).

- **Config migration**: legacy `wallpaper_layer: true` entries are normalized to pin-to-desktop by `normalize_mode_flags`; the `SkinRuntimeConfig.wallpaper_layer` field is deprecated and kept only for that migration. Placement is back to two states (always-on-top / pin-to-desktop, exactly one true): `set_skin_placement` accepts only `top` / `desktop`; **both directions flip in place** ("top → desktop" used to reload — recreating the window resets the skin's JS runtime state, interrupting timers and the like; fixed): desktop → top = unpin first, then `set_always_on_top(true)` (the pin's HWND_BOTTOM would strip a later-set WS_EX_TOPMOST, so the order must not be reversed); top → desktop = `set_always_on_top(false)` first (keeps tao's internal flag in sync), then `pinner.pin` (drops to HWND_BOTTOM + registers with the 250 ms enforcement loop; the end state is identical to creation-time pinning and Win+D behavior is unchanged — the loop has no transition state machine, it keys off registration, not the path taken). When the migration fires, `repaint_wallpaper_surfaces_once` (`desktop.rs`) does a one-time `SW_HIDE`→`SW_SHOW` forced repaint of every candidate wallpaper surface (on a background thread, once startup has settled), clearing the residual black window-shaped holes the removed wallpaper layer may have left on users' wallpaper.
- **What stays**: the dead-handle `Destroyed` patch in the vendored `src-tauri/vendor/tauri-runtime-wry` (wired via `[patch.crates-io]` in `Cargo.toml`; the patch must survive upgrades/replacement) — it was introduced for the wallpaper layer's cross-process child windows, but it is equally necessary for any "process killed via Task Manager" scenario: upstream's `WindowMessage::Destroy` handler only runs `on_window_close` (drops the tao window) — entry removal depends on the `Destroyed` event that never arrives afterwards; the patch (NOTE(driftlet) in `vendor/tauri-runtime-wry/src/lib.rs`) detects a dead handle (`IsWindow` = false) on destroy and replays `WindowEvent::Destroyed` to tauri + removes the runtime entry + reuses the empty-store exit logic — so dead-hwnd windows release their labels for recreation. The virtual-display DPI fix lives in the previous section.

## Preview Capture

- **`capture_skin_preview` must stay an `async fn`**: Tauri 2's non-async commands execute on the **main thread**, while the capture implementation needs `recv_timeout` to block waiting for the WebView2 `CapturePreview` completion callback — and that callback is dispatched precisely by the main thread message pump. A sync command blocks the main thread so the callback can never arrive, freezing the whole manager UI until timeout; an async command waits on a runtime worker thread while the main thread keeps pumping messages — no mutual blocking.
- Capture goes through `ICoreWebView2::CapturePreview` (`capture.rs`); **do not** change back to `PrintWindow` + GDI: the latter's alpha channel is undefined (the saved PNG has large transparent "missing chunks"), transparent skins get a black background, and when the window is occluded / pinned to desktop / minimized you capture a black screen or ghosting.
- **The preview PNG is downscaled to a longest side ≤ 640 px before hitting disk**: the manager card's display area is only 226×96 CSS px, while CapturePreview outputs at the window's physical resolution — a full-size PNG from a large skin decodes to ~8 MB of RGBA sitting permanently in the manager renderer (one copy per visible preview in the list). The downscale happens in `capture.rs` (via the `image` crate, png feature only), and **on any failure it falls back to writing the original**: an oversized preview is a memory tradeoff, a missing one breaks the "installed → preview visible" flow. Creator-shipped `preview.png/jpg/jpeg` is covered by a second line of defense: `package.rs` validates longest side ≤ 1280 px at both install and packaging (header-only parse — PNG IHDR / JPEG SOF; unparseable headers pass, since the browser can't decode those either), with a hand-mirrored copy in pack-skin (changing one side requires syncing and rebuilding the exe).

## Data Flow

```
User drags a skin → WebviewWindow Moved event
→ backend factory::save_dragged_position: in-memory config updated immediately (takes effect on reload) + 500 ms debounced disk write
→ emit_to("main", "skin-moved") → skin-editor.js listen() → only updates the input box display
```

- Dragged-position saving must stay in the **backend** Moved event; do not move it back to the frontend — the frontend listener is only registered while the config page is open, which once caused "drags aren't saved while the panel is closed, and the skin returns to its original position after reload".
- **Real-time sync of window-property changes to the manager (single funnel `emit_window_config_changed` — do not bypass)**: every path that mutates a window property (manager panel / skin right-click quick toggles / skin self-control `skin_set_window_config`) must land in a `set_skin_*_impl` and thereby pass through this function — it **dispatches twice**: `emit_to("main", "window-config-changed", { skinId, key, value })` (regardless of loaded state — the config is persisted and an open editor must reflect it; skin-editor.js listens and syncs the controls in place; an input the user is editing is not clobbered — same focus-protection idiom as the position inputs) +, when the skin is loaded, an eval dispatch of `desk-window-config-changed` (the skin-facing API surface). Panel-originated changes echo back the same value — idempotent, harmless. Incident behind this: the event used to go only to the skin — toggling edge snapping from the right-click menu left the "Window" tab's checkbox stale (panel-display-vs-actual-state incident). Completeness is pinned by a source-scan test in commands.rs (`window_config_setters_all_broadcast`: a new set_skin_*_impl that doesn't broadcast goes red). Position/size changes from dragging/border-resize take the Moved/Resized debounce channel (`skin-moved` / `skin-resized`), not this one — the skin dragged itself (it knows), and the debounce channel must not be flooded.
- **Rescuing fully off-screen skins** (after unplugging an external monitor / a DPI topology change, a skin can land outside every display — invisible and undraggable): the check is `factory::offscreen_target` — a skin counts as off-screen only when its window rectangle intersects **no** monitor work area (`Monitor::work_area`, physical pixels, same coordinate system as outer_position/outer_size); **partially off-screen is never touched** (multi-monitor seams and deliberate half-hiding are legitimate placements). When fully off-screen it is moved via `set_position` to the primary monitor's work area (top-left + 24px; the Moved event persists the new position through the existing debounce). Two hook points: `rescue_offscreen_skins` inside lib.rs's 5-second maintenance timer (topology changes self-heal within 5 s, and the first tick covers the startup auto-load — no WM_DISPLAYCHANGE hook needed), and the config page's "Bring On Screen" 「复位到屏幕内」 button via the `bring_skin_onscreen` command (`require_manager`; returns whether a move happened so the frontend can toast).
- Config values for position and size are **always logical pixels**: creation (`inner_size`), setting (`LogicalPosition` / `LogicalSize`), and event readback (physical ÷ `scale_factor`) all follow the same convention. Any path that feeds a config value into `PhysicalSize` / `PhysicalPosition` will, at DPI zoom ≠100%, make the actual size inconsistent with the panel and "restore" after reload.
- **New fields in persisted structures must carry `#[serde(default)]`** (`AppConfig` / `SkinRuntimeConfig`; except `Option` fields, which serde automatically sets to `None` when missing). The cost of forgetting: every old config.json fails to parse wholesale and is reset to defaults as a corrupted file — with the single-file scheme the blast radius is all skin data (only `.bak` as the backstop).
- For skins that no longer exist on disk, their config leftovers (`skin_settings` / `loaded_skins` entries) are **cleaned up uniformly at startup** (covering two sources: the folder was manually deleted, or the author changed the id); in-app deletion goes through `remove_skin` for immediate cleanup. Disk-write failures of settings commands **must be propagated to the frontend** (`配置保存失败: …` — "failed to save config: …"); do not change back to swallowing them with `let _ =` — the user would see "saved successfully" but lose it after restart. Exception: the drag debounce save only logs `log::warn` (the panel may not be open; nobody is there to receive the error).
- config.json (version 2) only stores window-page data and global settings; the user values of the "Skin Settings" 「皮肤设置」 page live in the **skin folder's `settings.json`** (see the next section). The v1 config's `skin_settings[id].custom` is migrated into each skin folder at startup by `migrate_v1_custom_settings` (after scan, before load_config): if settings.json already exists, the existing file wins and is not overwritten; entries whose write fails keep their custom and **the version number is not bumped**, retried at next startup; orphan entries (skin no longer exists) have their custom discarded with the version upgrade (consistent with prune semantics). `SkinRuntimeConfig` has deleted the `custom` field; leftover old keys are automatically ignored when serde reads them.
- **All writes go through `config::save_config`** (atomic write: temp file + rename) — it does **no normalization**; normalization is concentrated in the **startup load path** (`load_config`: `language` normalized via `i18n::normalize`, the always-on-top/pin-to-desktop either-or via `normalize_mode_flags`, and migration results are persisted immediately) — once loaded, the in-memory state is already normalized, so every write path naturally writes out the normalized result, eliminating the back-and-forth oscillation of "normalize on load, write back verbatim on save". The `save_app_config` command was deleted as a dead command (do not resurrect a same-named entry). New write entries must all go through `save_config`; don't hand-write `serde_json::to_string` to disk.

## Skin Custom Settings

- Initial values = baked into `__DESK_PP__.settings` when the `skin://` protocol layer serves HTML (a merge of schema defaults + override values from the skin folder's `settings.json`; see `baked_settings_json` in `skin/protocol.rs` and `effective_settings` in `skin/loader.rs`) — same reasoning as position lock; **do not** change it to a post-creation eval restore (races page load).
- **`password`-type values are not baked into the page**: `baked_settings_json` always replaces password items with an empty string (that key in `__DESK_PP__.settings` is always empty) — skin:// is same-origin for all skins, so a value baked into HTML can be fetched away by any skin. Skins instead read on demand via the `skin_get_setting` command (`skin_api/mod.rs`; identity is taken from the window label, it can only read keys declared in its own schema, no permissions declaration needed). Accordingly, the `skin-setting-changed` event after `skin_set_setting` writes to disk was changed to `emit_to("main")`, targeted at the manager — broadcasting would route the setting value (possibly containing a password) past every skin window via the event.
- **User override values are persisted in the skin folder's `settings.json`** (sibling of skin.json; read/write in `skin/settings.rs`: missing → empty, BOM tolerated, corrupted → renamed to .bak, atomic write). `skin.json` is never rewritten by the app: the schema and defaults live only there, and "reset" = delete `settings.json` (`reset_skin_config` also deletes `skin_settings[id]`, both falling back to defaults).
- **skin:// intercepts any `settings.json`** (including `.bak` / `.tmp`) → 404 — this file is an exposure surface newly introduced with the value-file scheme; without interception skin A could fetch skin B's setting values.
- Before serializing the settings JSON into `<script>`, `</` must be escaped to `<\/`, otherwise a `</script>` in a setting value closes the tag early.
- Runtime change = the `set_skin_custom_setting` command writes to disk then pushes via eval: updates `__DESK_PP__.settings[key]` and dispatches the `desk-setting-changed` document event. A skin that doesn't listen for the event still gets the new value on the next reload.
- **Skins can also write their own settings**: the `skin_set_setting` command (`skin_api/mod.rs`, skin-only — does not reuse the manager command; identity from the window label, can only write keys declared in its own schema, values go through the same `validate_custom_setting`, no permissions declaration needed). Therefore `settings.json` has **two writers**; the whole load→save sequence must hold `AppState::settings_lock` (std Mutex; both commands are sync fns) to prevent them from losing each other's updates — do not split it back to lock-free.
- **Skin → manager direction sync**: after `skin_set_setting` writes to disk it does `emit_to("main", "skin-setting-changed")` (targeted at the manager, not broadcast — see the previous item); skin-editor.js listens and refreshes the corresponding control in place (`_syncCustomControl`: list-type re-renders the row — event delegation bound on the container is not lost; assignment-type only updates value/checked — the node must not be replaced; composite types like palette/chips don't touch the DOM in the first version; always skip when focus is inside the control — content being edited takes priority). A skin's **self-write does not re-dispatch** `desk-setting-changed` (preventing a "write → event → write again" loop), it only silently syncs `__DESK_PP__.settings[key]`.
- Persisted override values are only adopted when their type matches the schema declaration; after a skin author changes a setting item's type, old values automatically fall back to the defaults.
- **Symmetric text-field naming + legacy-key aliases (do not regress)**: `name_zh`/`name_en`, `label_zh`/`label_en`, etc. come in pairs; the legacy unsuffixed keys (`name`/`label`/`group`/`description`) stay accepted via serde aliases. **Any code path that rewrites skin.json (duplicate_skin / sync_skin_copy) must remove the corresponding legacy key before writing the new one** — an alias shares its slot with the canonical name, so both keys present parse as a duplicate-field error and the rewritten skin won't load (fixed in this pass; a test pins it with `assert!(json.get("name").is_none())`). A skin reading `skin.json` itself via `fetch()` sees the raw file where aliases don't apply — it must fall back like `v.label_zh ?? v.label` (reference: `demos/controls-demo`).
- **Single-language skin fallback rule**: display selection = UI language preferred, missing (None or empty) falls back to the other language — a single-language skin shows the language its creator provided under either UI language; there is no `bilingual` switch (removed), and every field combination is valid. Backend `SkinManifest::display_name/display_description` and frontend `dom.js dispName/dispDesc` implement the same rule — do not let them drift; list sorting, the window title, and the tray menu all go through `display_name(DEFAULT_LANG)`.
- Controls are rendered by branching on `type`, concentrated in `renderCustomSettings` / `bindCustomSettings` in `skin-editor.js`; **adding a new control type requires syncing four places**: `SkinSettingKind` in `types.rs`, the type matching and fallback in `loader.rs`, the validation in `commands.rs`, and frontend rendering/binding (same for pack-skin's hand-mirror, see AGENTS.md). Custom controls exclusively occupy the "Skin Settings" 「皮肤设置」 tab, separate from the built-in "Window" 「窗口」 page. The `file` / `directory` picker controls have one extra link: **the system dialog can only be hosted by the manager** (a skin window neither has the handle nor should pop system dialogs) — the control's button calls the `pick_path` command (require_manager, blocking dialog inside spawn_blocking, extensions whitelisted to lowercase alphanumerics), and the picked value writes back through the same set_skin_custom_setting pipeline (the skin receives desk-setting-changed as usual).

## Skin Backend Interface (skin_api)

> The system-info and sensitive-capability commands that skins can call via `__DESK_PP__.invoke` (the `skin_api/` module). For the external contract see `docs/skin-development-guide.md` §2.3 / §5.

- **The bridge is a passthrough, with no command whitelist**: `__DESK_PP__.invoke` directly forwards `__TAURI_INTERNALS__.invoke`; any command registered into `invoke_handler` can be called by skins. Therefore **sensitive commands must carry their own permission check** (`require_perm`: window label → skin id → re-scan the manifest for `permissions`); "documented convention not to call it" is not enough. All new sensitive commands go through this entry.
- **Manager commands are uniformly gated by `require_manager`**: the bridge passthrough means the manager commands in `commands.rs` are also reachable by skins by default, and skins should never be able to reach them (unrelated to whether permissions are declared — `require_perm` can't cover this layer). All 64 manager commands (load/unload/settings/install etc.) validate at entry that the calling window label == "main"; calls from skin windows always fail with "该命令仅允许管理器窗口调用" ("this command may only be called by the manager window"). The legitimate skin exceptions are the Ungated 2 (`start_skin_drag` / `start_skin_resize`) plus the SkinLabel 4 (`show_skin_context_menu` / `skin_set_menu_items` / `open_skin_devtools` / `skin_console_log` — identity is reverse-looked-up from the window label; they can only operate on themselves); `policy.rs` is the single source of truth for the list, do not re-enumerate here. **New manager commands get `require_manager` by default**.
- **The command policy table `policy.rs` (a single source of truth for the whole app's attack surface)**: all 126 IPC commands register their gate tier in `COMMAND_POLICIES` — eight tiers: ManagerOnly (64) / LogWindow (2) / Perm (38) / AnyPerm (open_external only, 1) / ControlTarget (7) / CallerSkin (8) / SkinLabel (4) / Ungated (2). The table **does not change runtime behavior** (the gates stay inside each command body); its value is the three completeness tests — `policies_complete_and_marked` (the table and lib.rs's `generate_handler!` list are the same set in both directions with no duplicates, and every command's body contains the gate-maker text of its registered tier — a wrong tier goes red; markers carry no trailing `?` because `take_hotkey_error` consumes gates via `.ok()?`), `perm_const_names_resolve` (Perm const names anchor back to the real constants via `perm_const_value` — a typo panics, a renamed/deleted constant fails at compile time), and `gate_distribution_snapshot` (per-tier counts are pinned; changing a tier requires updating the numbers). **New-command discipline: put the gate on the first line of the body + register one row in the table (with the permission const name), or cargo test goes red** — "forgot to defend" shifts from a manual review item to a build failure; a new command module must be registered in `policy::tests::module_source`. **The table only registers, it never replaces the body gate** — do not delete any of the tests.
- **Capabilities are split and tightened per window**: `default.json` only attaches to `"main"` (core:default + minimize/toggle-maximize/hide — only what the manager frontend actually uses); the new `skin.json` attaches to `"skin-*"` with **empty permissions** — skins don't use @tauri-apps/api, app custom commands aren't constrained by the capabilities ACL, and the real gate is on the Rust side (caller_skin / require_perm / require_manager); core and plugin permissions like shell / dialog / autostart / window-create / event-emit are never granted to skin windows.
- **Rate-type readings = the sampling baseline pattern**: a static `Mutex<Option<…>>` holds the sampler (`CPU_SYS` for CPU, `PdhMultiCounter` for PDH); the first call only establishes the baseline and returns 0 — the dev guide already tells skins to poll once per second.
- **sysinfo 0.32 has no disk IO stats** (removed since 0.30); disk read/write speed goes through PDH `\LogicalDisk(*)\Disk Read/Write Bytes/sec` (the instance name is the drive letter, joined with sysinfo mount points by drive letter; **do not use `\PhysicalDisk`** — it aggregates by physical disk, and multiple partitions on the same disk would show the same rate); GPU usage goes through PDH `\GPU Engine(*)\Utilization Percentage` (instance names contain `luid_0x…_0x…`, aggregated by LUID to the DXGI adapter). PDH counter paths must be added as English paths with `PdhAddEnglishCounterW`, independent of the system display language.
- **GPU assembled from two sources**: name/LUID/total VRAM = DXGI adapter enumeration (skipping SOFTWARE adapters); VRAM usage = PDH `\GPU Adapter Memory(*)\Dedicated|Shared Usage` (under AMD drivers DXGI `QueryVideoMemoryInfo` always returns 0, so the DXGI value serves only as a fallback when PDH isn't ready). For unified-memory adapters (iGPUs), both the total and the usage are reported as shared system memory — the dedicated segment is just a small BIOS-carved slice and "dedicated + shared" can exceed physical RAM, making it an unsound basis (iGPU usage lands almost entirely in the shared counter anyway). **iGPU detection uses the D3D12 UMA architecture query** (`D3D12_FEATURE_DATA_ARCHITECTURE.UMA`, result cached per LUID) — do not guess from the dedicated-VRAM size: APUs can carve out a 1GB+ dedicated segment in the BIOS; this detection also produces the returned `gpu_type` field (`"discrete"` / `"integrated"`). There is no general Windows interface for core frequency (only vendor SDKs; the NVML route and the `frequency_mhz` field were removed per requirements).
- **Audio loopback**: wasapi automatically sets `AUDCLNT_STREAMFLAGS_LOOPBACK` for "render device + Capture direction + Shared", no manual flag needed; `convert=true` guarantees f32/48k/stereo. The capture thread is lazily started (spawned on the first `get_audio_spectrum`), **releases the device after 30 s idle** (a skin can be unloaded at any time, so the endpoint can't be permanently occupied), and failures are written to shared.error and surfaced by the command side. Spectrum = 2048-point Hann + FFT, 30Hz–16kHz log-spaced bands, normalized with a -60dB floor.
- **File sandbox (the `files` permission has been removed; the sandbox remains)**: file reads/writes inside the skin folder no longer need a permission declaration — the sandbox confines every operation to the skin's own install directory and is itself the basis for being declaration-free: first reject absolute paths and `..` components, then canonicalize and do a prefix check (against symlink escape); `create_dir_all` on the parent before writing, so write paths can also be canonicalized. `skin.json` / `settings.json` (including `.bak`/`.tmp`) are read-only — no write, no delete. Read 32MB / write 16MB caps. **Any path component containing `:` is rejected** (against NTFS ADS: `skin.json::$DATA` is an alternate data stream of the same file and could bypass the per-filename read-only interception — same rule as protocol.rs).
- **`run_command` must be async + spawn_blocking**: Tauri 2 non-async commands execute on the main thread (same constraint as the "Preview Capture" section); a 120-second child-process timeout on the main thread would freeze the entire manager. Child process output is read by two threads, one each for stdout/stderr (sequential reads get deadlocked by a filled pipe), each truncated at 1MB; Chinese Windows console output is GBK, and invalid UTF-8 falls back to `MultiByteToWideChar(CP_OEMCP)` transcoding. `CREATE_NO_WINDOW` hides the console window.
- **COM conventions for volume/media**: `volume.rs` calls `CoInitializeEx(MTA)` per call and **pairs CoUninitialize on both S_OK and S_FALSE (`hr.is_ok()`)** — S_FALSE ("this thread was already initialized with the same model") is also a success HRESULT, and checking only S_OK would miss one uninit and unbalance the refcount; only RPC_E_CHANGED_MODE (a failure code — already initialized under a different apartment model) goes unpaired; SMTC (`media.rs`) WinRT async always blocks with `.get()`, and all three media commands (`get_media_info` / `media_control` / `media_seek`) must be `async + spawn_blocking` (the same main-thread prohibition as `run_command`, see the "Preview Capture" section). SMTC degradation contract: no session returns `None`, which is not an error; cover/progress field failures just stay empty without failing the whole call. **Session picking = enumerate + prefer** (`pick_session`: playing > has progress > has metadata), never `GetCurrentSession` (that's Windows's "most recently interacted", and in multi-session scenarios — a browser plus NetEase Cloud Music — it isn't the real one). **Seeking**: `media_seek` (media permission) calls `TryChangePlaybackPositionAsync` with absolute seconds; source support is read via `IsPlaybackPositionEnabled` (surfaced as the `seekable` field — when unsupported the progress bar stays read-only).
- **Elevated-launch notice (`elevation.rs`, no auto-demotion — all demotion machinery removed)**: the app needs no administrator rights (the manifest has no requestedExecutionLevel = asInvoker; volume/media/run_command-normal-privilege/the five power commands/WebView2 all work as a standard user). At the very top of `run()` (before Builder/single-instance) it checks `TokenElevation` (not "is the user an admin" — a normal launch by an admin under UAC does not trigger); when elevated it only **notifies once**: a MessageBoxW (the windowing system isn't up yet, same technique as lib.rs's fatal_startup_error; language from a light early read of config.json with OS fallback) explains the consequences (shell-permissioned skins can silently run commands with full administrator rights; Explorer→manager .dskin drag is blocked by UIPI — double-click or the file picker work instead) — "Yes" writes `allow_elevated` into config.json as a persistent opt-out and continues (never asked again), "No" exits. **No demotion is attempted at all** — both routes were tried in the field and are retired for good, do not resurrect: ① scheduled-task relaunch (schtasks /create + /run): programmatically creating tasks to relaunch trips behavioral AV detection (Behavior:Win32/Execution.A!ml, observed on a real Administrator machine) and is provably useless for genuine Administrator accounts (the interactive token is itself elevated) — banned by maintainer decision; ② SAFER restricted token + CreateProcessWithTokenW / CreateProcessAsUserW: using a token requires SeImpersonatePrivilege / SeAssignPrimaryTokenPrivilege, and **a standard user elevated via UAC has neither of these admin privileges in their token** (observed PRIVILEGE_NOT_HELD / ACCESS_DENIED on both arms on a real machine) — demotion is account-shape-dependent and therefore unreliable. Leftover tasks and the `--demote-cleanup` argument from the 1.1.2 era were removed together with the demotion machinery (no self-clean logic remains in the repo). `DRIFTLET_ALLOW_ELEVATED=1` and the `allow_elevated` field (now part of AppConfig, so save_config can't drop it) are both opt-outs that skip the notice; debug builds skip it by default (dev-loop quiet), with `DRIFTLET_FORCE_DEMOTE=1` available to exercise the path in debug (legacy variable name kept). **Other dead routes** (all observed in practice): the explorer-COM chain (ShellWindows→…→GetItemObject(SVGIO_BACKGROUND)→IShellDispatch2.ShellExecute dies at not handing out IShellFolderViewDual, E_NOINTERFACE); `runas /trustlevel:0x40000` prompts via WriteConsole — with no console it dies instantly. `elevation::enable_privilege` stays as the shared privilege-enabling helper (AdjustTokenPrivileges returning Ok still requires checking GetLastError ≠ ERROR_NOT_ALL_ASSIGNED) — skin_api's sleep/power_control enable SE_SHUTDOWN_NAME through it; never copy a third implementation.
- **WebView2 runtime version floor = Chromium 111 (two layers — never change just one)**: the isles skins' scaling model is built entirely on container queries (`container-type: size` + cqw/cqh units, 105+) and `color-mix()` (111+) — on older runtimes those declarations fail wholesale: cards collapse and theme tints vanish (field report: "skins look drastically different on an old WebView2"). Layer one = the install/update side `bundle.windows.nsis.minimumWebview2Version` (bundler template logic: an installed-but-older runtime gets upgraded — the standard package goes online via EdgeUpdate, **the offline package instead upgrades it in place with the embedded offline runtime** (the upstream template only has the online path there, which always fails without network; fixed as customization ⑤); works in update mode too; the UpdateMode guard covers uninstall cleanup only). Layer two = the runtime-side `webview2.rs` startup check (winreg reads `Clients\\{F3017226-…}\\pv`, same lookup order as the installer; below the floor a native MessageBox guides a one-click update). **Reminding at every launch is deliberate** (the rendering is genuinely broken — the reminder is the repair entry); an unreadable version means not-installed/undeterminable → no warning (better to miss than to false-alarm — a missing runtime is the installer's job). The floor value is identical on both sides; changing it requires syncing both. Additionally — every cqw/cqh and color-mix declaration in the isles skins and the shared base carries a fallback line (fallback first, modern second: vw/vh, plain/neutral-gray/universal-black-veil colors; each @container breakpoint pairs a same-condition @media fallback block), so older runtimes degrade to a still readable, usable look — never delete the fallback lines when editing isles styles (the convention lives in the base.css header note and the guide's §3.5).
- **Clipboard goes through tauri-plugin-clipboard-manager** (Rust side `app.clipboard()`, the command carries its own permission gate); `open_external` uses `ShellExecuteW` (the shell plugin's `open` is deprecated — do not change back), whitelist = only `http(s)`/`mailto`/`ms-settings:` (system Settings-page URIs, handled by the Settings app — no code-execution surface; re-evaluate before whitelisting any other scheme); **the local-path arm has been removed outright** — defending ShellExecute on local files with an executable-extension blacklist was negative enumeration (a 35-entry list that can't keep up with new execution surfaces and was once bypassed via trailing dots/spaces); skins that genuinely need to open local files use `run_command` under the `shell` permission (high risk, shown on the install page); UNC / relative paths / `file:` / `javascript:` are rejected along with local paths. **All targets share one InvalidTarget error.** A return value ≤32 is ShellExecute's failure code.
- **The five `system` power commands (`power.rs`) deliberately take no path/target parameters**: `lock_workstation` (LockWorkStation) / `monitor_off` (PostMessage broadcast of SC_MONITORPOWER — **do not change to SendMessage**: a broadcast can hit a hung window and get dragged down synchronously, the same lesson as GetWindowTextW → SendMessageTimeoutW) / `sleep` (SetSuspendState, requires enabling SE_SHUTDOWN_NAME first — AdjustTokenPrivileges returning Ok does not prove the privilege was enabled; check GetLastError == ERROR_NOT_ALL_ASSIGNED) / `power_control` (ExitWindowsEx, **without EWX_FORCE** — apps with unsaved data may block, the user sees the system-level blocking screen, and a skin cannot bypass it to silently discard data) / `empty_recycle_bin` (SHEmptyRecycleBinW with flags=0 = the Explorer-style confirmation box + progress + sound — the final say over the destructive action stays with the user; SHQueryRecycleBinW checks emptiness first: already empty succeeds immediately without the box). **The `system` permission never provides a "launch an exe" channel** (open_external accepts only the URI whitelist plus this parameterless command set) — running programs belongs exclusively to `run_command` under `shell`; new `system` commands must not take executable-target parameters.
- **assetProtocol has been deleted wholesale**: tauri's assetProtocol scope allows by path prefix and can't block individual files inside a directory; it once exposed every skin's `settings.json` to all windows. Preview images now go straight out of the `skin://` protocol (on Windows `http://skin.localhost/<skin folder>/preview.<ext>` — take the **last two segments** of the preview image's absolute path to build the URL, see `src/js/api.js`), the same interception chain as skin resources (built-in settings.json interception and canonicalize protection), adding no new exposure surface. Do not re-enable assetProtocol.
- **There are now twelve permissions (wizard display in three tiers: high-risk red / medium-risk yellow / low-risk blue — the tier is display-only; enforcement stays a binary declared-or-not check)**: high — `shell` / `system` / `file_system`; medium — `registry` / `clipboard` / `mic` / `control`; low — `media` / `notify` / `sys_info` / `network` / `open_link`. **Permission-free baseline**: the 4 sandboxed skin-folder file commands, settings read/write of one's own schema, `skin_log` / `skin_console_log` / `skin_broadcast`, the control family's self-targeted arms, and the skin-callable bridge/self-targeted commands: the Ungated 2 (`start_skin_drag` / `start_skin_resize`) plus the SkinLabel 4 (`show_skin_context_menu` / `skin_set_menu_items` / `open_skin_devtools` / `skin_console_log` — identity is reverse-looked-up from the window label, self-target only). method propagation follows browser semantics (303, and 301/302 for non-GET/HEAD, switch to GET and drop the body; 307/308 resend the same method and body). `is_private_host` also gained inet_aton numeric-literal hardening: the pure function `parse_inet_aton` folds forms that `IpAddr::parse` rejects but OS resolvers treat as IPs (`2130706433` / `0x7f000001` / `127.1` / `0177.0.0.1`) back into IPv4 and runs them through the same segment checks (note: the current `url` crate's WHATWG host parser already pre-normalizes these forms to IPv4 — this function is defense-in-depth against parser-assumption changes, not the primary line); overflowing segments (e.g. 999.1.1.1) can't even pass WHATWG URL parsing, so they're handled as "parse failure = reject" (the residual of domain names resolving to internal networks stays outside this layer). **The v6 arm checks its own loopback/unspecified first, then folds via `to_ipv4()` into the v4 segment checks** — IPv4-mapped forms like `::ffff:127.0.0.1` actually reach the v4 target on dual-stack (re-review D-B), and `to_ipv4` folds `::1` into 0.0.0.1 (with the wrong order, loopback escapes; pinned by tests). **Request headers are filtered per hop by `headers_for_hop`**: on cross-origin hops (any of scheme/host/port changed) strip authorization / cookie / proxy-authorization, and when the body is dropped on the GET switch also strip content-length / content-type — ureq's auto-follow did this built-in, and the manual hop loop must maintain it or a skin's tokens leak to third-party hosts via 302 (re-review D-A). **Do not regress: do not turn ureq auto-follow back on** — a 302 hop once became a corridor into the internal network (audit H1).
- **Dual audio sources (`audio.rs`)**: `Source::Loopback` (render device + Capture init = loopback) and `Source::Mic` (capture device) share one capture-thread template and ring buffer, each holding its own static slot and its own lazy-start/idle-self-stop; when changing the pipeline, change both sources together. On desktops without a battery, `get_battery_info` returns `has_battery=false` (not an error); with no audio endpoint the corresponding commands reject and retry in 5 seconds.
- **Toast notifications' (`notify.rs`) unpackaged trio**: at startup `SetCurrentProcessExplicitAppUserModelID("Driftlet")` (lib.rs setup) + Start Menu `Driftlet.lnk` (IShellLink + IPropertyStore stamping `PKEY_AppUserModel_ID`, including `SetIconLocation`; rewritten as self-healing when the target **or the AUMID property** doesn't match, **done on a background thread at startup**, not waiting for the first notification) + `CreateToastNotifierWithId` with the same ID — **all three are indispensable**; on Win10, without the shortcut, Show succeeds but nothing is displayed. Two memory disciplines not to regress: the AUMID wide-char buffer is **deliberately leaked** (the property bag may lazily read it back; freeing it is use-after-free); in `create_shortcut`, **never CoUninitialize after CoInitializeEx** (propsys's shortcut handler corrupts the heap when the MTA apartment is torn down — measured 0xc0000374). The XML must escape the five characters; title/body truncated at 64/256 characters.

So `ensure_aumid_shortcut` must, one, carry `SetIconLocation`; two, refuse cargo test binaries (filename `driftlet_lib-*`) rewriting the shortcut (probes must not pollute the user's Start Menu entry); three, self-heal at startup.
- **The main thread's COM apartment belongs to tao**: no `CoInitializeEx(MTA)` may run on the main thread — tao's `OleInitialize` at window creation wants STA; if the main thread went MTA first it's `RPC_E_CHANGED_MODE` and a direct panic. All COM work goes to background threads (volume/media commands already run on the spawn_blocking path, not as sync commands; the shortcut self-heal in setup likewise spawns).

## Stability Conventions (Mutex / FFI Callbacks)

- **Global `std::sync::Mutex` poison recovery**: always `.lock().unwrap_or_else(|e| e.into_inner())` — after a panic on a lock-holding path the lock enters the poisoned state, and a bare `unwrap()` would make every other caller panic in a chain until the whole app locks up; `into_inner()` tolerates "state may be partially updated" and keeps serving, far better than total failure. New Mutexes follow the same pattern; do not write bare `.lock().unwrap()`.
- **Never hold a lock guard across a call that re-takes the same lock**: `std::sync::Mutex` is not re-entrant — calling `tray::rebuild_tray_menu` while holding the `state.config` guard (its `build_layouts_submenu` takes the config lock again) deadlocks the thread forever and kills all backend IPC (actual incident in the layouts feature: saving a layout froze the whole manager). The correct pattern is in `set_language`: scope config writes in a `{ }` block, drop the guard, then call the lock-taking external function. For any new "mutate config + trigger tray/other subsystem rebuild" path, check the callee's lock usage first.
- **Hotkey bookkeeping always uses the `Shortcut` Display-normalized string**: `tauri-plugin-global-shortcut`'s `Shortcut::to_string()` yields lowercase modifiers + keyboard-types Code names (e.g. `shift+control+alt+KeyD`), which is NOT equal to the config/user-input form `Ctrl+Shift+Alt+D`. When `dispatch_hotkey` compares the event shortcut's Display against bookkeeping, storing the raw config string in the bookkeeping means a permanent mismatch — the global hotkey dies silently (found in review, release-blocking). `REGISTERED_COMBO` and `SKIN_HOTKEYS` keys always store Display strings; any hotkey-string comparison normalizes both sides first. hotkey.rs has a round-trip unit test pinning this.
- **Per-skin visibility hotkeys = a resident registry with dispatch precedence over the global hotkey**: settings live in `skin_settings[id].hotkey`, rebuilt into `SKIN_HOTKEYS` (Display-normalized combo → skin id, see previous entry) from config at startup, after backup imports, and after selective-import merges; all hotkey events funnel through `dispatch_hotkey`, per-skin hits win over the global one, and pressing while the skin is unloaded is a silent no-op (no load/unload hooks). Triple conflict protection: duplicate of the global hotkey / duplicate of another skin's (i18n key `HotkeyConflict`) / held by another program (rolls back to the previous combo and does NOT write config — same discipline as `set_hotkey`). The bind/rebind/rollback write points all live in hotkey.rs — never keep a second bookkeeping on the command side.
- **FFI callbacks must `catch_unwind`**: entries called back into Rust directly by Windows (`skin_subclass_proc`, `EnumDisplayMonitors`, etc.) are wrapped in `catch_unwind(AssertUnwindSafe(..))` — a panic crossing the FFI boundary is undefined behavior (in practice, process termination); after catching, log and degrade to a default return value. New WNDPROC / enumeration callbacks follow the same pattern.

## Skin Packages (.dskin) and Skin Identity

- **Skin identity = the `id` field of `skin.json`** (kebab-case). Required when packaging for distribution; during folder scan, when missing, it falls back to a slug of the folder name (compat with old skins). Same id = same skin; scanning dedupes by id, later arrivals are warned about and skipped.
- **Locating a directory by skin must go through scan resolution first** (`find_skin_dir`); do not directly `skins_dir.join(skin_id)` — the id doesn't necessarily equal the folder name. `remove_skin` / `open_skin_folder` / `capture_skin_preview` have been changed to this; follow it for new commands of this kind too.
- **User data lives in two places, both preserved across update/reinstall/rollback**. Window config (`skin_settings[id]`) belongs by id in config.json, decoupled from the skin files; the user values of the "Skin Settings" 「皮肤设置」 page live in the skin folder's `settings.json`, taken out before a wholesale folder replacement and written back after copying (`install_package` in `package.rs` and `copy_example_skins` in `lib.rs` follow the same convention; user values take precedence over same-named files in the package; the six Isles skins ship inside the installer via bundle.resources with a first-install seeding step — see the dedicated section; demos/ is no longer synced, and examples/ syncs into the skins dir in development only). New items in a new schema go through defaults; old values with mismatched types are auto-fallen-back by `effective_settings`; leftover data of deleted setting items is harmlessly ignored. The user-side clearing entry = the config panel's "Reset Data" 「重置数据」 button → the `reset_skin_config` command deletes `skin_settings[id]` and deletes `settings.json` (window config and custom settings both fall back to skin.json defaults); loaded skins reload accordingly.
- **`settings.json` is user data and does not go into distribution packages**: `tools/pack-skin` excludes `settings.json` / `settings.json.bak` / `settings.json.tmp` when packing.
- Package extraction (`skin/package.rs`) must go through `enclosed_name` against zip-slip; the size cap is measured by **actual extracted bytes** (accumulated from `io::copy` return values, not trusting the zip header's declared uncompressed size — headers can be forged, and a zip bomb is exactly "declares small, extracts huge"), keeping the size/file-count caps (256MB / 1GB / 10000 — creators may bundle Chinese fonts and 4K assets, so 64/256/5000 was relaxed to this, mirrored on both sides; the pack side also checks the produced archive's size, never producing an uninstallable package); the temp directory is cleaned up by an RAII guard. The validation rules (parseable, legal id, entry exists) are **kept consistent** with the packing tool `tools/pack-skin` (the same `SkinManifest` deserialization, strongly-typed validation) — changing one side requires syncing the other.
- **Install = the staging rollback flow** (`install_package`): ① fully copy the extracted content to `skins/.staging-<id>`; ② rename the existing `<id>` to `.<id>.old`; ③ rename staging in (on failure, rename .old back); ④ restore `settings.json` from .old, then delete .old. Failure at any step leaves no "half-new half-old" directory, and the old version can always be rolled back. Skin scanning **skips directories starting with `.`** — staging / .old and stray dot-directories are never listed as skins. **TOCTOU closure (added in the audit)**: between the wizard's confirm page and the install, the package at the path can be swapped ("confirm A's permissions, install B's content") — `install_skin_package` verifies the actually-installed id matches the pre-install parsed id and rolls back by deleting the new directory on mismatch (residual: same id but swapped content can still drift permissions; the full fix would hash the inspected package and pin it through the confirm flow — not implemented). **Same-id-different-folder shadowing (added in the audit)**: scan dedup keeps the first folder alphabetically while packages land at `skins/<id>` — if a skin with the same id already exists at a folder whose name ≠ id, the install is refused with guidance to remove the old copy first.
- **Loader hardening** (`skin/loader.rs`): `skin.json` ≤1MB (hand-written or packed manifests are all small files; over the limit is anomalous); `entry` rejects `..` / `\` / `:` (against the entry pointing outside the skin directory or ADS); `id` blacklists Windows reserved device names (con / prn / aux / nul / com1-9 / lpt1-9 — system-reserved names can't form normal directories; judged by base name, forms with extensions like `con.txt` are likewise reserved by the system); the install/update staging directory copy (`copy_dir_recursive` in `package.rs`, not this file) **skips symlinks and junctions** (against pointing outside the skins directory; junctions are unmarked by is_symlink on Windows and detected via the reparse attribute bit) and limits depth to 32 levels (`MAX_COPY_DEPTH`); **window defaults are normalized at load** (added in the audit: width/height clamped to 1..10000, non-finite/out-of-range opacity falls back into [0.1,1.0], zoom via clamp_zoom, refresh_seconds ≤24h — `opacity:0 + always-on-top + a giant size` makes an invisible topmost click-eating full-screen window, and the wizard never shows window defaults, so load must enforce it).
- Updating a running skin: `unload_skin` first, then install, and **stay unloaded** after install (product decision: update/reinstall/rollback by default do not auto-resume running; the user loads explicitly; do not change back to auto load).
- The file picker only filters `.dskin`; `.zip` no longer appears in the user entry, to avoid confusion with ordinary archives.

## Double-Click Install (.dskin File Association)

- **File association = `bundle.fileAssociations` in `tauri.conf.json`**, written to the registry by the NSIS installer — only the installed build has the double-click entry; portable exe / dev have no double-click, but the install logic can be fully tested with a command-line argument: `npm run tauri dev -- -- "D:\path\x.dskin"`.
- **Cold/hot two entry paths, cannot be merged**:
  - Cold start: `dskin_arg(std::env::args_os().map(to_string_lossy))` (`args()` panics on non-UTF-8 args — a release build has no console, so that is a silent crash; skips argv[0], case-insensitive extension, the file must exist) → stored in `AppState.pending_package`, the main window `show()`s immediately, and after frontend startup it **actively pulls** with `take_pending_package_install` (`Mutex::take` consume-style, pops only once). **You cannot emit an event here** — the frontend listener isn't registered yet; emitting loses it.
  - Hot start: the `tauri-plugin-single-instance` callback (must stay registered **first** in the plugin list) → `tray::show_manager_window` + `emit("open-skin-package")`; the frontend listener is long ready.
  - Known race window: within the few hundred milliseconds after a cold start before the frontend is ready, a **second** double-click — that forwarded event may be lost (ends up showing the first package's wizard). Acceptable.
- **Install serialization = `AppState::install_lock` (tokio Mutex)**, wrapping the whole `install_skin_package`: repeated double-clicks + repeated clicks on "Install" 「安装」 would concurrently install the same skin, and `remove_dir_all` and copying would trample each other's directories. Must use `tauri::async_runtime::Mutex` (its guard is Send and can be held across the `.await` of reload) — std Mutex's guard is `!Send` and won't compile; and don't lock only the file-operation section either — unload/reload need the mutual exclusion too. Coverage: package install, skin removal, backup import/export, and the tray's "reload all" all take this lock. **Lock order = lifecycle_lock → install_lock → settings_lock**: `lifecycle_lock` (added in the audit) serializes load/unload/reload/reset and the skin_api lifecycle commands (the "check-exists → register" sequence is not atomic, and concurrent interleaving would fork registry vs loaded_skins state; impls stay lock-free — callers serialize: reload_all holds install_lock while calling impls, reset holds lifecycle, commands hold both, and the skin context menu holds both inside its spawn closure (pre-audit-M3 the menu path called the lock-free impls directly and could race hot-reload/manager loads) — no nested ABBA): the directory-replace sections (install/import) additionally hold `settings_lock`, serializing against settings writes from `set_skin_custom_setting`/`skin_set_setting` (a write landing in a just-replaced old directory would be lost); settings commands never take install_lock, so there is no reverse path.
- **.dskin file icon = `src-tauri/icons/dskin.ico`** (16–256, 10 frames total, scaled from `icon/dskin-icon.png`, packed via `tools/make-ico.cjs`). tauri doesn't support `fileAssociations.icon`; the icon is applied by the installer overriding the default exe icon: NSIS goes through `NSIS_HOOK_POSTINSTALL` in `src-tauri/windows/installer-hooks.nsh` to rewrite the ProgID's `DefaultIcon`; the ico itself is put in the install directory root via `bundle.resources`. **The ProgID is strongly coupled to the config**: the key name = `fileAssociations.name` (currently "Driftlet Skin Package") — changing name requires syncing the hook, or the icon silently stops working. Uninstall needs no registry cleanup (NSIS deletes the whole ProgID key). **The icon takes effect immediately**: the tauri template never calls `SHChangeNotify` anywhere; the hook adds one `UPDATEFILEASSOC` after install and one after uninstall (`SHCNE_ASSOCCHANGED`, provided by the template-bundled `FileAssociation.nsh` — do not delete) — without it Explorer keeps showing the old icon until the cache is manually refreshed. (An MSI was previously produced as well: the icon went through the `windows/dskin-icon.wxs` fragment, language differentiated per package; now only NSIS is built — `targets: ["nsis"]`, the wxs is deleted, recovering it requires digging it out of git history.)
- **The installer language automatically follows the system** (NSIS single package, dual language): the `nsis.languages` order is `["English", "SimpChinese"]` — NSIS automatically matches the system UI language at runtime (probe-verified, unrelated to whether a selection box pops up), falling back to the **first** array element on no match — so English must come first: Chinese systems → SimpChinese, everything else → English; reverse the order and non-Chinese systems would see a Chinese installer. The hook writes `$LANGUAGE` to `HKCU\${MANUPRODUCTKEY}\Installer Language` at POSTINSTALL (the same behavior as `MUI_LANGDLL_DISPLAY`) — without it, in dual-language, the uninstaller's `MUI_UNGETLANGUAGE` finds no record and pops a language selection box. **The app's first-launch language is synced with the installer**: `default_language()` (`skin/types.rs`) uses `GetUserDefaultUILanguage` to judge a Chinese environment (primary language ID 0x04) → `zh-CN`, otherwise `en` — the same judgement rule as the installer, so the install language is the first-launch language; it only takes effect when config.json lacks the `language` field (first launch); existing configs are unaffected.
- **Uninstall data cleanup = the hook POSTUNINSTALL deletes everything, no checkbox**: app data is placed **next to the exe** per `resolve_portable_dir` (writable install location; protected directories like Program Files fall back to `%APPDATA%`), the updater's download dir sits at `$INSTDIR\update` (`Driftlet-update-setup.exe` + version marker + `.part` segments), and WebView2 data is in `%LOCALAPPDATA%` — the template itself only deletes the files it installed and does only a non-recursive RMDir on `$INSTDIR` (which fails while ANYTHING remains inside, leaving the whole install directory behind); all of these are beyond its reach. On non-update uninstalls the hook **unconditionally** backfills deletion: `RMDir /r /REBOOTOK "$INSTDIR"` **recursively wipes the whole install root** (incident basis: it used to delete only config/skins plus a non-recursive retry of the root, so a downloaded update package left in `update/` made the root removal fail and orphaned the entire install directory; the policy is now "the install directory is emptied, period" — files the user placed there are removed too, no longer preserved, and /REBOOTOK sweeps up anything still locked at uninstall time) + `%APPDATA%` / `%LOCALAPPDATA%\<bundle id>` + the `${MANUPRODUCTKEY}` registry (including the `Installer Language` written at install time). **The `${If} $UpdateMode <> 1` guard must never be removed** — an update install runs the old uninstaller first; without it every update would wipe the user's config and skins (and in update mode the very installer being run lives in `$INSTDIR\update`, so a recursive root wipe would delete the running executable itself). **The "delete app data" 「删除应用数据」 checkbox has been removed**: the original template creates it unconditionally in `un.ConfirmShow` (unchecked by default, the whole page skipped in silent/passive mode, and it only covered `%APPDATA%`), with no config switch at all (tauri-utils 2.9.3 has no such field), and a hook file can't pre-define it at compile time either (the template has no `!ifdef` guard; ## Layout Backup (Export / Import)

- **Import extracts to a temp dir first and only touches the live dirs after every check passes** (the same size/entry-count/zip-slip defenses as skin packages; `config/config.json` must be present, and the manifest `driftlet-backup.json`'s `format` must be 1), then does a **staged replace**: `config` / `skins` are renamed aside to `*.import-old`, and any copy failure deletes the partials and renames them back — a failed import must never leave a half-replaced state (`backup.rs::replace_data_dirs`, rollback paths covered by unit tests). **Import is two-phase** (post-re-review A-M2): `inspect_backup` (pick the package → extract + validate → return the skin list with permission declarations and the backup's host version) → a frontend confirm dialog shows the skin list + permission chips (same perms.js conventions, with a warning line when high-risk declarations are present) → `import_config(path)` executes only after confirmation — backup import no longer bypasses the permission display the .dskin wizard provides.
- **Startup rollback for the import crash window**: `.import-old` existing = the last import was interrupted during the in-place/finalization phase (the success path deletes them) — the target directory can now be in one of three states (missing / half-written / intact), and in **all three** the old copy is renamed back (under an intact copy the user just re-imports; under a half-written one this is the only intact data). **Two do-not-regress rules** (audit A-H1, once caused silent data loss): ① the rollback must run **before** `resolve_portable_dir` — its writability probe creates directories, erasing the "directory missing" scene into "both exist"; ② never infer success from "both exist" (a mid-way crash is exactly the both-exist case). lib.rs setup runs the rollback once for each of the two candidate locations, portable and %APPDATA% (the leftover only ever sits where the app last actually ran).
- **Every loaded skin must be unloaded before the swap** (WebView2 locks the folders; on Windows the rename would fail), and `install_lock` is held to exclude concurrent package installs.
- **The post-import runtime rebuild checklist** (missing one item = state drift): reload config + `prune_stale_entries` + replace the in-memory mirror, language mirror + rebuild the tray menu, sync the autolaunch plugin from `config.autostart`, re-register the global hotkey via `hotkey::reregister_from_config` (**never `register_from_config`** — it doesn't unregister the old registration, which still holds the combo after a wholesale config swap, so registration must fail and would falsely toast "hotkey taken"), and `load_skin_impl` each id in `loaded_skins`; the frontend then does a full `location.reload()` (language/theme/list/config caches rebuilt in one shot — do not replace with piecemeal refreshing).
- **Export-side defenses (added in the audit)**: the destination must not be inside config/ or skins/ (otherwise the zip swallows the very file being written — self-inclusion, runaway size; checked via canonicalized parent); **write to a temp file then rename into place** (no half-written zips on failure); junctions/reparse points are not followed (unmarked by is_symlink on Windows — detected via the attribute bit; a cyclic junction would recurse forever, and an outbound junction would leak non-skins content into the backup); entry/byte limits use the backup side's own caps (5000 entries / 256MB — the package caps were relaxed after this entry was written, so the backup side no longer shares the import side's values); `.staging-*` / `*.old` / `*.import-old` staging leftovers are skipped.
- **Selective import = per-skin staged replacement + config union (merge mode)**: after checking skins in the review list, `import_config(skin_ids)` — each selected skin goes through the three-phase replace (`.<folder>.old` aside → copy in → clean up, restored one by one on failure; **config untouched until every directory is in place**); **pre-flight check before any rename/copy** — if the fallback landing spot collides with an existing folder carrying a different id, the whole import errors out (it once silently destroyed an unselected skin). Config merges only the selected skins' `skin_settings` / `loaded_skins` plus layouts (`merge_backup_layouts` unions by id, backup wins; layouts referencing unimported skins survive and are flagged via `skipped` at apply time); language / theme / autostart / hotkeys / groups stay untouched (selected skins land in "ungrouped"); the skin-hotkey registry is rebuilt from the merge result (`sync_skin_hotkeys_from_config` — was once missed, the merged per-skin hotkeys only took effect after a restart). **Crash recovery for per-folder staging**: `.staging-*` / `.<folder>.old` (shared by selective import / sync-from-source / package install) are cleaned/restored at startup by `package::recover_interrupted_folder_ops` (old copy wins; a half-written target is deleted even when the target exists), invoked at the same point as the `.import-old` wholesale rollback (both the portable and %APPDATA% layouts).

## Update Check and Auto-Download

- **Check → dialog appears immediately + background multi-source download → "Install now" once done**: `check_update` (queries the latest GitHub release, carrying the installer URL as `installer_url`, the official hash as `installer_sha256`, and an in-place flag as `installer_ready`) raises the window and shows the dialog **immediately** upon finding a new version (the download runs in the background — the prompt no longer waits for it); `download_installer` then races **multiple sources** — the direct GitHub link and acceleration mirrors start simultaneously (scoped threads), and the first source to **pass the SHA-256 check** claims the win (`AtomicUsize` compare_exchange; the rest are stopped) — only if every source fails does the primary button degrade to "Go to download page". Progress is emitted via `update-download-progress` events (throttled to 500 ms); the frontend progress bar tracks the leading source. **No re-download when already in place**: when `installer_ready` (marker version matches + file hash matches the marker) is true, the frontend skips the download and goes straight to "Install now" (restarting after "Later" or a completed download no longer re-downloads the whole installer).
- **Trust model (do not regress)**: the version number and the official SHA-256 come **only from api.github.com** — the hash is parsed from a `SHA256: <hex>` line in the release notes (mandated by the release process: exactly 64 hex chars bounded by non-hex on a line containing "sha256"; 40-char commit SHAs and all-digit runs are rejected); mirror sources enter the candidate list **only when the official hash exists** (`source_urls` gate), and content that fails the hash is vetoed (fail-closed); old releases without a hash download directly from GitHub only (its TLS is the trust anchor). If the version+hash were ever taken from a third-party mirror, that mirror could fake the version, the hash, and the installer all at once — the entire update chain would be MITM-able. Never.
- **Segmented parallelism**: within one source, the file is fetched in parallel Range segments (8 by default) — a single connection to GitHub is often throttled to ~10 KB/s in mainland China, and segmentation buys roughly an order of magnitude; the first request doubles as a probe (Range for the first segment, total size from content-range): 206 → preallocate + offset writes, 200 = Range ignored (some mirrors don't support it) → single-stream save. Redirects are followed manually (`redirects(0)`, re-sending Range on every hop, max 5 — same precedent as skin_api/http_request). Timeouts per request: 60 s overall / 10 s connect / 15 s read stall (the last two live on the agent — ureq 2's per-request API only exposes the overall timeout).
- **Install**: `install_update` (require_manager) launches the installer from the fixed directory (only the one we just downloaded — arbitrary paths are not accepted) and exits the whole app via `tray::graceful_exit` (NSIS's CheckIfAppIsRunning waits for this process to exit before it can overwrite the exe).
- **Three gates against junk accumulation**: the fixed filename overwrites + the per-source `.s<i>.part` segment files cleared at start/on failure + **startup cleanup** (`cleanup_downloaded_installer`: current version ≥ marker version = installed → delete the installer and marker; a newer marker version = not installed yet, keep it for the prompt).
- The download URL is pinned to the public repo's release download domain (the `https://github.com/xiaochengzina/Driftlet/releases/download/` prefix check — only direct links returned by the GitHub API assets are accepted; mirrors are derived by prefix-rewriting this URL and cannot steer the download anywhere outside the repo).
- **The update directory joins the `file_system` mutation-forbidden roots + installer hash verification (post-audit H2)**: `ensure_mutable_any_path` grew its forbidden roots from two to four — + `update_dir` (derived via `crate::update::update_dir(config_dir)`, `<data root>/update`) + the exe's own directory (`current_exe`'s parent; in the portable layout it's the parent of the first three roots, redundant but explicit, covering Driftlet.exe itself / WebView2Loader.dll / the uninstaller; in the non-portable fallback layout the four roots are disjoint and each applies independently); reads/lists stay unrestricted. `download_installer` computes SHA-256 while streaming and writes it into downloaded-version.json (`{"version","sha256"}`); before launch, `install_update` goes through `verified_installer`, a three-way check — the marker exists and is complete (an old-download marker without sha256 fails closed) / the marker version is newer than the running version (is_newer) / the installer file's SHA-256 matches the marker (case-insensitive) — missing any one rejects with an error steering to "re-download"; a missing installer still reports "installer not downloaded yet". **Do not regress: "Install now" is a trusted host action — the installer the host executes must prove it is the one the host itself downloaded** (the hash is an absolute veto, regardless of the overwrite route) — host trust boundary: every place where the host consumes skin-influenceable data with elevated trust (executing an installer / rendering into the manager DOM / eval injection) belongs in this list.

## Developer Mode (formerly Skin Hot Reload)

- **Debug builds only** (gated in setup behind `cfg!(debug_assertions)`): a single watcher recursively watches the whole skins directory, debounces per skin folder for 300 ms, and reuses `reload_skin_impl`; release builds have no watcher. **Master switch = `config.hot_reload` (default off) + `AppState.hot_reload_enabled`**: toggled from the settings page (`set_hot_reload` flips the flag instantly); the watcher stays resident and the flag only gates the reload action. The same toggle (labeled "Developer mode" in Settings) also gates the skin-window DevTools unlock — the bridge captures F12 / Ctrl+Shift+I keydowns, the `open_skin_devtools` command verifies the skin-window identity and the runtime flag, then calls `OpenDevToolsWindow`; effective in all builds, no debug gate. **Skin-API self-writes with arbitrary names do not trigger self-reloads** — `note_self_write` registers the normalized path, and the watcher skips hits on unexpired registrations (TTL 5s); **a hit is not consumed**: one `fs::write` produces multiple notify events, and consume-once semantics only blocked the first (this is exactly the toolbox todo.json scenario); expiry cleanup happens in the registrar's retain. The event channel is bounded (4096, dropping on full under storms — a dev-convenience path whose debounce semantics tolerate coalescing); after an error event, the watch is rebuilt once the root dir exists again (the watch handle used to die silently when a backup import renamed+deleted skins/).
- **Self-write filtering is the load-bearing part**: `settings.json` (plus `.tmp` / `.bak`), `preview.png`, and `.staging-*` / `*.old` never trigger a reload, or the loop never ends — **any new app self-write into skin folders must be added to `hotreload.rs`'s `SELF_WRITE_NAMES` / segment filter**.
- Reloads must be spawned (`tauri::async_runtime::spawn(reload_skin_impl(...))`): the old window's label is freed only once the event loop processes the close, so synchronous destroy+create on one thread hits duplicate labels (same lesson as `tray::reload_all_skins`).

- The six Isles skins (isles-countdown/calendar/clock/monitor/weather/timer) ship inside the installer via tauri `bundle.resources` (sources live in the repo `examples/`; they land in `<install>/bundled-skins/`; the NSIS template expands directories into file lists via resources_dirs + resources, and the parent-relative `../examples/` paths are canonicalized by tauri-build).

## The skin:// Protocol

Skin pages and resources are loaded via the `skin://` custom protocol (handler: `skin/protocol.rs`). Its job is not restricting the network, but four control points:

- **Bridge injection**: baking `__DESK_PP__` when serving HTML (setting values / opacity / lock / resizable / UI language / host `hostVersion` / context-menu takeover / edge resize hot zones), plus the recommended alias `window.driftlet` (same object; `__DESK_PP__` is the legacy name, kept for compatibility) — zero-race delivery; **do not** change back to post-creation eval (see "Position Lock", "Skin Custom Settings"). `hostVersion` bakes `CARGO_PKG_VERSION` for runtime feature detection; the optional `min_host_version` in skin.json complements it — `inspect_package` reuses `update::is_newer`'s numeric-segment comparison and passes `requires_host_version` to the install wizard when the host is too old (a warning, not a block). Runtime language switches go through `set_language`'s eval (updating `__DESK_PP__.language` and dispatching the `desk-language-changed` event — the page is already loaded, no race; same convention as runtime lock toggling). Runtime theme switches use the same pattern via `set_theme` (`__DESK_PP__.theme` + `desk-theme-changed`); the baked value is resolved from `auto` into a concrete light/dark by `commands::current_theme` based on the local hour (light 06–18, same rule as the frontend's timeBasedTheme). **The inter-skin event bus = `skin_broadcast` (permission-free)**: evals `desk-skin-message` to every loaded skin window (detail = { channel, from, payload }); the sender also receives its own broadcast (filter by `from`); channel 1–64 chars, payload ≤16KB, delivers DOM events only and touches no host state. **`</` escaping of baked strings (re-review B-F1)**: serde_json does not escape `/`, and a `"</script>"` sequence closes the bridge's injected `<script>` early — `baked_settings_json` and `bridge_script`'s language/theme/hostVersion all pass through `</`→`<\/` escaping; and `load_config` normalizes the `language` field via `i18n::normalize` (the load path used to accept a free-form string with zero validation — a hand-edited or backup-imported config.json was a script-injection vector; now double-gated).
- **User data isolation**: `settings.json` (including `.bak` / `.tmp`) always 404s; skin A can't get skin B's setting values. The interception is **double**: once by URL path filename before normalization, and once more by the real `file_name` after canonicalize — Windows 8.3 short names (`SETTIN~1.JSO`) can bypass the pre-normalization string match, and canonicalize restores them to long names; any path component containing `:` is rejected (against ADS `skin.json::$DATA` — an alternate data stream is the same file as its body; same rule as `skin_api/fs.rs`).
- **Path sandbox**: canonicalize + prefix check; skins can only read files inside `skins_dir`; it also masks the path difference between dev (repo `skins/`) and prod (install directory).
- **The `__fs__` reserved endpoint (arbitrary-path serving, `file_system` gate)**: `http://skin.localhost/__fs__?path=<percent-encoded absolute path>` lets a page URL-reference files outside the skin directory (display-type references like images/videos without a JS memory hop; the base64 command channel stays for data processing). Skin ids only allow lowercase letters/digits/hyphens, so they **can never collide with `__fs__`**. Identity must come from `UriSchemeContext::webview_label()` (the trusted IPC channel) — **Referer/Origin are page-forgeable and must never be used** (all skins share one origin, so skin A could forge skin B's Referer to borrow its permission); the target must be an existing regular file at an absolute path (`parse_fs_query`, pinned by tests); **UNC paths are always rejected** (`\\`/`//` prefix plus `Prefix::UNC/VerbatimUNC` component double-check — the `is_file()` probe would send an NTLMv2 challenge response to an attacker's SMB server, a hash-leak surface; the declared permission means *local* arbitrary paths, so outbound auth is out of bounds. Gate added in the 2026-09-08 review; it was missing before).
- **Atomic delivery of window state**: the entry URL query (`opacity` / `locked` / `resizable`) takes effect with the document's first frame.
- **Web skins (entry is an http(s) URL)**: the window loads the site page directly via `WebviewUrl::External`, bypassing the skin:// protocol and the bridge injection — no drag region / right-click menu / command channel on the page (**tauri's remote-origin guard is the backstop**: custom-command calls from remote origins are rejected, see the non-local origin check in webview/mod.rs); initial opacity lands via initialization_script (a post-creation eval would race and lose it); cookies/login state persist in the WebView2 user-data folder (no re-login across restarts); `window.refresh_seconds` spawns a plain thread that `location.reload()`s on the interval (**the closure holds the window handle from creation time** — after unload/reload the old window is destroyed and eval errors out, so the thread exits naturally; the old registry lookup would hit the reloaded new window and let stale threads accumulate). loader/package/pack-skin exempt URL entries from the entry-name validation (no local file to check).

**URL rewriting (Windows)**: WebView2 doesn't support subresource loading for non-standard protocols; wry rewrites the navigation URL `skin://localhost/...` to `http://skin.localhost/...`, then on the request side intercepts by the `http://skin.*` filter and rewrites it back for the protocol handler (wry `custom_protocol_workaround.rs`) — requests never leave the process, no DNS/TCP.

**Network reality**: a skin page is a full Chromium. Only `http://skin.*` is intercepted; external http/https requests go straight to the real network; skin page responses have **no CSP** (tauri.conf's CSP only applies to app-protocol pages; custom-protocol responses are hand-built by the handler and carry only Content-Type). Cross-origin `fetch`/`XHR` are constrained by CORS (the target server must allow it); `<img>`/`<script>` tag-style loads and WebSocket are not subject to CORS. **A third-party skin = local code that can access the network** — treat the install trust model accordingly.

**Boundary (known exposure surface)**: all skins share the single origin `http://skin.localhost` — the same-origin policy doesn't isolate skins; skin A can request skin B's ordinary resource files (only `settings.json` is blocked). If skin networking is ever to be restricted, the landing point is still this layer: add a CSP header to protocol responses, or register a `*://*` filter for whitelisting.

## Tray Icon

- **Per-size PNGs, never a multi-size .ico**: `tray.rs` embeds 7 tray artwork sizes (16–48, rendered by `tools/make-tray-icon.py` from grid-snapped parametric geometry, not downscaled from a master) and picks the exact size via `SM_CXSMICON` on Windows. Tauri's `Image::from_bytes` decodes only a single ico frame, so a multi-size .ico buys nothing and lets Windows rescale one bitmap to 20/24px instead.
- **`src-tauri/vendor/tray-icon` is a patched vendored dependency** (wired in via `[patch.crates-io]` in `Cargo.toml`) — **the patch must survive any upgrade/replacement**: upstream (0.24.1/0.24.2) `into_windows_icon()` calls `CreateIcon`, passing a **1-byte-per-pixel** buffer where the AND-mask parameter expects a **1bpp monochrome bitmap** (80 bytes for a 20px icon; 400 passed), so the resulting HICON carries a garbage mask. `DrawIconEx` uses the alpha channel for 32bpp icons and ignores the mask — which is why the tray looks fine — but **mask-aware consumers** (Task Manager, which uses the tray icon for processes with no visible window, and the Win11 tray drag image) render horizontal-striped garbage. The patch builds a proper 1bpp mask (rows padded to 16 bits) + 32bpp premultiplied DIB via `CreateIconIndirect`. (The probe `tools/win32-probes/probe_icon_render.py` reproduces both render paths.)
- **Second patch in the same crate** (the NOTE(driftlet) in `mod.rs`): the `NIM_DELETE` on the `TaskbarCreated` handling path now uses the quiet variant — after an explorer restart the old icon already vanished with the dead taskbar, so the deletion **inevitably fails**, and upstream's unconditional `eprintln!` prints a spurious "Error removing system tray icon" to the console on every explorer restart (the tray icon itself recovers normally via the subsequent `NIM_ADD`; pure log noise).
- **Window icons must stay disabled**: tao (0.35.x) `RgbaIcon::into_windows_icon()` is the same buggy code as the tray-icon issue above, and tauri-codegen bakes `icons/icon.ico` as `default_window_icon`, applied to every window (`WindowManager::prepare_window`) — with a window visible, Task Manager/Alt+Tab would pick up exactly that garbage-mask HICON. So `lib.rs` explicitly calls `context.set_default_window_icon(None)` at `run()`; window icons are instead set by `apply_window_icon()` — `CreateIconFromResourceEx` on the multi-size icon.ico + `WM_SETICON` (called for both the manager and the log window): the exe-resource fallback does **not** cover the taskbar button / hover preview / Alt+Tab (observed the generic default icon there), so it cannot be relied on. Do **not** call `.icon()`/`set_icon()` on windows or remove this suppression.

## The Log Window and app_log

- **Backend buffer always records; the frontend pulls on demand**: the ring buffer in `src-tauri/src/app_log.rs` (`VecDeque<LogEntry>`, cap 1000, oldest evicted when full, each message truncated to 1000 chars, every entry carrying a monotonic `seq` and an epoch-ms timestamp) records from startup, but `push` only emits `emit_to("log", "app-log-added")` while a window labeled `"log"` exists (`get_webview_window("log")` is the existence check) — "no frontend memory cost while the log window is closed" lives on that single line; do not change it to an unconditional `emit`. **Event batching (added in the audit)**: a high-frequency `skin_log` caller would storm the log window with per-entry IPC events — `push` now buffers entries and flushes them about every 100ms as a batch (the payload changed from a single entry to an array, same event name; the frontend accepts both shapes).
- **Capture scope = a custom `log`-crate logger**: `init_logger()` (replacing the former `env_logger`) only accepts records whose target starts with `driftlet_lib` (wry/tao and other third-party crates are filtered out) and `eprintln!`s every accepted record to stderr for dev-time visibility — but **only Warn and above is `push`ed into the log buffer**: Info-level operation noise (startup/tray/hotkey/load/unload/setting changes) proved worthless to users (things you already know because you just did them), so it stays stderr-only. Hook points keep writing `log::info!/warn!/error!` — the level decides whether an entry reaches the window; process chatter uses `log::debug!` (below the `set_max_level(Info)` gate, never even reaches stderr — the former "Creating skin window…" process lines were demoted for exactly this).
- **Operation-event hook points** (Info level, stderr only — never reaches the window): manager started (end of setup) / destroy-on-close and no-tray exit (the main window's `CloseRequested` branches) / app exit (`graceful_exit`'s existing line), global hotkey triggered (inside the hotkey handler — do **not** move it into `focus::toggle`, the tray menu's focus-mode toggle calls the same function and would be misrecorded), skin loaded/unloaded (the `load_skin_impl`/`unload_skin_impl` convergence points — reloads and config resets all pass through; placement switches no longer converge here since the in-place flip, and are logged at the single point in `set_skin_placement`), skin setting changed (one line on each side — manager `set_skin_custom_setting` and skin `skin_set_setting` — **key only, never the value**: password-type setting values must not appear even on stderr).
- **Skin-side channels = the bridge's automatic console capture + the explicit `skin_log`**: `inject_bridge`'s console hook wraps `console.log/info/debug/warn/error` (calls the original first, then forwards) and listens for `error` (capture phase — catches both uncaught script exceptions and img/script/link resource load failures, which don't bubble), `unhandledrejection`, and `securitypolicyviolation`. Flood protection must live bridge-side (IPC flooding is the real cost): a queue flushes every 250 ms, one invoke per flush, consecutive duplicates collapse into `(xN)`, cap 30 entries per flush with a hard in-queue cap of 300 (a tight loop logging distinct messages must not grow memory unboundedly), each message pre-truncated to 1200 chars; overflow becomes a synthesized "flood guard" warn entry. Hook-internal errors are swallowed silently (never call console inside the hook — recursion); the injected script stays pure ASCII (we don't control the skin page's charset). The batch command `skin_console_log` takes its identity from the window label (same as `show_skin_context_menu`) and deliberately does **not** go through `caller_skin` (which rescans the skins directory on every call — unacceptable on a sustained high-frequency channel), with a ≤60-entries-per-batch backstop; the explicit `skin_log` remains (identity via `caller_skin`). Both record the source as `skin:<id>` and need no permission declaration (messages never leave the local in-memory buffer).
- **The source filter is a dynamic per-skin list**: All / Backend / one option per skin, rebuilt as entries appear; a selected skin keeps its option even with no entries, and clearing the log doesn't touch the filter selection.
- **The log window (label `"log"`)**: created by `open_log_window` from the Settings → Advanced tab (on success the settings page closes itself; `require_manager`; if already open it show+unminimize+focuses instead of stacking), the second entry of the multi-page build (`log.html` via vite `rollupOptions.input`), the same titlebar-less native frame as the manager window (`decorations(false)` + `apply_native_frame` — see the "manager/log window frame" entry; this command runs on a spawn_blocking worker, so the subclass is installed via `run_on_main_thread` — SetWindowSubclass fails cross-thread), and `spawn_webview_hardening_retry` disables the context menu / accelerator keys here too. **`open_log_window` must stay an async command building the window inside `spawn_blocking`** (the same path as `load_skin_impl`): sync commands run on the main thread inside the WebView2 IPC callback context, and calling `build()` right there deadlocks the main thread inside wry's window-creation path (reproduced live: the main thread enters `build()` and never returns, the whole app goes unresponsive) — any "frontend click creates a window" command must not be sync. **Theme and language are baked into the URL query** (`log.html?theme=…&lang=…`, the same pattern as opacity in skin windows) — the log window is not the manager window, so `get_app_config`'s `require_manager` would reject it; the optional `initI18n(forceLang)` parameter exists for this; runtime language/theme switches are pushed by `set_language`/`set_theme` via `emit_to("log", "app-log-language"/"app-log-theme")` (the frontend re-runs `initI18n`/`applyTheme` and re-renders) — the baked query only covers window creation. On open, the frontend **listens first, then invokes `get_app_log`** (the reverse order would lose entries arriving in the window between the two), merges by `seq`, then switches to pure incremental appends; `get_app_log`/`clear_app_log` are gated by `require_log_window` on the label — the buffer contains internal paths and other skins' messages and must not be readable by skins (the injected bridge is a raw passthrough and custom commands have no ACL, the same reason `require_manager` exists).

## The comctl32 v6 Manifest for cargo test (build.rs)

- **Symptom**: `cargo test`'s test exe fails at launch with `0xc0000139 STATUS_ENTRYPOINT_NOT_FOUND` (the process never reaches main). Root cause: the vendored tauri-runtime-wry message box statically imports `TaskDialogIndirect` (a comctl32 v6 export), but tauri_build's winres manifest reaches only bins via `rustc-link-arg-bins` — the lib unit-test binary has no manifest, so without a v6 activation context `comctl32.dll` resolves to System32's v5 (which lacks the export) and binding fails at load time. `rustc-link-arg-tests` can't help: it only applies to `tests/` integration targets, this crate has none, and using it errors out outright.
- **Solution (do not dismantle)**: `build.rs` calls `try_build(Attributes::new().windows_attributes(WindowsAttributes::new_without_app_manifest()))` to disable tauri's bins-only manifest, then `embed_resource::compile_for_everything` embeds `windows/app-manifest.rc` (the same comctl32 v6 dependency as tauri's default windows-app-manifest.xml) into **all** link targets — bins and lib test binaries get exactly one manifest each (using compile_for_everything on top of tauri's default manifest collides with CVT1100 "duplicate resource"). Diagnostic tool: `tools/win32-probes/check_imports.py` (static PE import-table check, requires pefile).

## Behavioral Constraints

- "Always on top" 「窗口置顶」 and "pin to desktop" 「贴在桌面」 are either-or, exactly one must be active: turning one on auto-turns the other off; turning the current mode off switches to the other; default is "pin to desktop". At config load, legacy "both on / both off" states are normalized to "pin to desktop".
- Clicking the main window's X button = **destroy the window** (with the tray present: `prevent_close` + `destroy()`; rebuilt when summoned back from the tray), not quit; the tray's "Exit" 「退出」 is the real quit.
- **Alt+F4 on a skin window = hide, not close**: Alt+F4 is a system-level window message (WM_CLOSE) that neither the JS layer nor the WebView2 accelerator-key switch can touch; tao turns it into `CloseRequested`. A forced system close cannot be defied, but WM_CLOSE is only a "request" — the application layer is entitled to interpret it as hide. The skin window's `on_window_event` at creation (`window/factory.rs`) has a new `CloseRequested` branch: an unregistered close request → `api.prevent_close()` + `window.hide()` + `crate::hotkey::sync_tray_toggle_item()` to sync the tray checked item; recall reuses the existing global hotkey (default Ctrl+Shift+Alt+D, stateless "hide all if any visible, show all if all hidden" semantics) and the tray checked item. **Programmatic closes must register in `INTENTIONAL_CLOSES`**: unload/reload/exit (all converging into `close_skin_window_nowait`) register the label into the `INTENTIONAL_CLOSES` static set (factory.rs) before `window.close()`, and the event handler consumes the registration to let it through; if `close()` fails the registration is revoked, so a leftover entry can't wrongly let through the next user close of the same label; `create_skin_window` also defensively removes any leftover entry for its label at creation (extreme case: the window was destroyed externally after `close()` was queued but before `CloseRequested` was processed). Why the discrimination must exist: in the vendored tauri-runtime-wry, `close()` and a user's Alt+F4 both go through `on_close_requested` (`WindowMessage::Close` and `TaoWindowEvent::CloseRequested` converge), and `CloseRequested` itself carries no close reason. The `hwnd_dead` branch goes through `destroy()`, which doesn't trigger `CloseRequested`, so it needs no registration. The manager window's Alt+F4 is covered by the existing "close = hide to tray" interception and is unchanged.
- **The manager's "Hidden" 「已隐藏」 state = real window visibility, not hotkey bookkeeping**: the `hidden` field on `SkinInfo`/`SkinDetail` is computed live in `list_skins`/`get_skin_detail` (loaded AND `is_visible()` false — tao's is_visible is IsWindowVisible), so every hide path (global hotkey toggle, tray check item, Alt+F4 downgrade-to-hide) is reflected in real state. The frontend refresh trigger = the `skins-visibility-changed` event, emitted from `hotkey::sync_tray_toggle_item` — the existing funnel for all visibility changes (tray check sync) that all three paths pass through — **and load/reload also pass through the funnel at the end** (after a global hide-all, a reload/load would unconditionally show the new window, so the tray checkmark and badge resync from real state immediately); never compute hidden state in the frontend from hotkey presses (the tray/Alt+F4 paths would be missed). Badge tiers: `hidden` (yellow, `--warning*` tokens) / `loaded` (green) / `unloaded` (gray) — the list cards and the config-page header share the same derivation.
- Tray left-click = show/hide the manager, right-click = menu; while the manager window is shown it's visible in the taskbar/Alt+Tab (minimize restores normally); when hidden its taskbar button disappears with it; skin windows keep `skip_taskbar(true)` and never enter the taskbar.
- Skin resources are uniformly loaded through the `skin://` custom protocol (responsibilities and boundaries in "The skin:// Protocol"). Subresource references inside skin HTML **can only use relative paths or `http://skin.localhost/<skin folder name>/<path>`** (the first segment is the on-disk folder name, not necessarily the skin id — folder-drop installs can make the two differ) — on Windows, WebView2 doesn't support subresource loading for non-standard protocols; writing `skin://` directly errors `ERR_UNKNOWN_URL_SCHEME` (styles/scripts silently fail to load).
- Theme variables only hang on `:root[data-theme="dark"]` (light is the default theme, variables directly on `:root`): the theme option buttons themselves carry the `data-theme` attribute (for JS to read), so a bare `[data-theme="dark"]` selector would apply the dark variables to those buttons — the same kind of accident once happened on the light tile (in dark mode the "Light" 「浅色」 button's black text was invisible at rest, turning white-background on hover); if the default theme flips, the direction reverses and the constraint applies the same way.
- Info toasts uniformly go through the `src/js/toast.js` singleton (a new toast replaces the old one, fading out upward then removed); do not add more showToast implementations that each `appendChild` — rapid consecutive operations would stack toasts.
- After the manager window is hidden → re-shown, buttons keep a stale :hover style: while the window is hidden WebView2 receives no mouseleave, and after re-showing it recomputes hover from the "last known cursor position" (still sitting on the button just clicked). Synthesized events can't clear it (not trusted input); only a real pointermove updates its cursor position — so all `:hover` rules on interactive elements are gated by `body.hover-ok` (20+ rules covered; `app.js` removes it on hide/blur and restores it on the first real pointermove), and buttons also `blur()` on click to avoid a stale :focus-visible outline.
- The manager/log window frame = **native frame without a title bar**: after a frameless build (`decorations(false)`), `apply_native_frame` does three things — strips `WS_CAPTION` and adds back `WS_THICKFRAME|WS_BORDER`, installs the `native_frame_proc` subclass which hands `WM_NCCALCSIZE` to `DefWindowProcW` (bypassing tao) and then, when not zoomed, pulls the client top back to "window top + 1px" (see the third trap below), and posts `SWP_FRAMECHANGED` so the DWM re-evaluates — at which point the DWM draws the native 1px border, shadow, and maximize/snap animations, with no title bar (Win11's rounded corners/outline likewise come for free with a real frame). **The key trap**: tao 0.35 answers `NCCALCSIZE` with 0 on its own for `decorations(false)` windows (client = the whole window rect — see its event_loop.rs), and the DWM reads "empty non-client area" as "nothing to draw" — so restoring style bits alone is useless; NCCALCSIZE must be handed back to the default handler. **Second trap**: tao's `WindowState::apply_diff` rewrites `GWL_STYLE` in full from `to_window_styles()` on any window-flag change (`set_visible`, maximize/restore, etc.), and that function unconditionally includes `WS_CAPTION` (only CHILD windows get it stripped per decorations) — the caption stripped at window-build time is silently re-added by `show()` (the on-machine probe `verify_manager_frame.py` dumped a full `WS_OVERLAPPEDWINDOW`, which is where this came from); so `native_frame_proc` also intercepts `WM_STYLECHANGING` and rewrites `styleNew` in place before the style lands (strip `WS_CAPTION`, keep `WS_THICKFRAME|WS_BORDER` — the same technique as the factory.rs skin subclass), so the caption style can never stick. **Third trap**: the default NCCALCSIZE insets all four sides by the resize-frame thickness, and both window states need a correction: ① restored — the left/right/bottom insets land outside the visible bounds (`GetWindowRect` is ~7px larger than the visible frame), but the top inset stays inside the visible window: the DWM draws only the 1px top border and the remaining ~7px is dead white space (measured on the manager window: the client top sat 8px below the window top), so `rgrc[0].top` is rewritten to "window top + 1px"; ② maximized — a `THICKFRAME` window without `WS_CAPTION` is placed at the FULL monitor rect (no work-area shrink), so the default client covers the taskbar strip (measured: client = full monitor size), and the window rect's bottom non-client band paints over the whole non-topmost taskbar (this is where the "maximize looks like fullscreen" report came from) — two corrections are needed: when `IsZoomed`, `rgrc[0]` is rewritten wholesale to the monitor's `rcWork` via `MonitorFromWindow` (content hugs the work area), AND `WM_GETMINMAXINFO` is intercepted to rewrite `ptMaxPosition`/`ptMaxSize` to "work area + frame inflation" (so the window rect itself no longer reaches into the taskbar zone; the inflation is derived from the default `ptMaxSize` vs. the monitor size — DPI-agnostic; the message goes through tao/default handling first, so `min_inner_size` constraints are unaffected). Both cases are proven by `tools/win32-probes/top-inset-probe.ps1`: restored clientTop 8px → 1px, maximized rect = work+inflation with client = rcWork exactly, border + shadow intact, and the DWM draws no title bar in either state (the thin-frame-ring trap is not tripped). Proven by Win10 probes (`tools/win32-probes/frame-probe.ps1`, re-runnable): NCCALCSIZE zeroed → DWM draws nothing (border and shadow both lost); a partial non-client area (thin frame ring) → DWM draws the full title bar; only `WS_THICKFRAME|WS_BORDER` without `WS_CAPTION` + default NCCALCSIZE yields native frame + shadow + no title bar. On-machine verification via `verify_manager_frame.py` (DWMWA_EXTENDED_FRAME_BOUNDS inset by 7px = DWM is drawing the frame). The subclass must be installed on the window's owner thread (the log window builds on a spawn_blocking worker and goes through `run_on_main_thread`); both windows keep `shadow(false)` — `shadow(true)` is the `DwmExtendFrameIntoClientArea` glass-extension path, which layered on a real frame leaves a 1px glass line at the window edge. Four earlier routes all died in Win10 field testing: fbdf515's frameless shadow (insufficient alone), the Win10-conditional 1px stroke (invisible at 14% alpha), the global CSS 2px stroke (vetoed on looks), and the custom-caption subclass (zeroed NCCALCSIZE loses the frame) — do not resurrect any of them. The skin windows' frameless machinery (factory.rs) is fully independent and unaffected. **Fourth trap (top border lost on unfocus)**: with this caption-less recipe the DWM paints the 1px top border only while the window is active — on losing focus it paints nothing at all (not a lighter color: the top window row samples equal the backdrop). The frame appearance of this recipe is driven entirely by what the default `WM_NCACTIVATE` processing reports, so `native_frame_proc` intercepts `WM_NCACTIVATE`: the original parameters first pass through to tao for its focus bookkeeping (`set_active` + focus events, which the manager's hover-ok gating relies on; its `ProcResult::DefWindowProc` reports the truthful state to the DWM), then `DefWindowProcW` is fed a lie — `(TRUE, -1)` — pinning the frame appearance to the active state (last write wins; the border/shadow no longer vanish on unfocus). Only the NC appearance changes, never the real activation state. The inverse trick ("skip DefWindowProc, return 1" — the same one the skin subclass uses for WM_NCACTIVATE) kills the border in the active state too under this recipe (the DWM never learns the frame state) — do not copy it here. Probes: `tools/win32-probes/focus-frame-probe.ps1` (recipe-level three-way control: current = no border unfocused, lie = border in both states, skip-and-return-1 = no border even when active) and `manager-focus-frame.ps1` (on-machine two-state sampling of the real manager window, incl. the `AttachThreadInput` foreground-lock workaround) — both re-runnable.
- The manager window corner-rounding policy = **follow the system default**: with real frame styles, Win11 rounds automatically via the DWM (see the frame entry above); Win10 stays square — this is a product decision, not a defect. "Transparent window + CSS `border-radius`" was tried to round Win10 too, and was vetoed and reverted; do not add `transparent(true)` to the manager window to chase rounded corners. Corollary: **window-level elements (`body`/`#app`/`.settings-overlay`/`.wizard-overlay`) never get `border-radius`** — they once carried a 12px radius matching the rounded window frame, and on Win10's square windows the settings / install wizard overlays showed uncovered corner blocks; Win11's rounding is cropped by the DWM on the window frame and doesn't rely on those radii. Plain `decorations(true)` was once vetoed (feared duplicate title bar, loss of the custom-drawn brand header) — the "native frame without a title bar" that finally landed is exactly the answer to that concern: strip `WS_CAPTION`, keep `WS_THICKFRAME|WS_BORDER`; border and shadow in, title bar out. **Drag mechanism**: titlebar dragging = tauri's injected drag.js (listens for mousedown, honors the `data-tauri-drag-region` attribute) invoking `plugin:window|start_dragging` — the `.titlebar` carries `data-tauri-drag-region="deep"` (clicks on any child element drag; buttons and other clickable elements are auto-excluded by drag.js), and the capabilities files must grant `core:window:allow-start-dragging` in default.json (main) / log.json (log) — otherwise the invoke is silently rejected by the ACL (the main window also grants `allow-internal-toggle-maximize` for double-click maximize). This was missing for a long time (the attribute was dropped in the UI redesign) — "the titlebar won't drag" was the symptom. Skin windows do not use this path (the bridge's `start_skin_drag` custom command, no ACL surface).
- For the manager UI's color tokens, layout skeleton, control language and motion standards, see `docs/设计规范.md` (Chinese; kept only in the dev repo, not synced to the public one); read it before changing `src/css/style.css` and frontend template markup.
- **Focus Mode (the `focus.rs` state machine and fullscreen detection)**: enter with one click (hotkey / tray / panel) or automatically on fullscreen — closes all non-whitelisted skins using the entry-time action, and restores from the entry-time snapshot on exit. Persistence: mode state + entry action + snapshot live in `config.focus_mode` (if the app exits/crashes while active, the next startup runs `startup_recover`, restores per the snapshot action and clears; hide-action needs nothing — hiding never touches loaded_skins so a normal restart loads everything back; startup = a clean desktop, the mode never resurrects). Restore follows the **entry-time** action (changing the preference mid-mode never mismatches); the `skin_settings.*.focus_exempt` whitelist is honored in both actions; user actions during the mode win (new loads are left alone, snapshot entries unloaded meanwhile are skipped on restore, skins the user already reloaded are not reloaded again). Fullscreen detection = a resident thread polling every 2.5s (only when `focus_mode_auto_fullscreen` is on): foreground window covering its monitor (≤4px tolerance) + excluding our process / system shells (explorer/lockapp/shellexperiencehost/searchhost/startmenuexperiencehost/textinputhost/sihost) / tool windows — covers exclusive fullscreen (proven live with Genshin Impact) and borderless fullscreen; plain maximized windows do not count (with a visible taskbar, a maximized window only covers the work area). Trigger semantics = **edge-triggered + 5s debounce + manual-exit suppression**: enter on the non-fullscreen→fullscreen edge; exit only after 5s continuously non-fullscreen (Alt+Tab flickers don't exit — returning to fullscreen voids the debounce timer); manual entries exit only manually; a manual exit during a fullscreen cycle suppresses auto re-entry for that cycle (cleared at the next cycle). The decision logic is extracted into the pure function `detector_step` with 4 unit tests (edges / debounce / flicker / manual trigger). **The hotkey and the tray "hide all skins" toggle were upgraded into this mode's switch** (the old `toggle_all_skins` is retired; the tray check item is relabeled "专注模式 / Focus Mode" and synced by `focus::emit_changed`).
- **Manager "close = destroy, reopen = recreate"**: the manager's renderer (~80MB) is the biggest resident block besides skins, and the suspend route (TrySuspend) was proven unreliable on-machine (see 已知问题.md), so closing the manager (close button / Alt+F4 — the frontend's `win.close()` funnels everything into CloseRequested) now `prevent_close` + `destroy()`s the window outright; reopening (tray left-click / "show manager" / double-clicked package / skin-menu "open config") goes through the `None` branch of `tray::show_manager_window` / `toggle_manager_window`, which calls `create_manager_window` (window build + frame subclass + icon + webview hardening + close handler all live in that one function, shared by startup and recreation). Three companion pieces: ① event-stash fallback — while a recreated page is still booting, the "open skin config" emit is lost: when `needs_recreate` (window absent at call time) the skin id is stashed in `AppState.pending_open_config` and the frontend pulls it idempotently at boot via `take_pending_open_config` (same convention as pending_package); ② the startup auto update check runs at most once per process (`AppState.update_auto_checked` + the `take_update_auto_checked` gate) — otherwise every manager recreation would re-query and re-pop the prompt; ③ **ExitRequested guard** — destroying the last window triggers an exit request; with the tray present and no real exit underway, `prevent_exit()` (otherwise closing the manager silently kills the process — seen live). Frontend transient state (selected skin / search query) is not preserved; the list/theme/permissions rebuild from backend config.
- **The `[hidden]` attribute vs author display (four recurrences so far — prevent the fifth)**: the UA stylesheet gives `[hidden]` nothing more than `display:none`, and any author rule with `display:block/flex/...` outranks it — an element with `hidden` still shows (web-view's `#frame`/`.empty`, media-hub's cover placeholder, power-tools' preview image — four cases, one root). Rule: **any element that both uses the `hidden` attribute and has an author display rule must get `<selector>[hidden]{display:none}` to pin it**; also note semantic class names that happen to be `hidden` (e.g. `.status-badge.hidden`) — adding the `hidden` attribute to such an element later would trip the same trap (its `display:inline-flex` always wins). To hunt for this class of bug, grep for the intersection of the `hidden` attribute and author display rules across skins and the manager.
- **Palette screen-picking = NOT provided; do not invest again (both paths proven dead)**: the eyedropper inside the native `<input type="color">` picker fails in WebView2 (field report one); b716360 therefore removed the dedicated button (`.cfg-eyedrop`, EyeDropper API), a second field report revived it, and **on runtime 152 EyeDropper rejects instantly with AbortError** (a DevTools-console call bypassing all app code fails identically — not our regression; it worked on the older runtimes the user remembers, evergreen updates muted it). With both paths dead, the resolution: **no in-app screen picker, wait for the evergreen runtime to heal**; if it is ever built in-house, the sanctioned shape is a one-shot GDI virtual-screen capture + a `screen-pick` overlay window (single capture, no polling; new commands must register in the policy table).
