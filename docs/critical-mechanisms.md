# Critical Mechanisms (Do Not Regress)

> [中文版](关键机制.md) | English

> This document records the critical mechanisms in Driftlet that easily regress when the code changes (window/desktop layering, the install pipeline, data flow, etc.). Before modifying `src-tauri/src/desktop.rs`, `window/factory.rs`, `window/snap.rs`, `skin/protocol.rs`, `lib.rs`, `commands.rs`, or the related frontend code, read the corresponding section first.

---

## Frameless Mechanism

The root cause of, and the defenses against, skin windows "sometimes showing the classic title bar":

1. **`SetWindowSubclass` must be called on the thread that owns the window**. If `load/reload_skin` runs on a `spawn_blocking` worker thread, the cross-thread call fails silently, the window keeps tao's `WS_CAPTION` style, and the DWM draws the classic title bar from it. Install/reinstall always goes through `install_frameless` (run directly on the main thread / rendezvous via `run_on_main_thread`); the 5-second timer idempotently reinstalls on the main thread as self-healing.
2. **`DwmExtendFrameIntoClientArea(-1)` is forbidden**. Glass extension paints any DWM frame into the entire client area, and the title bar shows through transparent skins.
3. `SWP_FRAMECHANGED` is sent only when the styles are actually dirty. Calling it unconditionally makes the DWM re-evaluate the window frame over and over — i.e., keeps giving the frame a chance to come back.
4. tao's `to_window_styles()` always includes `WS_CAPTION` for top-level windows, and any `set_window_flags` (e.g. `set_always_on_top`) rewrites the styles via `apply_diff` — the subclass's synchronous interception of `WM_STYLECHANGING` is the backstop.

## Pin to Desktop

1. **The real mechanism of Win+D**: skins **are not minimized** — the frameless style strips `WS_MINIMIZEBOX`, and minimize-all only targets minimizable windows. The skin "disappearing" is **z-order occlusion**: Show Desktop raises the desktop icon host (and the wallpaper WorkerW) to the top of the non-topmost band, covering everything on the desktop layer. Any "rearrange once on state change" scheme loses the race against that raise.
2. **Current solution = continuous z-order pinning**: every 250 ms, verify that each pinned-to-desktop skin is in place (the test = **the window immediately below is the icon host or another pinned skin** — with multiple skins, the strict "exactly right above the host" condition cannot hold for all of them at once; it once caused ≥2 skins to flip back and forth every tick, each eating a SetWindowPos). If one has drifted, insert it back **immediately above the desktop icon host (the host of `SHELLDLL_DefView`)**; once converged, multiple skins stack in a pile above the host. No state machine, no helper window — it self-heals every kind of disorder (Win+D double cycles, click raises, fullscreen apps, host rebuild after an explorer restart). A skin in the foreground (the user is interacting with it) is skipped, and sinks back to the desktop layer within 250 ms of losing focus. When the host itself is at the top of the z-order, the repair falls back to `HWND_TOP`; enforce validates the process ownership of the hwnd — if the hwnd has been recycled by the system into someone else's window, it only cleans up the entry and never touches the window.
3. Finding the icon host **uses no version heuristics**: both Progman directly containing `DefView` (Win11 24H2+, and Win10/11 right after an explorer restart) and a top-level WorkerW containing `DefView` (the classic form) are collected, and the one highest in z-order wins — that is the desktop surface actually being rendered.
4. The z-order must be explicitly placed **immediately above the icon window** — below it, the desktop ListView (`SysListView32`) swallows all clicks, and the skin can never be clicked or dragged.
5. When pinning to desktop, set `WS_EX_TOOLWINDOW` and clear `WS_EX_APPWINDOW` (invisible in taskbar / Alt+Tab, belt-and-braces against minimize-all); when unpinning, **clear both bits** — tao never sets `WS_EX_APPWINDOW` for `skip_taskbar` windows in the first place, so "restoring" it means inventing it out of thin air, which would put the skin on the taskbar / Alt+Tab.

## Position Lock

- The drag-interception switch = `__DESK_PP__.positionLocked` inside the webview (injected by the bridge, `skin/protocol.rs`).
- The locked state at window creation must be baked into the bridge by the protocol layer via the `skin://` URL query (`locked=1`) — do **not** restore it with a post-creation eval (it races page load; this once caused the lock to be lost after reload when switching always on top ↔ pin to desktop).
- Toggling the lock at runtime goes through the eval in `set_skin_position_locked` (the page is already loaded, no race); the lock CSS uniformly uses the `#desk-lock-style` id, removed on unlock.

## Skin Dragging and the Context Menu

- No longer relies on `-webkit-app-region: drag` (Windows treats draggable regions as a title bar and pops up the system menu on right-click). `.drag-region` in the skin HTML gets a `pointerdown` binding from the injected script; pressing the left button calls the backend `start_skin_drag` command to drag (border resize reuses the same synthesized-message mechanism — see "Border Drag-Resize"). **A press landing on an interactive element (`button/input/select/textarea/a/label/[contenteditable]`) must skip the drag** — `start_dragging` enters the system modal move loop on pointerdown and captures the mouse, so the matching pointerup is eaten and the DOM `click` never fires (in 1.0 controls-demo had no in-window buttons, so this bug stayed latent until a skin with in-window buttons appeared).
- Right-click = a self-drawn native menu (Open Skin Config / Refresh Skin / Uninstall Skin 「打开皮肤配置 / 刷新皮肤 / 卸载皮肤」): bridge `contextmenu` → `show_skin_context_menu` command → `TrackPopupMenu` on the main thread (`TPM_RETURNCMD`, modal, with `SetForegroundWindow` before the call so clicking outside can close it) → action dispatch. "Open Skin Config" activates the manager and `emit("open-skin-config")`; refresh/uninstall reuse `reload_skin` / `unload_skin`, and must be **fire-and-forget** (return immediately after spawn) — the action destroys the very webview that made the call, and awaiting would make wry deliver the invoke response to a dead window (in debug this prints a harmless PostMessage warning).
- **`close()` returning ≠ the label is freed**. In `destroy_skin_window`, after `window.close()` the webview still needs a few ms in the event loop to actually be destroyed; `load_skin` recreating a window with the same label right away reports "already exists" (right-click refresh once reliably reproduced "can't come back after uninstall"). So after close you must poll `get_webview_window(label)` until it is None before returning. **Polling is only needed on the "rebuild with the same label" path** — the tray exit `graceful_exit` uses the no-wait `close_skin_window_nowait` (the split-out shared first half); otherwise every loaded skin serially waits for one webview destruction, which is a source of exit jank. Do not change the exit path back to `destroy_skin_window`.
- The WebView2 default menu is disabled via `SetAreDefaultContextMenusEnabled(false)`. WebView2 is not ready yet at window creation, so the first call fails — the creation-time retry thread (~6 s) plus the 5 s maintenance timer keep covering it; do **not** change it back to a single post-creation call. The subclass's interception of `WM_NCHITTEST => HTCLIENT` and `WM_NCRBUTTONUP` / `WM_CONTEXTMENU` is kept, to prevent the system menu leaking through.

## Border Drag-Resize (resizable)

- **The switch value is tri-state**: the runtime config `SkinRuntimeConfig.resizable: Option<bool>`; None = follow `skin.json window.resizable` (old configs missing the field are None, automatically following the author's default); Some(v) = the user's explicit choice on the "Window" 「窗口」 page. Both window-creation baking and panel display use the effective value `config.resizable.unwrap_or(manifest.window.resizable)`.
- **The hot zones must be implemented in the JS bridge layer, not via subclass `WM_NCHITTEST`** — the WebView2 child window covers the entire skin window, so the parent (the subclassed tao window) never receives the hit test (this was once implemented that way; even the frameless cursor couldn't drag it, and it was reverted).
- Current chain (same mechanism as `start_skin_drag`): effective value → URL-baked `resizable=1` at window creation (same path as `locked=1`; **do not** change back to post-creation eval) → the protocol layer bakes `__DESK_PP__.resizable` → the bridge script, when `pointermove` hits the 6px edge hot zone, shows the resize cursor via `#desk-resize-style` (`*{cursor:…!important}`), and on `pointerdown` (`stopPropagation` in the capture phase, to avoid triggering a drag) calls `start_skin_resize` → backend `ReleaseCapture` + `PostMessage(WM_NCLBUTTONDOWN, HT*)`; DefWindowProc enters the system modal resize loop.
- **Runtime toggle = `set_skin_resizable` eval calling the bridge's `__DESK_PP__.setResizable(on)`** (the page is already loaded, no race): flips the flag + syncs the border hint layer (`#desk-resize-frame`: 4px yellow-black hazard stripes on the four edges, a `transform` displacement animation (GPU-composited; a background-position animation repaints every frame and jitters — do not change back), `pointer-events:none`, boundaries visible even on transparent skins). The bridge's pointermove/pointerdown listeners are **permanently registered and check the flag per event** — do not change back to flag-conditional registration, or enabling it would require a reload to take effect.
- Size persistence goes through tao `WindowEvent::Resized` (same path as `Moved`): physical pixels ÷ scale_factor → in-memory config updated immediately + 500 ms debounced disk write (shares `debounced_config_flush` with position) + `emit("skin-resized")` to refresh the panel inputs. The panel's `set_skin_size` loop-back event carries the same value and is skipped, not written.
- **Zoom**: the user can scale the whole skin to 50%–200% on the "Window" 「窗口」 page (`MIN/MAX_ZOOM`, `clamp_zoom`). Tri-state value: `SkinRuntimeConfig.zoom: Option<f64>`; None follows `skin.json window.zoom` (**use Option, not an opacity-style bare f64** — entries built by `or_default()` won't flush the manifest default to 1.0; the serde default of `WindowDefaults.zoom` must fall back to 1.0 — landing on 0.0 = the window gets multiplied away). **The width/height in the config are always the 100% base size; the panel's width/height inputs are always the zoomed actual size**: actual window = base size × zoom (`inner_size(w*z,h*z)` at window creation, `set_size` in `set_skin_zoom`/`set_skin_size`), and `WebviewWindow::set_zoom(z)` (WebView2 ZoomFactor) scales the content by the same factor — **both sides multiplied by the same ⇒ the page's CSS viewport is always the design size, the layout never reflows, and any skin can be scaled as a whole with zero adaptation** (this is the platform landing point of "all skins must be written so they can scale proportionally"). The conversion points of the two size semantics: persistence is always = actual ÷ effective zoom (the Resized event; the panel's `set_skin_size` inputs the actual size and converts the same way; the effective zoom is read live from config, missing entries fall back to the manifest — the closure captures `manifest_zoom`); panel display is always = actual (`get_skin_detail` multiplies the config width/height by zoom before returning, `skin-resized` carries the actual value, and since `set_skin_zoom` leaves the base size unchanged its loop-back would be swallowed by Resized's "unchanged, skip", so it must explicitly `emit("skin-resized")` itself); when `set_skin_zoom`'s entry is missing it seeds from the manifest size (`or_default`'s 300×200 would make set_size wrong); a `set_zoom` failure only degrades to a log (the size is still correct), and at window creation it is called before show, so there is no 100% flash.
- The subclass's `WM_GETMINMAXINFO` setting a minimum of 60×40 (DPI-scaled) must be kept — the modal resize loop reads it no matter who triggered it, preventing the window from being dragged to a size that can't be grabbed.

## Edge Snapping

- **The hook point = the window subclass's `WM_MOVING`** (`window/factory.rs`); do not implement it with the `Moved` event + `set_position` — that would loop back on itself and the drag trajectory wouldn't be smooth. The system modal drag loop passes in the pending screen-coordinate RECT at every step; `on_window_moving` in `window/snap.rs` rewrites it in place to complete the snap. Precise coordinates entered in the panel (`set_skin_position`) don't take this path and are unaffected by snapping.
- **Snap state is registered per HWND** (`SNAP_WINDOWS` in `snap.rs` — only the HWND is available in the subclass callback): `upsert` at window creation, `unregister` at destruction (HWNDs get recycled and reused by the system; a leftover entry would mistake an unrelated window for a snap candidate, so it must be cleaned up on destroy), `upsert` updates on panel toggle / gap change. Candidate edges = the other skin windows in the registry (live `GetWindowRect` during the drag, no caching, skipping destroyed/invisible/minimized ones) + the **work area** of the monitor the window is on (`MonitorFromRect` + `GetMonitorInfoW`, excludes the taskbar, multi-monitor correct).
- **Snapping = pure distance judgement**: on each of the X/Y axes, screen candidates are computed first; if |delta| ≤ threshold (`SNAP_THRESHOLD` = 10 logical px, converted to physical px by the window's DPI) the screen wins; only when neither is within threshold does the window candidate with the smallest |delta| win (left/right/top/bottom edge alignment + adjacent abutting). A window candidate requires the two windows to overlap, or be within threshold distance, in the direction perpendicular to that axis — otherwise distant windows cause "phantom snaps". After snapping, within the same drag you have to drag out of the threshold zone to detach — the feel is simple and predictable; fine adjustment goes through the escape window below. Direction-aware escape (3px reverse detachment + escape suppression) and Shift temporary bypass were both tried; in practice the feel was unstable/superfluous, both were reverted and deleted — do not add them back.
- **Escape = the 1-second free window of "release and drag again"**: when the last drag ended snapped (`DragRuntime.ended_snapped` records the snapped coordinates, updated per WM_MOVING) and the window is still at the same coordinates (±1px), `begin_drag` (`WM_ENTERSIZEMOVE`) opens a 1-second escape window for this drag (`escape_until`, judged by `Instant`) — during it there is no snapping, the window is only clamped into the screen work area − gap (`clamp_to_work`, "cannot go beyond the screen + custom gap"; when the window is wider than the work area it pins to the min edge to avoid a panic); when time is up, snapping resumes (takes effect within the same drag). `DRAG_STATES` persist across drags and are only cleared on `unregister`; **do not** clean up state on `WM_EXITSIZEMOVE`, and do not update `ended_snapped` inside the escape window (losing the memory breaks "release and drag again"). After the position is changed by the panel/program, `should_arm_escape`'s coordinate check naturally fails and won't wrongly open the window.
- The gap `snap_gap` (logical pixels, clamp 0–200 = `MAX_SNAP_GAP`) applies both to screen edges and to window adjacent-abutting (alignment-type candidates don't include the gap). Persisted in `SkinRuntimeConfig.edge_snap` / `snap_gap` (both `#[serde(default)]`, default off / 0); the commands `set_skin_edge_snap` / `set_skin_snap_gap` only persist when the skin is not loaded, and sync the registry for immediate effect when it is loaded (same semantics as `set_always_on_top`).

## Preview Capture

- **`capture_skin_preview` must stay an `async fn`**: Tauri 2's non-async commands execute on the **main thread**, while the capture implementation needs `recv_timeout` to block waiting for the WebView2 `CapturePreview` completion callback — and that callback is dispatched precisely by the main thread message pump. A sync command blocks the main thread so the callback can never arrive, freezing the whole manager UI until timeout; an async command waits on a runtime worker thread while the main thread keeps pumping messages — no mutual blocking.
- Capture goes through `ICoreWebView2::CapturePreview` (`capture.rs`); **do not** change back to `PrintWindow` + GDI: the latter's alpha channel is undefined (the saved PNG has large transparent "missing chunks"), transparent skins get a black background, and when the window is occluded / pinned to desktop / minimized you capture a black screen or ghosting.

## Data Flow

```
User drags a skin → WebviewWindow Moved event
→ backend factory::save_dragged_position: in-memory config updated immediately (takes effect on reload) + 500 ms debounced disk write
→ emit("skin-moved") → skin-editor.js listen() → only updates the input box display
```

- Dragged-position saving must stay in the **backend** Moved event; do not move it back to the frontend — the frontend listener is only registered while the config page is open, which once caused "drags aren't saved while the panel is closed, and the skin returns to its original position after reload".
- Config values for position and size are **always logical pixels**: creation (`inner_size`), setting (`LogicalPosition` / `LogicalSize`), and event readback (physical ÷ `scale_factor`) all follow the same convention. Any path that feeds a config value into `PhysicalSize` / `PhysicalPosition` will, at DPI zoom ≠100%, make the actual size inconsistent with the panel and "restore" after reload.
- **New fields in persisted structures must carry `#[serde(default)]`** (`AppConfig` / `SkinRuntimeConfig`; except `Option` fields, which serde automatically sets to `None` when missing). The cost of forgetting: every old config.json fails to parse wholesale and is reset to defaults as a corrupted file — with the single-file scheme the blast radius is all skin data (only `.bak` as the backstop).
- For skins that no longer exist on disk, their config leftovers (`skin_settings` / `loaded_skins` entries) are **cleaned up uniformly at startup** (covering two sources: the folder was manually deleted, or the author changed the id); in-app deletion goes through `remove_skin` for immediate cleanup. Disk-write failures of settings commands **must be propagated to the frontend** (`配置保存失败: …` — "failed to save config: …"); do not change back to swallowing them with `let _ =` — the user would see "saved successfully" but lose it after restart. Exception: the drag debounce save only logs `log::warn` (the panel may not be open; nobody is there to receive the error).
- config.json (version 2) only stores window-page data and global settings; the user values of the "Skin Settings" 「皮肤设置」 page live in the **skin folder's `settings.json`** (see the next section). The v1 config's `skin_settings[id].custom` is migrated into each skin folder at startup by `migrate_v1_custom_settings` (after scan, before load_config): if settings.json already exists, the existing file wins and is not overwritten; entries whose write fails keep their custom and **the version number is not bumped**, retried at next startup; orphan entries (skin no longer exists) have their custom discarded with the version upgrade (consistent with prune semantics). `SkinRuntimeConfig` has deleted the `custom` field; leftover old keys are automatically ignored when serde reads them.
- **`save_app_config` uniformly goes through normalization**: version is force-written as the current version, `language` is synced with the in-memory state, and the always-on-top/pin-to-desktop either-or goes through `normalize_mode_flags` (already promoted to `pub(crate)`, sharing one implementation with config load) — all write paths and startup loading produce the same normalized result, eliminating the back-and-forth oscillation of "normalize on load, write back verbatim on save". New write entries must all go through `save_app_config`; don't hand-write `serde_json::to_string` to disk.

## Skin Custom Settings

- Initial values = baked into `__DESK_PP__.settings` when the `skin://` protocol layer serves HTML (a merge of schema defaults + override values from the skin folder's `settings.json`; see `baked_settings_json` in `skin/protocol.rs` and `effective_settings` in `skin/loader.rs`) — same reasoning as position lock; **do not** change it to a post-creation eval restore (races page load).
- **`password`-type values are not baked into the page**: `baked_settings_json` always replaces password items with an empty string (that key in `__DESK_PP__.settings` is always empty) — skin:// is same-origin for all skins, so a value baked into HTML can be fetched away by any skin. Skins instead read on demand via the `skin_get_setting` command (`skin_api/mod.rs`; identity is taken from the window label, it can only read keys declared in its own schema, no permissions declaration needed). Accordingly, the `skin-setting-changed` event after `skin_set_setting` writes to disk was changed to `emit_to("main")`, targeted at the manager — broadcasting would route the setting value (possibly containing a password) past every skin window via the event.
- **User override values are persisted in the skin folder's `settings.json`** (sibling of skin.json; read/write in `skin/settings.rs`: missing → empty, BOM tolerated, corrupted → renamed to .bak, atomic write). `skin.json` is never rewritten by the app: the schema and defaults live only there, and "reset" = delete `settings.json` (`reset_skin_config` also deletes `skin_settings[id]`, both falling back to defaults).
- **skin:// intercepts any `settings.json`** (including `.bak` / `.tmp`) → 404 — this file is an exposure surface newly introduced with the value-file scheme; without interception skin A could fetch skin B's setting values.
- Before serializing the settings JSON into `<script>`, `</` must be escaped to `<\/`, otherwise a `</script>` in a setting value closes the tag early.
- Runtime change = the `set_skin_custom_setting` command writes to disk then pushes via eval: updates `__DESK_PP__.settings[key]` and dispatches the `desk-setting-changed` document event. A skin that doesn't listen for the event still gets the new value on the next reload.
- **Skins can also write their own settings**: the `skin_set_setting` command (`skin_api/mod.rs`, skin-only — does not reuse the manager command; identity from the window label, can only write keys declared in its own schema, values go through the same `validate_custom_setting`, no permissions declaration needed). Therefore `settings.json` has **two writers**; the whole load→save sequence must hold `AppState::settings_lock` (std Mutex; both commands are sync fns) to prevent them from losing each other's updates — do not split it back to lock-free.
- **Skin → manager direction sync**: after `skin_set_setting` writes to disk it does `emit_to("main", "skin-setting-changed")` (targeted at the manager, not broadcast — see the previous item); skin-editor.js listens and refreshes the corresponding control in place (`_syncCustomControl`: list-type re-renders the row — event delegation bound on the container is not lost; assignment-type only updates value/checked — the node must not be replaced; composite types like palette/chips don't touch the DOM in the first version; always skip when focus is inside the control — content being edited takes priority). A skin's **self-write does not re-dispatch** `desk-setting-changed` (preventing a "write → event → write again" loop), it only silently syncs `__DESK_PP__.settings[key]`.
- Persisted override values are only adopted when their type matches the schema declaration; after a skin author changes a setting item's type, old values automatically fall back to the defaults.
- Controls are rendered by branching on `type`, concentrated in `renderCustomSettings` / `bindCustomSettings` in `skin-editor.js`; **adding a new control type requires syncing four places**: `SkinSettingKind` in `types.rs`, the type matching and fallback in `loader.rs`, the validation in `commands.rs`, and frontend rendering/binding. Custom controls exclusively occupy the "Skin Settings" 「皮肤设置」 tab, separate from the built-in "Window" 「窗口」 page.

## Skin Backend Interface (skin_api)

> The system-info and sensitive-capability commands that skins can call via `__DESK_PP__.invoke` (the `skin_api/` module). For the external contract see `docs/skin-development-guide.md` §2.3 / §5.

- **The bridge is a passthrough, with no command whitelist**: `__DESK_PP__.invoke` directly forwards `__TAURI_INTERNALS__.invoke`; any command registered into `invoke_handler` can be called by skins. Therefore **sensitive commands must carry their own permission check** (`require_perm`: window label → skin id → re-scan the manifest for `permissions`); "documented convention not to call it" is not enough. All new sensitive commands go through this entry.
- **Manager commands are uniformly gated by `require_manager`**: the bridge passthrough means the manager commands in `commands.rs` are also reachable by skins by default, and skins should never be able to reach them (unrelated to whether permissions are declared — `require_perm` can't cover this layer). All ~40 manager commands (load/unload/settings/install etc.) validate at entry that the calling window label == "main"; calls from skin windows always fail with "该命令仅允许管理器窗口调用" ("this command may only be called by the manager window"). The only legitimate skin exceptions are three harmless commands: `start_skin_drag` / `start_skin_resize` / `show_skin_context_menu` (identity is reverse-looked-up from the window label; they can only operate on themselves). **New manager commands get `require_manager` by default**.
- **Capabilities are split and tightened per window**: `default.json` only attaches to `"main"` (core:default + minimize/toggle-maximize/hide — only what the manager frontend actually uses); the new `skin.json` attaches to `"skin-*"` with **empty permissions** — skins don't use @tauri-apps/api, app custom commands aren't constrained by the capabilities ACL, and the real gate is on the Rust side (caller_skin / require_perm / require_manager); core and plugin permissions like shell / dialog / autostart / window-create / event-emit are never granted to skin windows.
- **Rate-type readings = the sampling baseline pattern**: a static `Mutex<Option<…>>` holds the sampler (`CPU_SYS` for CPU, `PdhMultiCounter` for PDH); the first call only establishes the baseline and returns 0 — the dev guide already tells skins to poll once per second.
- **sysinfo 0.32 has no disk IO stats** (removed since 0.30); disk read/write speed goes through PDH `\LogicalDisk(*)\Disk Read/Write Bytes/sec` (the instance name is the drive letter, joined with sysinfo mount points by drive letter; **do not use `\PhysicalDisk`** — it aggregates by physical disk, and multiple partitions on the same disk would show the same rate); GPU usage goes through PDH `\GPU Engine(*)\Utilization Percentage` (instance names contain `luid_0x…_0x…`, aggregated by LUID to the DXGI adapter). PDH counter paths must be added as English paths with `PdhAddEnglishCounterW`, independent of the system display language.
- **GPU assembled from two sources**: name/LUID/dedicated VRAM = DXGI (skipping SOFTWARE adapters); VRAM usage = `IDXGIAdapter3::QueryVideoMemoryInfo`. There is no general Windows interface for core frequency (only vendor SDKs; the NVML route and the `frequency_mhz` field were removed per requirements).
- **Audio loopback**: wasapi automatically sets `AUDCLNT_STREAMFLAGS_LOOPBACK` for "render device + Capture direction + Shared", no manual flag needed; `convert=true` guarantees f32/48k/stereo. The capture thread is lazily started (spawned on the first `get_audio_spectrum`), **releases the device after 30 s idle** (a skin can be unloaded at any time, so the endpoint can't be permanently occupied), and failures are written to shared.error and surfaced by the command side. Spectrum = 2048-point Hann + FFT, 30Hz–16kHz log-spaced bands, normalized with a -60dB floor.
- **File sandbox (files permission)**: first reject absolute paths and `..` components, then canonicalize and do a prefix check (against symlink escape); `create_dir_all` on the parent before writing, so write paths can also be canonicalized. `skin.json` / `settings.json` (including `.bak`/`.tmp`) are read-only — no write, no delete. Read 32MB / write 16MB caps. **Any path component containing `:` is rejected** (against NTFS ADS: `skin.json::$DATA` is an alternate data stream of the same file and could bypass the per-filename read-only interception — same rule as protocol.rs).
- **`run_command` must be async + spawn_blocking**: Tauri 2 non-async commands execute on the main thread (same constraint as the "Preview Capture" section); a 120-second child-process timeout on the main thread would freeze the entire manager. Child process output is read by two threads, one each for stdout/stderr (sequential reads get deadlocked by a filled pipe), each truncated at 1MB; Chinese Windows console output is GBK, and invalid UTF-8 falls back to `MultiByteToWideChar(CP_OEMCP)` transcoding. `CREATE_NO_WINDOW` hides the console window.
- **COM conventions for volume/media**: `volume.rs` calls `CoInitializeEx(MTA)` per call and **only CoUninitializes when it returns S_OK** — RPC_E_CHANGED_MODE (the thread was already initialized elsewhere) semantically means "keep using it, don't uninit"; SMTC (`media.rs`) WinRT async always blocks with `.get()`, and both media commands must be `async + spawn_blocking` (the same main-thread prohibition as `run_command`, see the "Preview Capture" section). SMTC degradation contract: no session returns `None`, which is not an error; cover/progress field failures just stay empty without failing the whole call.
- **Clipboard goes through tauri-plugin-clipboard-manager** (Rust side `app.clipboard()`, the command carries its own permission gate); `open_external` uses `ShellExecuteW` (the shell plugin's `open` is deprecated — do not change back), whitelist = `http(s)`/`mailto` or an existing absolute path, preventing `file:`/`javascript:` injection; for local paths additionally a **23-item executable-extension blacklist** (exe / bat / cmd / ps1 / vbs / msi / lnk / hta etc. — ShellExecuteW on an executable equals a skin bypassing the `shell` permission declaration to run a program directly), **UNC paths (`\\` / `//` prefix) are always rejected** (they trigger SMB outbound connections and remote executables), and URL and path targets share one error message. A return value ≤32 is ShellExecute's failure code.
- **assetProtocol has been deleted wholesale**: tauri's assetProtocol scope allows by path prefix and can't block individual files inside a directory; it once exposed every skin's `settings.json` to all windows. Preview images now go straight out of the `skin://` protocol (on Windows `http://skin.localhost/<skin folder>/preview.<ext>` — take the **last two segments** of the preview image's absolute path to build the URL, see `src/js/api.js`), the same interception chain as skin resources (built-in settings.json interception and canonicalize protection), adding no new exposure surface. Do not re-enable assetProtocol.
- **There are now six permissions**: `files` / `registry` / `shell` / `system` (volume · media control · open external · system notifications) / `clipboard` (read/write clipboard) / `mic` (microphone spectrum — loopback only listens to system output so it's exempt; the microphone is real pickup and must be listed separately). Read-only info commands (including `get_media_info`, `get_volume`) stay declaration-free; **any command that changes system state or could read out user privacy must go into `require_perm`**, and sync the §2.3 table of the development guide.
- **Dual audio sources (`audio.rs`)**: `Source::Loopback` (render device + Capture init = loopback) and `Source::Mic` (capture device) share one capture-thread template and ring buffer, each holding its own static slot and its own lazy-start/idle-self-stop; when changing the pipeline, change both sources together. On desktops without a battery, `get_battery_info` returns `has_battery=false` (not an error); with no audio endpoint the corresponding commands reject and retry in 5 seconds.
- **Toast notifications' (`notify.rs`) unpackaged trio**: at startup `SetCurrentProcessExplicitAppUserModelID("Driftlet")` (lib.rs setup) + Start Menu `Driftlet.lnk` (IShellLink + IPropertyStore stamping `PKEY_AppUserModel_ID`, including `SetIconLocation`; rewritten as self-healing when the target doesn't match the current exe, **done on a background thread at startup**, not waiting for the first notification) + `CreateToastNotifierWithId` with the same ID — **all three are indispensable**; on Win10, without the shortcut, Show succeeds but nothing is displayed. Two memory disciplines not to regress: the AUMID wide-char buffer is **deliberately leaked** (the property bag may lazily read it back; freeing it is use-after-free); in `create_shortcut`, **never CoUninitialize after CoInitializeEx** (propsys's shortcut handler corrupts the heap when the MTA apartment is torn down — measured 0xc0000374). The XML must escape the five characters; title/body truncated at 64/256 characters.
- **The AUMID is also the resolution key for the taskbar icon**: once the process sets an AUMID, the taskbar matches Start Menu shortcuts by it to get the icon — when the shortcut points to an icon-less binary (test programs, a deleted install path) the taskbar shows the **default program icon**. So `ensure_aumid_shortcut` must, one, carry `SetIconLocation`; two, refuse cargo test binaries (filename `driftlet_lib-*`) rewriting the shortcut (probes must not pollute the user's Start Menu entry); three, self-heal at startup.
- **The main thread's COM apartment belongs to tao**: no `CoInitializeEx(MTA)` may run on the main thread — tao's `OleInitialize` at window creation wants STA; if the main thread went MTA first it's `RPC_E_CHANGED_MODE` and a direct panic. All COM work goes to background threads (volume/media commands already run on the spawn_blocking path, not as sync commands; the shortcut self-heal in setup likewise spawns).

## Stability Conventions (Mutex / FFI Callbacks)

- **Global `std::sync::Mutex` poison recovery**: always `.lock().unwrap_or_else(|e| e.into_inner())` — after a panic on a lock-holding path the lock enters the poisoned state, and a bare `unwrap()` would make every other caller panic in a chain until the whole app locks up; `into_inner()` tolerates "state may be partially updated" and keeps serving, far better than total failure. New Mutexes follow the same pattern; do not write bare `.lock().unwrap()`.
- **FFI callbacks must `catch_unwind`**: entries called back into Rust directly by Windows (`skin_subclass_proc`, `EnumDisplayMonitors`, etc.) are wrapped in `catch_unwind(AssertUnwindSafe(..))` — a panic crossing the FFI boundary is undefined behavior (in practice, process termination); after catching, log and degrade to a default return value. New WNDPROC / enumeration callbacks follow the same pattern.

## Skin Packages (.dskin) and Skin Identity

- **Skin identity = the `id` field of `skin.json`** (kebab-case). Required when packaging for distribution; during folder scan, when missing, it falls back to a slug of the folder name (compat with old skins). Same id = same skin; scanning dedupes by id, later arrivals are warned about and skipped.
- **Locating a directory by skin must go through scan resolution first** (`find_skin_dir`); do not directly `skins_dir.join(skin_id)` — the id doesn't necessarily equal the folder name. `remove_skin` / `open_skin_folder` / `capture_skin_preview` have been changed to this; follow it for new commands of this kind too.
- **User data lives in two places, both preserved across update/reinstall/rollback**. Window config (`skin_settings[id]`) belongs by id in config.json, decoupled from the skin files; the user values of the "Skin Settings" 「皮肤设置」 page live in the skin folder's `settings.json`, taken out before a wholesale folder replacement and written back after copying (`install_package` in `package.rs` and `copy_example_skins` in `lib.rs` follow the same convention; user values take precedence over same-named files in the package; example skins are synced from the repo `examples/` folder in development only — the installer bundles no skins). New items in a new schema go through defaults; old values with mismatched types are auto-fallen-back by `effective_settings`; leftover data of deleted setting items is harmlessly ignored. The user-side clearing entry = the config panel's "Reset Data" 「重置数据」 button → the `reset_skin_config` command deletes `skin_settings[id]` and deletes `settings.json` (window config and custom settings both fall back to skin.json defaults); loaded skins reload accordingly.
- **`settings.json` is user data and does not go into distribution packages**: `tools/pack-skin` excludes `settings.json` / `settings.json.bak` / `settings.json.tmp` when packing.
- Package extraction (`skin/package.rs`) must go through `enclosed_name` against zip-slip; the size cap is measured by **actual extracted bytes** (accumulated from `io::copy` return values, not trusting the zip header's declared uncompressed size — headers can be forged, and a zip bomb is exactly "declares small, extracts huge"), keeping the size/file-count caps (64MB / 256MB / 5000); the temp directory is cleaned up by an RAII guard. The validation rules (parseable, legal id, entry exists) are **kept consistent** with the packing tool `tools/pack-skin` (the same `SkinManifest` deserialization, strongly-typed validation) — changing one side requires syncing the other.
- **Install = the staging rollback flow** (`install_package`): ① fully copy the extracted content to `skins/.staging-<id>`; ② rename the existing `<id>` to `.<id>.old`; ③ rename staging in (on failure, rename .old back); ④ restore `settings.json` from .old, then delete .old. Failure at any step leaves no "half-new half-old" directory, and the old version can always be rolled back. Skin scanning **skips directories starting with `.`** — staging / .old and misplaced dot-directories are never listed as skins.
- **Loader hardening** (`skin/loader.rs`): `skin.json` ≤1MB (hand-written or packed manifests are all small files; over the limit is anomalous); `entry` rejects `..` / `\` / `:` (against the entry pointing outside the skin directory or ADS); `id` blacklists Windows reserved device names (con / prn / aux / nul / com1-9 / lpt1-9 — system-reserved names can't form normal directories; judged by base name, forms with extensions like `con.txt` are likewise reserved by the system); directory copying **skips symlinks** (against pointing outside the skins directory) and limits depth to 32 levels.
- Updating a running skin: `unload_skin` first, then install, and **stay unloaded** after install (product decision: update/reinstall/rollback by default do not auto-resume running; the user loads explicitly; do not change back to auto load).
- The file picker only filters `.dskin`; `.zip` no longer appears in the user entry, to avoid confusion with ordinary archives.

## Double-Click Install (.dskin File Association)

- **File association = `bundle.fileAssociations` in `tauri.conf.json`**, written to the registry by the NSIS installer — only the installed build has the double-click entry; portable exe / dev have no double-click, but the install logic can be fully tested with a command-line argument: `npm run tauri dev -- -- "D:\path\x.dskin"`.
- **Cold/hot two entry paths, cannot be merged**:
  - Cold start: `dskin_arg(std::env::args())` (skips argv[0], case-insensitive extension, the file must exist) → stored in `AppState.pending_package`, the main window `show()`s immediately, and after frontend startup it **actively pulls** with `take_pending_package_install` (`Mutex::take` consume-style, pops only once). **You cannot emit an event here** — the frontend listener isn't registered yet; emitting loses it.
  - Hot start: the `tauri-plugin-single-instance` callback (must stay registered **first** in the plugin list) → `tray::show_manager_window` + `emit("open-skin-package")`; the frontend listener is long ready.
  - Known race window: within the few hundred milliseconds after a cold start before the frontend is ready, a **second** double-click — that forwarded event may be lost (ends up showing the first package's wizard). Acceptable.
- **Install serialization = `AppState::install_lock` (tokio Mutex)**, wrapping the whole `install_skin_package`: repeated double-clicks + repeated clicks on "Install" 「安装」 would concurrently install the same skin, and `remove_dir_all` and copying would trample each other's directories. Must use `tauri::async_runtime::Mutex` (its guard is Send and can be held across the `.await` of reload) — std Mutex's guard is `!Send` and won't compile; and don't lock only the file-operation section either — unload/reload need the mutual exclusion too.
- **.dskin file icon = `src-tauri/icons/dskin.ico`** (16–256, 10 frames total, scaled from `icon/dskin-icon.png`, packed via `tools/make-ico.cjs`). tauri doesn't support `fileAssociations.icon`; the icon is applied by the installer overriding the default exe icon: NSIS goes through `NSIS_HOOK_POSTINSTALL` in `src-tauri/windows/installer-hooks.nsh` to rewrite the ProgID's `DefaultIcon`; the ico itself is put in the install directory root via `bundle.resources`. **The ProgID is strongly coupled to the config**: the key name = `fileAssociations.name` (currently "Driftlet Skin Package") — changing name requires syncing the hook, or the icon silently stops working. Uninstall needs no registry cleanup (NSIS deletes the whole ProgID key). **The icon takes effect immediately**: the tauri template never calls `SHChangeNotify` anywhere; the hook adds one `UPDATEFILEASSOC` after install and one after uninstall (`SHCNE_ASSOCCHANGED`, provided by the template-bundled `FileAssociation.nsh` — do not delete) — without it Explorer keeps showing the old icon until the cache is manually refreshed. (An MSI was previously produced as well: the icon went through the `windows/dskin-icon.wxs` fragment, language differentiated per package; now only NSIS is built — `targets: ["nsis"]`, the wxs is deleted, recovering it requires digging it out of git history.)
- **The installer language automatically follows the system** (NSIS single package, dual language): the `nsis.languages` order is `["English", "SimpChinese"]` — NSIS automatically matches the system UI language at runtime (probe-verified, unrelated to whether a selection box pops up), falling back to the **first** array element on no match — so English must come first: Chinese systems → SimpChinese, everything else → English; reverse the order and non-Chinese systems would see a Chinese installer. The hook writes `$LANGUAGE` to `HKCU\${MANUPRODUCTKEY}\Installer Language` at POSTINSTALL (the same behavior as `MUI_LANGDLL_DISPLAY`) — without it, in dual-language, the uninstaller's `MUI_UNGETLANGUAGE` finds no record and pops a language selection box. **The app's first-launch language is synced with the installer**: `default_language()` (`skin/types.rs`) uses `GetUserDefaultUILanguage` to judge a Chinese environment (primary language ID 0x04) → `zh-CN`, otherwise `en` — the same judgement rule as the installer, so the install language is the first-launch language; it only takes effect when config.json lacks the `language` field (first launch); existing configs are unaffected.
- **Uninstall data cleanup = the hook POSTUNINSTALL deletes everything, no checkbox**: app data is placed **next to the exe** per `resolve_portable_dir` (writable install location; protected directories like Program Files fall back to `%APPDATA%`), and WebView2 data is in `%LOCALAPPDATA%` — the template itself only deletes the files it installed and does only a non-recursive RMDir on `$INSTDIR` (which fails when config/skins are inside, leaving the whole install directory behind); all three places are beyond its reach. On non-update uninstalls the hook **unconditionally** backfills deletion: `$INSTDIR\config` / `$INSTDIR\skins` recursively + a non-recursive retry of the root directory (deliberately not /r — files the user placed themselves are preserved) + `%APPDATA%` / `%LOCALAPPDATA%\<bundle id>` + the `${MANUPRODUCTKEY}` registry (including the `Installer Language` written at install time). **The `${If} $UpdateMode <> 1` guard must never be removed** — an update install runs the old uninstaller first; without it every update would wipe the user's config and skins. **The "delete app data" 「删除应用数据」 checkbox has been removed**: the original template creates it unconditionally in `un.ConfirmShow` (unchecked by default, the whole page skipped in silent/passive mode, and it only covered `%APPDATA%`), with no config switch at all (tauri-utils 2.9.3 has no such field), and a hook file can't pre-define it at compile time either (the template has no `!ifdef` guard; pre-defining collides with a `!define` redefinition error) — the only way is the `nsis.template`-style own template `src-tauri/windows/installer.nsi` (taken from the tauri-cli **v2.11.4** tag, with the checkbox's Var/SHOW/LEAVE functions and the gated block in the uninstall Section deleted, converging the deletion path to the single hook location). **Upgrading @tauri-apps/cli requires re-syncing that template** (take the new installer.nsi from the corresponding tag and re-apply the same deletions), or template drift silently loses new fixes.
- **The wizard `src/js/install-wizard.js`**: full-window overlay (covers the window's own title bar, with its own drag region and close=cancel), four states: check → confirm → install → done/failed. `_gen` **generation counting** obsoletes the results of stale async flows — consecutive double-clicks switching packages, or an install interrupted by a new package, never cross states; follow the same pattern when adding new async steps (capture gen, validate after await). Close requests are ignored while `busy` (installing). **"+ Add Skin" 「+ 添加皮肤」 and double-clicking `.dskin` both go through the wizard** (the manager's original `confirmPackageInstall` confirm dialog has been deleted; both entries take the same install pipeline — do not open a second confirmation path); the confirm page lists the skin's `permissions` declarations item by item (when there are none, it explicitly shows "未申请敏感权限" — "no sensitive permissions requested"), and `shell` / `mic` are flagged high-risk — before installing a third-party skin, the user must be able to see what capabilities it will get.

## The skin:// Protocol

Skin pages and resources are loaded via the `skin://` custom protocol (handler: `skin/protocol.rs`). Its job is not restricting the network, but four control points:

- **Bridge injection**: baking `__DESK_PP__` when serving HTML (setting values / opacity / lock / resizable / UI language / context-menu takeover / edge resize hot zones) — zero-race delivery; **do not** change back to post-creation eval (see "Position Lock", "Skin Custom Settings"). Runtime language switches go through `set_language`'s eval (updating `__DESK_PP__.language` and dispatching the `desk-language-changed` event — the page is already loaded, no race; same convention as runtime lock toggling).
- **User data isolation**: `settings.json` (including `.bak` / `.tmp`) always 404s; skin A can't get skin B's setting values. The interception is **double**: once by URL path filename before normalization, and once more by the real `file_name` after canonicalize — Windows 8.3 short names (`SETTIN~1.JSO`) can bypass the pre-normalization string match, and canonicalize restores them to long names; any path component containing `:` is rejected (against ADS `skin.json::$DATA` — an alternate data stream is the same file as its body; same rule as `skin_api/fs.rs`).
- **Path sandbox**: canonicalize + prefix check; skins can only read files inside `skins_dir`; it also masks the path difference between dev (repo `skins/`) and prod (install directory).
- **Atomic delivery of window state**: the entry URL query (`opacity` / `locked` / `resizable`) takes effect with the document's first frame.

**URL rewriting (Windows)**: WebView2 doesn't support subresource loading for non-standard protocols; wry rewrites the navigation URL `skin://localhost/...` to `http://skin.localhost/...`, then on the request side intercepts by the `http://skin.*` filter and rewrites it back for the protocol handler (wry `custom_protocol_workaround.rs`) — requests never leave the process, no DNS/TCP.

**Network reality**: a skin page is a full Chromium. Only `http://skin.*` is intercepted; external http/https requests go straight to the real network; skin page responses have **no CSP** (tauri.conf's CSP only applies to app-protocol pages; custom-protocol responses are hand-built by the handler and carry only Content-Type). Cross-origin `fetch`/`XHR` are constrained by CORS (the target server must allow it); `<img>`/`<script>` tag-style loads and WebSocket are not subject to CORS. **A third-party skin = local code that can access the network** — treat the install trust model accordingly.

**Boundary (known exposure surface)**: all skins share the single origin `http://skin.localhost` — the same-origin policy doesn't isolate skins; skin A can request skin B's ordinary resource files (only `settings.json` is blocked). If skin networking is ever to be restricted, the landing point is still this layer: add a CSP header to protocol responses, or register a `*://*` filter for whitelisting.

## Tray Icon

- **Per-size PNGs, never a multi-size .ico**: `tray.rs` embeds 7 tray artwork sizes (16–48, rendered by `tools/make-tray-icon.py` from grid-snapped parametric geometry, not downscaled from a master) and picks the exact size via `SM_CXSMICON` on Windows. Tauri's `Image::from_bytes` decodes only a single ico frame, so a multi-size .ico buys nothing and lets Windows rescale one bitmap to 20/24px instead.
- **`src-tauri/vendor/tray-icon` is a patched vendored dependency** (wired in via `[patch.crates-io]` in `Cargo.toml`) — **the patch must survive any upgrade/replacement**: upstream (0.24.1/0.24.2) `into_windows_icon()` calls `CreateIcon`, passing a **1-byte-per-pixel** buffer where the AND-mask parameter expects a **1bpp monochrome bitmap** (80 bytes for a 20px icon; 400 passed), so the resulting HICON carries a garbage mask. `DrawIconEx` uses the alpha channel for 32bpp icons and ignores the mask — which is why the tray looks fine — but **mask-aware consumers** (Task Manager, which uses the tray icon for processes with no visible window, and the Win11 tray drag image) render horizontal-striped garbage. The patch builds a proper 1bpp mask (rows padded to 16 bits) + 32bpp premultiplied DIB via `CreateIconIndirect`. (The probe `tools/win32-probes/probe_icon_render.py` reproduces both render paths.)
- **Window icons must stay disabled**: tao (0.35.x) `RgbaIcon::into_windows_icon()` is the same buggy code as the tray-icon issue above, and tauri-codegen bakes `icons/icon.ico` as `default_window_icon`, applied to every window (`WindowManager::prepare_window`) — with a window visible, Task Manager/Alt+Tab would pick up exactly that garbage-mask HICON. So `lib.rs` explicitly calls `context.set_default_window_icon(None)` at `run()`; Windows then falls back to the exe-embedded icon.ico (a proper multi-size .ico, no runtime HICON creation). Do **not** call `.icon()`/`set_icon()` on windows or remove this suppression.

## Behavioral Constraints

- "Always on top" 「窗口置顶」 and "pin to desktop" 「贴在桌面」 are either-or, exactly one must be active: turning one on auto-turns the other off; turning the current mode off switches to the other; default is "pin to desktop". At config load, legacy "both on / both off" states are normalized to "pin to desktop".
- Clicking the main window's X button = hide to tray, not quit; the tray's "Exit" 「退出」 is the real quit.
- Tray left-click = show/hide the manager, right-click = menu; while the manager window is shown it's visible in the taskbar/Alt+Tab (minimize restores normally); when hidden its taskbar button disappears with it; skin windows keep `skip_taskbar(true)` and never enter the taskbar.
- Skin resources are uniformly loaded through the `skin://` custom protocol (responsibilities and boundaries in "The skin:// Protocol"). Subresource references inside skin HTML **can only use relative paths or `http://skin.localhost/<skin id>/<path>`** — on Windows, WebView2 doesn't support subresource loading for non-standard protocols; writing `skin://` directly errors `ERR_UNKNOWN_URL_SCHEME` (styles/scripts silently fail to load).
- Theme variables only hang on `:root[data-theme="dark"]` (light is the default theme, variables directly on `:root`): the theme option buttons themselves carry the `data-theme` attribute (for JS to read), so a bare `[data-theme="dark"]` selector would apply the dark variables to those buttons — the same kind of accident once happened on the light tile (in dark mode the "Light" 「浅色」 button's black text was invisible at rest, turning white-background on hover); if the default theme flips, the direction reverses and the constraint applies the same way.
- Info toasts uniformly go through the `src/js/toast.js` singleton (a new toast replaces the old one, fading out upward then removed); do not add more showToast implementations that each `appendChild` — rapid consecutive operations would stack toasts.
- After the manager window is hidden → re-shown, buttons keep a stale :hover style: while the window is hidden WebView2 receives no mouseleave, and after re-showing it recomputes hover from the "last known cursor position" (still sitting on the button just clicked). Synthesized events can't clear it (not trusted input); only a real pointermove updates its cursor position — so the CSS `.win-btn:hover` rules are gated by `body.hover-ok` (`app.js` removes it on hide/blur and restores it on the first real pointermove), and buttons also `blur()` on click to avoid a stale :focus-visible outline.
- The manager window corner-rounding policy = **follow the system default**: Win11 rounds via DWM (`round_window_corners`, `DWMWA_WINDOW_CORNER_PREFERENCE`); Win10 has no such API and stays square — this is a product decision, not a defect. "Transparent window + CSS `border-radius`" was tried to round Win10 too, and was vetoed and reverted; do not add `transparent(true)` to the manager window to chase rounded corners. Corollary: **window-level elements (`body`/`#app`/`.settings-overlay`/`.wizard-overlay`) never get `border-radius`** — they once carried a 12px radius matching the rounded window frame, and on Win10's square windows the settings / install wizard overlays showed uncovered corner blocks; Win11's rounding is cropped by the DWM on the window frame and doesn't rely on those radii. Likewise, **Win10's 1px window stroke is backfilled by CSS** (the DWM draws no outline for frameless windows): `app.js` hangs a `no-native-frame` class on `<html>` per `is_windows_11_or_newer` (sysinfo's RtlGetVersion, build ≥22000 = Win11; falls back to true when unavailable / non-Windows), giving `#app` a `1px solid var(--border)` inner stroke — only backfilling Win10; Win11 keeps the native DWM look; restoring `decorations(true)` native frames was discussed and vetoed because it would introduce a duplicate title bar and lose the custom-drawn brand header.
- For the manager UI's color tokens, font/class-name contracts, the nautical-chart visuals and other visual mechanisms, see `docs/设计系统.md` (Chinese); read it before changing `src/css/style.css` and frontend template markup.
